# Модуль анализа существующего проекта (brownfield onboarding)

*ProjectArchitect · проектный документ · 2 октября 2026*
*Дополняет отчёт «Сервис автономной ИИ разработки». Языки: Python, C#, TypeScript, PowerShell.*

## Зачем нужен этот модуль

Основная архитектура сервиса рассчитана на проект, который с первого дня растёт внутри «контура проверок». Существующий проект устроен иначе. Он уже написан, правила в нём не записаны, и почти наверняка в нём есть дублирование, мёртвый код и неочевидные связи между частями. Если сразу включить строгий CI, он будет красным месяцами. Если подключить агентов без анализа, они начнут «улучшать» то, чего не понимают.

Поэтому для существующего проекта добавляется отдельный этап, который выполняется один раз перед подключением к основному конвейеру. На этом этапе проект только изучают. Анализ ничего не меняет в коде: он строит карту, снимает исходное состояние (baseline), восстанавливает решения и готовит для вас понятный отчёт. Код начинает меняться только после того, как вы утвердили результаты.

## Главная особенность вашего случая: четыре языка

Каждый инструмент статического анализа работает с одним языком. Python-линтер не видит C#, а проверка архитектуры для TypeScript ничего не знает о PowerShell-скриптах. Внутри одного языка инструменты видят связи хорошо, но **швы между языками для них невидимы**. Примеры таких швов: PowerShell-скрипт запускает собранную C#-программу с определёнными аргументами; TypeScript-интерфейс вызывает Python-сервер по HTTP; Python читает JSON, который записал C#.

Именно на этих швах ИИ-агенты чаще всего ломают проект молча. Агент меняет формат данных в C#, все проверки C# зелёные, а Python-часть падает только при реальном запуске. Поэтому модуль анализа добавляет к стандартной архитектуре два элемента:

- **`docs/INTERFACES.md` — реестр межъязыковых связей.** Одна запись на каждый шов: кто вызывает, кого, через что (аргументы командной строки, файл, HTTP, база данных), в каком формате. Где можно, формат описывается машинно-проверяемой схемой (например, JSON Schema).
- **Контрактные тесты (contract tests).** Для каждого шва пишется тест, который проверяет, что обе стороны по-прежнему понимают друг друга. Это единственный способ поймать поломку на стыке языков до запуска.

## Инструменты по языкам

Ниже набор, который запускается на этапе анализа и потом остаётся в CI. Общий принцип: проверка типов и линтер ловят ошибки на уровне методов и переменных, проверки архитектуры следят за связями между модулями, поиск мёртвого кода и дублирования следит за «лишним».

| Задача | Python | TypeScript | C# | PowerShell |
|---|---|---|---|---|
| Проверка типов | pyright или mypy | `tsc --noEmit` в strict-режиме | компилятор с nullable и «предупреждения = ошибки» | нет (язык без статических типов) |
| Линтер и форматирование | ruff | ESLint + Prettier (или Biome) | встроенные .NET-анализаторы, `.editorconfig`, `dotnet format`, Roslynator | PSScriptAnalyzer |
| Правила архитектуры | import-linter | dependency-cruiser | ArchUnitNET или NetArchTest.eNhancedEdition (в виде тестов) | готового инструмента нет; свои правила PSScriptAnalyzer или простой скрипт-проверка |
| Мёртвый код | vulture; deptry для лишних зависимостей | knip | анализаторы неиспользуемых членов (IDE0051/IDE0052), Roslynator; публичный код ловится слабо | инструмента нет; косвенно через покрытие Pester |
| Дублирование | jscpd | jscpd | jscpd | jscpd (поддержку проверить на пилоте) |
| Тесты и покрытие | pytest + coverage.py | Vitest или Jest | xUnit + coverlet | Pester (умеет считать покрытие) |
| Навигация агента по символам | Serena / LSP | Serena / LSP | Serena / LSP | Serena не поддерживает; только поиск по тексту |

Для всех языков сразу запускаются ещё две вещи. **Подсчёт объёма** (tokei или cloc) показывает, сколько кода на каждом языке. **Анализ истории git** находит «горячие точки» (hotspots): файлы, которые меняются чаще всего и при этом большие. Обычно именно там сосредоточены ошибки, и там же агент должен быть осторожнее всего.

Несколько честных оговорок по таблице. Для C# инструменты архитектуры работают с уже скомпилированным кодом, поэтому опечатка в имени пространства имён может дать «зелёный» тест, который на самом деле ничего не проверяет. Каждое такое правило нужно один раз проверить на заведомом нарушении. PowerShell — самое слабое звено: нет типов, нет готовых проверок архитектуры и мёртвого кода, и Serena его не поддерживает. Отсюда кандидат в первое ADR: **PowerShell остаётся тонким «клеем»** (запуск, настройка окружения), а вся логика живёт в Python или C#, где её можно проверять.

## Как проходит анализ

Анализ идёт в шесть шагов. Первые пять только читают проект. Шестой готовит почву для изменений и начинается после вашего утверждения.

**Шаг 1. Инвентаризация.** Какие языки и в каком объёме, как проект собирается и запускается, есть ли тесты и проходят ли они сейчас, какие внешние зависимости подключены, где горячие точки по истории git. Если проект сейчас не собирается или тесты красные, это фиксируется первым пунктом отчёта: дальше чинить что-то бессмысленно, пока не восстановлена сборка.

**Шаг 2. Снимок состояния (baseline).** Все инструменты из таблицы запускаются в режиме «только отчёт». Результаты сохраняются в `analysis/baseline/` в машинном формате (JSON). Это точка отсчёта для «храповика»: дальше CI будет требовать, чтобы ни одна из этих цифр не росла.

**Шаг 3. Карта проекта.** Агенты-explorer на дешёвой модели проходят проект по частям, по одному модулю или языку за раз, чтобы не перегружать контекст. Они заполняют черновики `docs/MODULES.md` (что делает каждый модуль, от чего зависит, кто его использует) и `docs/INTERFACES.md` (все найденные межъязыковые швы). Карта строится по коду, а не по старым README: документация в существующих проектах часто устаревшая.

**Шаг 4. Восстановление решений.** Агент-architect читает карту и baseline и пишет ADR задним числом со статусом `proposed`: «проект использует такую-то структуру», «данные между частями передаются так-то», «такой-то модуль не должен зависеть от такого-то». Отдельно он пишет `docs/QUESTIONS.md`: места, где намерение по коду непонятно. Например: «функция X нигде не вызывается, это мёртвый код или её запускают снаружи?» На эти вопросы отвечаете вы. ИИ здесь не должен угадывать.

**Шаг 5. Отчёт для вас.** Агент собирает `analysis/ANALYSIS_REPORT.md` на русском, без кода. В отчёте:
- карточка здоровья проекта (ниже);
- 5–10 главных рисков с объяснением последствий;
- список ADR, ждущих вашего решения, каждое одной строкой;
- вопросы из QUESTIONS.md;
- предлагаемый порядок наведения порядка.

Перед тем как отчёт попадёт к вам, его проверяет отдельный агент-reviewer в чистом контексте. Он сверяет утверждения отчёта с baseline и кодом, чтобы карта не содержала выдуманных связей.

**Шаг 6. Включение контура (после вашего утверждения).** Утверждённые ADR превращаются в правила архитектурных проверок. CI включается в режиме храповика: новых нарушений ноль, старые допускаются, но их число может только уменьшаться. Перед любым рефакторингом участков без тестов пишутся **характеризационные тесты (characterization tests)**. Они фиксируют текущее поведение кода, даже если оно странное, чтобы при переделке было видно, что что-то изменилось. После этого проект подключается к обычному конвейеру, и агент-janitor начинает по расписанию разбирать накопленный мёртвый код и дублирование небольшими PR.

## Карточка здоровья проекта

Это то, что вы видите в отчёте без чтения кода. По каждому языку отдельно:

| Сигнал | Что значит | Тревожно, если |
|---|---|---|
| Сборка и тесты проходят | проект вообще в рабочем состоянии | нет |
| Число тестов и покрытие | насколько безопасно что-то менять | тестов почти нет, особенно в горячих точках |
| Ошибки типов и линтера | количество мелких дефектов | сотни на тысячу строк |
| Нарушения архитектуры | насколько запутаны связи | есть циклические зависимости между модулями |
| Мёртвый код | сколько лишнего | заметная доля кода не используется |
| Дублирование | сколько копипасты | процент выше примерно 5–10% |
| Межъязыковые швы без тестов | где поломка будет незаметной | любой шов без контрактного теста |
| Горячие точки | где сосредоточен риск | большие файлы, которые часто меняются и без тестов |

Пороги в правом столбце — ориентиры для первого знакомства, а не научно обоснованные границы. После первого анализа важнее не абсолютные числа, а их динамика.

## Что анализ не делает и почему

**Ничего не удаляет.** Инструменты поиска мёртвого кода дают ложные срабатывания. В C# код может вызываться через рефлексию, в Python — динамически, PowerShell-скрипт может запускаться планировщиком задач или другим скриптом через dot-sourcing, а точку входа может вызывать внешняя программа. Поэтому найденный «мёртвый» код сначала попадает в вопросы для вас, потом в реестр со статусом (удалить / оставить с меткой `keep-until`), и только потом janitor удаляет его отдельным PR с архивным тегом в git. Удалённое всегда можно вернуть.

**Не переписывает архитектуру.** Даже если анализ покажет, что структура плохая, первая цель — зафиксировать то, что есть, и остановить ухудшение. Переделка идёт потом, маленькими шагами, каждый под защитой тестов.

**Не гарантирует понимания намерений.** ИИ видит, что код делает, но не всегда понимает зачем. Всё, что касается смысла, проходит через ваши ответы в QUESTIONS.md и утверждение ADR.

## Стоимость в токенах

Анализ большого проекта — самая дорогая разовая операция в сервисе. Основную работу (запуск инструментов, подсчёт метрик) делают обычные программы, токены на это не тратятся. Агенты читают уже готовые отчёты инструментов и обходят код по модулям, а не целиком. Для обхода используется дешёвая модель, для ADR и итогового отчёта — сильная. Результат анализа сохраняется в файлах, поэтому повторять его не нужно. Дальше CI просто сравнивает текущее состояние с baseline.

## Место в общем плане сборки

Для нового проекта порядок фаз остаётся прежним. Для существующего проекта этот модуль становится **фазой 0-б**: после фундамента (репозиторий, защищённая ветка, базовый CI) и до hooks и остальных фаз. Сам модуль удобно оформить как skill для Claude Code (например, `/analyze-existing`). Тогда его можно одной командой запустить на любом вашем проекте, и он каждый раз будет проходить одни и те же шаги.

## Открытые вопросы для пилота

- Проверить на реальном проекте, насколько хорошо jscpd работает с PowerShell.
- Выбрать для C# между ArchUnitNET и NetArchTest.eNhancedEdition по результатам пилота.
- Решить, каким способом передавать данные через межъязыковые швы (файлы, HTTP, командная строка), чтобы их можно было описывать схемами. Это кандидат во второе ADR.
