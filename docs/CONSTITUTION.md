# CONSTITUTION — ProjectArchitect

> **Как пользоваться этим файлом.** Это главные правила проекта. Их утверждает только владелец. Агенты
> читают этот файл, соблюдают его и сами не меняют (защита включена, правка потребует вашего подтверждения).
> Два раздела ниже («Разрешённые пакеты» и «Команды проверки») читают автоматические проверки, поэтому
> оставляйте их заголовки и формат строк как есть.

## О проекте

Набор инструментов (плагин Claude Code и шаблоны), который подключается к программному проекту и держит ИИ-разработку под контролем.

## Версия стандарта

ProjectArchitect 1.3 (docs/STANDARD.md в репозитории продукта). При выходе новой версии
`/parch:analyze-existing` покажет, что изменилось.

## Целевая ОС

Windows 11

> На этой системе работает исполнитель (Claude Code): он запускает тесты и проверки на ней при каждой сессии
> бесплатно. CI всегда идёт на Linux (`ubuntu-latest`) и проверяет, что в код не попало ничего, привязанного
> к одной системе. Раннер Windows или macOS в CI добавляется только через ADR с оценкой стоимости
> (Windows считается в квоте как x2, macOS как x10). STANDARD.md, 7.2.

## Что для владельца важно

- надёжность проверок: ИИ не может их заглушить
- понятность владельцу без чтения кода
- экономия квоты CI

## Правила для агентов

- Одна задача, одна ветка, один pull request. В `main` напрямую не пушим.
- Тесты правят только роли architect и tester. Тест не «подгоняют» под код.
- CI-файлы, настройки Claude, этот файл и принятые ADR меняются только с подтверждения владельца.
- Новая зависимость требует ADR. Решения, которые трудно отменить, оформляются как ADR и ждут утверждения.
- Новые `.md`-файлы создаются только в `docs/`. Рабочие заметки в репозиторий не кладём.
- Каждое решение, отчёт и описание PR для владельца пишутся по-русски и на языке последствий:
  что изменится, что будет при ошибке, как откатить.
- Перед новой функцией, классом или модулем (роль `implementer`, полный текст в её описании), по порядку:
  1) каталог возможностей `docs/CAPABILITIES.md` и реестр модулей `docs/MODULES.md`; 2) поиск по коду;
  3) `git log -S"имя"` по затрагиваемым файлам; 4) `docs/LESSONS.md`, `state/incidents/`, ADR;
  5) только потом решение: переиспользовать, расширить или создать новое. Чего не хватает, записать в
  `docs/QUESTIONS.md` и остановиться. Раздел «Основания»: что искал и почему создал новое; он пишется один раз, в сообщении коммита ветки (CI читает
  `git log main..HEAD`), а в описание PR вставляется командой `python .github/parch/parch_ci.py basis`.
