# ADR-0012. Табло STATUS.md: пересчёт после слияния и где оно публикуется

- Статус: proposed
- Тип решения: необратимое (форма табло и место публикации закрепятся в подключённых проектах)
- Дата: 2026-10-03

## Контекст

Стандарт (7.1) говорит: файл `state/STATUS.md` генерирует CI после каждого слияния, владелец смотрит его на GitHub.
Одновременно (7.2, правило 6) CI запускается только на `pull_request`, а после слияния допускается только отдельная
маленькая работа по пересчёту состояния. Эта работа должна положить результат туда, где его увидит владелец, а ветка
`main` защищена: в неё можно попасть только через PR с зелёными проверками.

Простое решение «CI сам коммитит `STATUS.md` в `main`» здесь не работает:

- прямая запись в `main` запрещена правилами ветки; чтобы её разрешить, GitHub-приложению Actions нужно дать обход
  защиты, а обход действует на любой workflow репозитория: PR, который правит workflow, мог бы записать что угодно в `main`
  и тем самым отменил бы защиту ветки;
- PR, созданный самим CI (`GITHUB_TOKEN`), не запускает проверки, а без них обязательные проверки не пройдут и PR не
  сольётся; для обхода нужен личный токен владельца в секретах, то есть ещё один ключ, который нужно хранить и обновлять.

## Решение (рекомендация, ждёт утверждения владельца)

1. **Табло публикуется на отдельной ветке `status`**, а не в `main`. Workflow `state.yml` (запуск на push в `main`,
   `timeout-minutes: 10`, отмена предыдущих запусков, Ubuntu) строит `state/STATUS.md` и коммитит его в ветку `status`
   (создаёт, если нет). Ветка `main` остаётся защищённой и ничего от этого workflow не получает. Страница открывается на
   GitHub: `https://github.com/ВЛАДЕЛЕЦ/ПРОЕКТ/blob/status/state/STATUS.md`, в том числе с телефона; Mermaid GitHub рисует сам.
2. **Тесты не запускаются.** Отчёт берётся из прогона CI того PR, который слит (артефакт `test-report`, срок хранения
   14 дней). Для PR только с документами отчёта нет: берётся последний известный отчёт, который хранится рядом
   с табло на ветке `status` (`state/test-report.xml`).
3. **Табло строится только из файлов и результатов CI**: `docs/GOAL.md`, `state/features.json`, отчёт тестов,
   `state/incidents/`, ADR со статусом `proposed`, открытые вопросы `docs/QUESTIONS.md`, открытые PR (GitHub API).
   Своих данных у него нет. Генератор: `parch_status.py` (только стандартная библиотека), покрыт тестами.
4. **Готовность блока считается по тестам приёмки**: блок «готов», если все его тесты приёмки (`acceptance_tests` в
   `features.json`) есть в отчёте и прошли, а все блоки, от которых он зависит, готовы. Статус `done` в самом
   `features.json` вручную не ставится (стандарт, раздел 3): такая отметка без прошедших тестов показывается
   предупреждением. Поля `passes` и `incidents` в `features.json` становятся производными: табло считает их каждый раз
   заново и в `main` ничего не записывает.
5. **Табло не скрывает, откуда отчёт.** Отчёт тестов берётся с коммита PR (при слиянии «в один коммит» он отличается
   от коммита `main`). Workflow сравнивает содержимое: если оно то же, табло пишет коммит отчёта; если нет, или отчёт
   старый (взят из ветки `status`), или коммит неизвестен, в начале табло стоит предупреждение «Отчёт тестов снят не с
   текущего коммита» с коммитом отчёта.
6. **Статусы блока.** Добавлен `waiting_owner` («ждёт владельца»): такой блок выводится в «Нужно ваше решение».
   `blocked` и `stuck` без отчёта `state/incidents/ГГГГ-ММ-ДД-БЛОК-*.md` нарушают проверку `standard` (и отмечены
   на табло); `blocked` в «Нужно ваше решение» не попадает, это блок, который ждёт устранения причины, а не вас.
7. **Расход CI на табло это ссылка на страницы GitHub** (решение владельца): минуты и деньги там точные, без токена с
   правом чтения биллинга. Это отступление от правила 10 раздела 7.2 («минуты на табло и под храповиком»); оно записано
   здесь, и это решение владельца.
8. **Диаграммы зависимостей** строятся по одной небольшой на критерий готовности (одна общая не масштабируется и
   нечитаема на большом плане).
9. **Первое табло** строится для самого репозитория продукта: `docs/GOAL.md` (черновик критериев G1-G5, их утверждает
   владелец) и `state/features.json` с блоками плана и тестами приёмки.

## Известные ограничения

- Планировщик (Claude Project) синхронизирует знания из одной ветки репозитория. Табло лежит на ветке `status`, поэтому
  его нужно синхронизировать отдельно или читать по ссылке (это связано с открытым вопросом 13.2 стандарта). Пока владелец
  смотрит табло сам по ссылке.
- Таблицу готовности по тестам приёмки пока считает только отчёт Python (JUnit) в шаблоне CI; для TypeScript, C# и
  PowerShell шаблоны выкладывают свои отчёты позже (отдельным PR); до этого блоки этих проектов не станут «готовыми».
- Ветка `status` содержит только сгенерированные файлы. PR, который правит workflow, мог бы записать в неё чужое табло:
  правка `.github/` требует вашего подтверждения (ADR-0003), так что такой PR вы видите.
- Нужна работа с настоящим GitHub: workflow проверен тестами структуры, но не запускался на GitHub до слияния.

## Последствия для владельца

- Что изменится: после каждого слияния в `main` обновляется страница-табло на ветке `status`; вы смотрите её вместо отчётов агента.
- Если решение окажется ошибкой: табло можно перенести (в `main` через токен, на GitHub Pages) отдельным ADR, генератор не
  изменится.
- Как откатить: удалить `.github/workflows/state.yml` и ветку `status`; на проект это не влияет.

## Рассмотренные альтернативы

- Коммит в `main` с обходом защиты для Actions: отменяет защиту ветки для любого workflow (см. контекст).
- PR от CI с личным токеном: лишний секрет, который нужно хранить и обновлять; такие PR ещё и создают шум в истории.
- Только артефакт или сводка запуска: исчезает через 14-90 дней и не открывается как обычная страница.
- GitHub Pages: отдельный сайт с публичным адресом, который нужно включать и настраивать.
