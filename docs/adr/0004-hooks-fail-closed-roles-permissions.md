# ADR-0004. Как устроены hooks: границы действия, поведение при сбое, роли, снятие блокировки и permissions

- Статус: proposed
- Тип решения: необратимое (на этих договорённостях строятся фазы C–F и шаблоны для всех проектов)
- Дата: 2026-10-02

## Контекст

Фаза B добавляет шесть hooks: `guard_paths`, `guard_packages`, `guard_destructive`, `post_edit_check`,
`stop_gate`, `audit_log`. При чтении документации Claude Code выяснилось несколько фактов, которые
влияют на устройство и расходятся с BUILD_PLAN.md:

- Hook, который не запустился, завис или упал с кодом 1, **не блокирует** действие. Блокирует только код 2.
  Значит, сломанная защита по умолчанию молча пропускает всё.
- Плагин не может поставлять правила `permissions`: из `settings.json` плагина действуют только два ключа
  (`agent`, `subagentStatusLine`). План же ждал «правила permissions» вместе с плагином.
- На Windows без Git Bash у Claude Code нет инструмента Bash, команды идут через PowerShell. Hook с условием
  «только Bash» там не сработает ни разу.
- Роль агента доступна в поле `agent_type`; для агентов плагина это `parch:implementer`, а не просто `implementer`.
- Поле `stop_hook_active` есть, и сверх него Claude Code сам обрывает цепочку после 8 блокировок подряд.
- Правило `ask` в настройках заставляет Claude Code спросить человека в любом режиме, включая
  `bypassPermissions`; нажать «разрешить» агент сам не может.

## Решение

1. **Где hooks работают.** Охранные и проверочные hooks действуют только в проектах, где есть `CONSTITUTION.md`
   (`docs/CONSTITUTION.md` или в корне). Исключение: `guard_destructive` действует везде. Так плагин не мешает
   в проектах, которые к ProjectArchitect не подключены.
2. **Сбой охранника = блок.** Охранные hooks (`guard_*`) при любой внутренней ошибке или нечитаемом входе
   завершаются кодом 2 и просят сообщить владельцу. Hooks `post_edit_check` и `stop_gate` при сбое не блокируют
   (иначе упавшая проверка навсегда запирает сессию), а лишь сообщают о сбое.
3. **Ограничения действуют на всех по умолчанию, включая основную сессию без роли.** Разрешения выдаются явно:
   - **Тесты** (папки `tests`, `test`, `__tests__`, `spec`, файлы `test_*.py`, `*.test.*`, `*.spec.*`, `*Tests.cs`,
     `*.Tests.ps1`) правят только роли `architect` и `tester`. Всем остальным, в том числе основной сессии без
     роли, блок с пояснением. Роль берётся из последней части `agent_type`. Агента `tester` в плане пока нет,
     имя заложено заранее.
   - **Защищённые пути:** `.claude/` и `.claude-plugin/` (настройки Claude и hooks), `.mcp.json`, CI-файлы
     (`.github/`, `.gitlab-ci.yml` и др.), `state/features.json`, `CONSTITUTION.md` (**сверх плана**: иначе можно
     самому внести нужный пакет в список разрешённых и обойти `guard_packages`), принятые ADR. Для всех ролей,
     без исключений, кроме снятия блокировки владельцем (пункт 4).
4. **Как владелец снимает блокировку.** Для защищённых путей hook отвечает Claude Code решением «ask»: владельцу
   показывается окно подтверждения с пояснением, что именно и зачем меняется. Агент
   подтвердить такое окно не может, потому что нажатие делает человек в интерфейсе. Разрешение действует на это
   одно действие, ничего не остаётся «открытым», перезапуск не нужен. Если спросить некого (режимы `bypassPermissions`
   и `dontAsk`, фоновый запуск без человека), правка запрещается совсем, а в сообщении сказано, как быть:
   владелец вносит правку сам или запускает сессию в обычном режиме. Тест показывает, что переменная окружения
   или лишнее поле во входе блокировку не снимают.
5. **Исключения для `.md`:** создавать новые `.md` можно внутри любой папки `docs/`, в `analysis/` и `state/`, а также
   `AGENTS.md`, `CLAUDE.md`, `README.md` в корне, `SKILL.md` внутри `skills/` и файлы агентов в `agents/`.
6. **Контракт с `CONSTITUTION.md` (его шаблон появится в фазе C).** Раздел «Разрешённые пакеты» — строки вида
   `- pip: requests, pydantic` (экосистемы `pip`, `npm`, `nuget`, `psgallery`). Раздел «Команды проверки» — по команде
   на строку; если его нет, `stop_gate` сам подбирает pytest, ruff и pyright для Python-проекта.
7. **Permissions.** Поскольку плагин правила поставлять не может, они лежат шаблоном `templates/claude/settings.json`
   (новая папка, в разделе 3 плана её нет). `/parch:init-project` (фаза C) копирует его в `.claude/settings.json`
   проекта. Там два списка. `ask` (спросить владельца): настройки Claude и hooks, `.github/`, `CONSTITUTION.md`.
   `deny` (запретить совсем): правка журнала `.claude/audit/`, чтение секретов (`.env` кроме `.env.example`, ключи,
   `~/.ssh`, `~/.aws`), `rm -rf`, `git push --force`, `git reset --hard`, `git clean` с `-f`/`-d`/`-x`.
   Правила `ask` работают независимо от hooks и в режиме `bypassPermissions` тоже, поэтому это вторая линия защиты.
   Жёсткая защита держится на них; разбор команд оболочки в hooks приблизительный.
8. **Запуск hooks.** `"command": "python"` с `args` (без оболочки), скрипты только на стандартной библиотеке.
   Matcher'ы охранников включают `Bash|PowerShell`.
9. **Журнал.** `.claude/audit/ГГГГ-ММ-ДД.jsonl`, одна запись на строку: время, сессия, роль, hook, решение
   (`attempt`, `block`, `ask`, `ok`...), детали. Пароли и токены в командах затираются.
10. **Защита `stop_gate` от зацикливания.** Если Claude Code уже продолжает из-за этого hook и ошибки не изменились,
    остановка разрешается с предупреждением владельцу. Если ошибки изменились, агент получает ещё попытку.
11. **Опасные команды (`guard_destructive`, для всех ролей, везде):** `rm -rf` и аналоги, `git push --force`,
    `git reset --hard`, `git clean` с флагами `-f`, `-x`, `-X`, `-d` (пробный `git clean -n` разрешён), вывод всех
    переменных окружения, обращения к секретам.

## Известная дыра: новый пакет через файл зависимостей

`guard_packages` проверяет команды установки. Но новый пакет можно добавить и правкой файла зависимостей
(`requirements.txt`, `package.json`, `pyproject.toml`, `*.csproj`) с последующей обычной сборкой (`npm install`,
`pip install -e .`, `dotnet restore`). Такую правку hook не видит: файл обычный, а установка идёт из манифеста.
**Закрытие:** проверка CI в фазе D: зависимости из манифестов сверяются со списком в `CONSTITUTION.md`, расхождение
валит CI. До фазы D дыра открыта; снижает риск только то, что CI-файлы и `CONSTITUTION.md` агенту недоступны.

## Открытые риски

- **`python` на macOS.** На Mac команда может называться только `python3`; тогда `"command": "python"` не найдёт
  интерпретатор, и все hooks молча не сработают (см. факт про код 1 выше). CI на macOS зелёный, но у GitHub-раннера
  `python` есть всегда. Результата проверки на вашем Mac у меня пока нет. Запасной вариант запуска описан ниже.
- Hooks не проверялись живым агентом: сессия Claude Code в этой среде не авторизована. Проверено: Claude Code
  принимает плагин (`claude plugin validate`, `claude plugin details` показывает события hooks), тесты запускают
  каждый hook так же, как Claude Code (JSON на stdin, код выхода, stdout и stderr).
- Что именно показывает окно подтверждения при ответе hook «ask» (в частности, виден ли текст причины) в живой
  сессии не проверялось. Если причина не видна, подтверждение остаётся, но пояснять придётся словами агента.
- Команды, которые обходят разбор (например, `python -c "open('tests/x','w')"`), hooks не видят. От них защищают
  правила permissions и, при необходимости, песочница Claude Code.

## Запасной вариант запуска hooks, если на Mac нет `python`

Один запускающий файл `plugin/hooks/run-hook.cmd`, составленный так, чтобы одновременно быть и скриптом для оболочки
sh (macOS, Linux), и пакетным файлом для Windows. Он перебирает `python3`, `python`, `py -3` и запускает нужный
скрипт, передавая ему код выхода как есть. В `hooks.json` все команды меняются на `"command": "${CLAUDE_PLUGIN_ROOT}/hooks/run-hook.cmd"`
с аргументом-именем скрипта. Плюсы: работает без правки Mac. Минусы: один дополнительный файл, форма запуска через
оболочку (пути с пробелами нужно брать в кавычки), больше мест для ошибки; потребуются тесты на всех трёх системах.
Альтернатива попроще: у себя на Mac создать команду `python`, указывающую на `python3` (например, ссылку
`ln -s "$(which python3)" /usr/local/bin/python`), без изменений в плагине.

## Последствия для владельца

- Что изменится: агенты (все роли, включая основную сессию) не смогут сами менять тесты, CI, настройки Claude,
  список пакетов и принятые решения; тесты правят только architect и tester. Когда правка нужна, вы увидите окно
  подтверждения и решите сами. Агенты не смогут стереть данные одной командой и читать секреты, а перед остановкой
  придётся проходить тесты и проверки.
- Если решение окажется ошибкой: слишком строгие правила будут мешать работе (агент будет упираться в блок и
  просить вас, окон подтверждения будет много); слишком мягкие пропустят нарушение. Оба случая видны в журнале
  `.claude/audit/`.
- Как откатить: выключить плагин (`claude plugin disable parch@project-architect`) или удалить hook из
  `plugin/hooks/hooks.json`; правила permissions убираются удалением строк из `.claude/settings.json` проекта.

## Рассмотренные альтернативы

- Снимать блокировку файлом-разрешением или переменной окружения: агент работает от вашего имени и может создать
  такой файл или запустить команду сам. Подтверждение человеком в окне интерфейса для агента недоступно.
- Включать hooks везде, а не только при наличии `CONSTITUTION.md`: плагин мешал бы в посторонних проектах.
- Блокировать и при сбое `stop_gate`: одна поломка запирала бы сессию, которую нельзя завершить.
- Пытаться поставлять permissions внутри плагина: документация этого не допускает.
