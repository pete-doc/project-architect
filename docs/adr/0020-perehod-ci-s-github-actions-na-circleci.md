# ADR-0020. Перевод CI продукта с GitHub Actions на CircleCI (параллельная работа обоих на переходный период)

- Статус: proposed
- Тип решения: обратимое (оба CI работают, откат это удаление `.circleci/`), но меняет расходы и источник проверок
- Дата: 2026-10-06
- Дополняет ADR-0011 (раннеры и стоимость CI) и ADR-0013 (быстрая и полная части): они остаются в силе для GitHub Actions.

## Контекст

CI на GitHub Actions нестабилен. 2026-10-05 три попытки задания `check` подряд закончились сообщением «The job was not acquired
by Runner of type hosted even after multiple attempts» (по 15 минут ожидания, отмена; у GitHub в это время был частичный сбой),
а скорость раннеров и раньше плавала почти вдвое (ADR-0011, изменение 2026-10-03). Владелец решил перевести CI на CircleCI
(проект в CircleCI создан). Режим CircleCI «GitHub Actions workflow как конфиг» не подошёл: он не поддерживает `windows-latest`,
а Windows 11 целевая платформа продукта (проверка hooks).

## Решение

1. Добавляется `.circleci/` в родном формате CircleCI (версия 2.1), повторяющий логику `ci.yml`. **GitHub Actions пока
   не удаляются и не выключаются**: первое время работают оба. Полный прогон `full-run` и пересчёт табло `state` остаются на
   GitHub Actions (ruleset `protect-main` требует `check`, `full-run` и `windows-hooks` именно от GitHub Actions, ADR-0013); перевод
   этих двух частей и смена обязательных проверок отдельное решение владельца после периода параллельной работы.
2. Конфигурация динамическая: `.circleci/config.yml` (setup-конфиг) считает состав PR и передаёт его в
   `.circleci/continue_config.yml`. Состав считает прежний `.github/scope.py`, список файлов берётся командой
   `git diff --name-only origin/main...HEAD` (без `gh`); не получилось: запасной путь «все языки», как сейчас. Правка самого
   `.circleci/` считается правкой CI: идут все языки и Windows.
3. Запуск: CircleCI собирает каждый push в любую ветку, включая черновики PR; в конфиге ветки `main` и `status` исключены.
   Чтобы не тратить кредиты на ветки без PR, **владельцу рекомендуется включить в проекте «Only build pull requests»**
   (в конфиге такого ограничения нет); оценка ниже считает только отправки в PR.
4. Задания и классы ресурсов:
   - `scope` (setup): Docker `small`, 5 кредитов/мин, около 1 минуты;
   - `check-text` (PR только с текстом): Docker `small`, только `standard`;
   - `check` (PR с кодом): Docker `large` (4 vCPU, 8 ГБ, 20 кредитов/мин). Тесты идут с явным `-n 4`: в контейнере CircleCI
     `-n auto` видит ядра хоста, а не 4 vCPU класса, и мог бы породить слишком много процессов (в `AGENTS.md` описан отказ полного
     прогона из-за памяти);
   - `windows-hooks`: Windows executor `win/server-2022`, класс `windows.medium` (**40 кредитов/мин**, ADR-0011 требует назвать не-Linux
     раннер в принятом ADR), только если PR меняет `plugin/hooks/**`, `plugin/templates/**`, `.github/**` или `.circleci/**`.
5. Таймауты. У CircleCI нет `timeout-minutes` на задание (общий предел плана Free: 1 час на задание). Вместо него:
   `no_output_timeout` на долгих шагах (срабатывает только при молчании) и общий предел времени на сами тесты:
   `timeout 1500` (25 минут) в `check` и ожидание процесса не дольше 15 минут в `windows-hooks`. Отмена устаревших прогонов настройкой
   проекта, не конфигом: **Project Settings → Advanced → Auto-cancel Redundant Workflows = включить** (действие владельца).
   Работает ли она для прогонов, продолжающих динамическую конфигурацию (continuation), из документации не подтверждено:
   проверить на первом реальном прогоне; если не работает, устаревшие прогоны будут добегать и тратить кредиты.
6. Кэши: pip, npm, .NET SDK и NuGet, PowerShell и модуль PSScriptAnalyzer 1.25.0 (ключи по тем же файлам, что в `ci.yml`).
7. Отличия от GitHub, о которых нужно знать: версия Node берётся из образа `cimg/python:3.12-node` (текущая LTS), а не закреплена
   на 22, как в `ci.yml`; в Windows-задании Python 3.12 ставится через `choco`, если его нет.
8. `parch_ci.py standard` читает стоимость CI только из `.github/workflows`; обучать его `.circleci/config.yml` сейчас не нужно (пока
   GitHub Actions остаются, проверка по ним сохраняется), но до выключения GitHub Actions это нужно сделать (`docs/BACKLOG.md`):
   иначе стоимостные правила станут невидимыми. До тех пор их держит тест `tests/test_circleci_config.py` (фильтр веток, Windows только
   при изменении hooks, предел времени, отчёт при падении тестов). Тест `test_github_actions_are_not_removed_yet` временный: его снимет
   только решение владельца о выключении GitHub Actions.

## Оценка кредитов

Цены по документации CircleCI: Docker small 5, medium 10, large 20 кредитов/мин; Windows medium 40 кредитов/мин
(circleci.com/pricing, страница классов ресурсов; Windows доступен на плане Free). Время берётся по прошлым прогонам на GitHub
(`check` с кодом 10 минут, текст 10 секунд, Windows 1 минута тестов) с запасом на раннеры CircleCI и подготовку.

| Что | Время | Кредиты за одну отправку |
|---|---|---|
| PR с кодом (`scope` 1 мин small + `check` ~12 мин large) | ~13 мин | ~245 |
| PR только с текстом (`scope` + `check-text` ~2 мин small) | ~3 мин | ~15 |
| PR с hooks (Windows medium ~4 мин, включая установку Python и pip) | ~4 мин | ~160 сверху |

(`scope` входит в первые две строки и учтён ещё раз в месячной сумме: оценка с небольшим запасом.)

**Платный и бесплатный пул.** Бесплатный план: 30 000 кредитов в месяц, не переносятся. Но репозиторий публичный, и по официальной
странице CircleCI для открытых проектов (circleci.com/open-source) организации на плане Free получают **до 400 000 кредитов в месяц
на сборки Linux, Arm и Docker** и 30 000 на macOS и Windows; справка CircleCI формулирует тот же пул как 100 000 кредитов в неделю на
Linux, при условии, что репозитории публичны и проект отмечен как открытый. Эти кредиты не видны в интерфейсе и не уменьшают общий
счёт. Сверка с документацией (2026-10-06): суммы на странице и в справке совпадают по порядку (около 400 000 в месяц на Linux),
по Windows пул указан только на странице (30 000), справка его не называет.

Месяц, ориентировочно (оценка, не измерение; реальную скорость покажет первая неделя):

| Сценарий | Linux (check, check-text, scope) | Windows | Куда считается |
|---|---|---|---|
| Спокойный: 30 отправок с кодом, 40 с текстом, 8 с hooks | ~8 500 | ~1 300 | Linux вписывается и в 30 000, и в открытый пул с запасом |
| Интенсивный (как последние дни): ~100 отправок с кодом, 60 с текстом, 20 с hooks | ~26 000 | ~3 200 | Linux на пределе обычных 30 000, но с запасом в открытом пуле (400 000, около 6,5 %) |

Если открытый пул применён, расход Linux не упирается в лимит ни в одном сценарии, а Windows (3 200 из 30 000) тоже вписывается.
Если проект не признан открытым, действуют обычные 30 000 кредитов: интенсивный месяц на пределе; выше предела платный план
Performance (от 15 долларов в месяц, 30 000 кредитов включено, дальше покупаются). Что именно применено, владелец видит в
Plan Usage CircleCI после первой недели. Во время параллельной работы GitHub Actions продолжают тратить собственную квоту.

## Проверка конфигов

Официальный CLI CircleCI (`circleci` 1.0.52041, скачан с `CircleCI-Public/circleci-cli`, контрольная сумма совпала) выполнил
`circleci config validate` для обоих файлов: оба валидны (первая версия setup-конфига не прошла: вставка кода через `<<` в
конфиге 2.1 должна быть экранирована, исправлено). Живого прогона в CircleCI ещё не было; не проверено: установка Python на
Windows через `choco`, наличие `sh` для тестов hooks на Windows, установка PowerShell 7.4.6 и .NET по `global.json` в образе
`cimg/python`, ключи кэшей. Скрипт состава PR выполняется тестами во временных git-репозиториях (текст, hooks, правка
`.circleci/`, имена не ASCII, нет базовой ветки).

## Последствия для владельца

- Что изменится: у каждого PR появятся ещё проверки от CircleCI (названия вида `ci/circleci: ...`), в ruleset они пока не обязательны.
  Обязательными остаются проверки GitHub Actions.
- **Нужно действие владельца в CircleCI:** (1) включить «Auto-cancel Redundant Workflows»; (2) убедиться, что включена динамическая
  конфигурация (Project Settings → Advanced → «Enable dynamic config using setup workflows»; для проектов, созданных после
  2023-12-01, включена по умолчанию); (3) включить «Only build pull requests»; (4) проверить в Plan Usage, что проект учтён как
  открытый (пул 400 000 кредитов).
- Риск: первый прогон может потребовать правок окружения (см. «Проверка конфигов»).
- Если решение окажется ошибкой: удалить `.circleci/`, GitHub Actions продолжают работать.
- Как откатить: удалить `.circleci/`, этот ADR заменить новым.

## Рассмотренные альтернативы

- Режим «GitHub Actions workflow как конфиг» в CircleCI: не поддерживает `windows-latest`.
- Состав PR через `path-filtering` (оркестр CircleCI): умеет только логические значения по шаблонам путей, а нужны ещё
  строка выбора тестов и правила «только текст»; проще переиспользовать `scope.py`, который уже проверен тестами.
- Один executor Linux machine вместо Docker: те же 10 кредитов/мин на medium, но образ `ubuntu` не гарантирует нужных `dotnet` и `pwsh`.
- Сразу выключить GitHub Actions: нет, пока обязательные проверки ruleset берутся оттуда.
