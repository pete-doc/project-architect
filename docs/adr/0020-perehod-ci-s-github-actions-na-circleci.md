# ADR-0020. CI продукта живёт на CircleCI, GitHub Actions для CI самого репозитория убраны

- Статус: accepted (решение владельца, 2026-10-06)
- Тип решения: обратимое (откат: вернуть три workflow из истории git), но меняет расходы, обязательные проверки и источник права на слияние
- Дата: 2026-10-06
- Дополняет и частично заменяет ADR-0011, ADR-0012 и ADR-0013 для CI самого репозитория продукта: для него полным прогоном перед слиянием, табло и обязательными проверками теперь служит CircleCI. Для шаблонов CI проектов пользователей (`plugin/templates/ci/`) эти ADR остаются в силе: шаблоны по-прежнему GitHub Actions.

## Контекст

CI на GitHub Actions нестабилен. 2026-10-05 три попытки задания `check` подряд закончились сообщением «The job was not acquired
by Runner of type hosted even after multiple attempts» (по 15 минут ожидания, отмена; у GitHub в это время был частичный сбой),
а скорость раннеров и раньше плавала почти вдвое (ADR-0011, изменение 2026-10-03). Владелец решил перевести CI на CircleCI
(проект создан) и убрать GitHub Actions для CI самого репозитория полностью. Режим CircleCI «GitHub Actions workflow как конфиг» не
подошёл: он не поддерживает `windows-latest`, а Windows 11 целевая платформа продукта (проверка hooks).

Первый прогон на CircleCI (коммит `21f01ed`) прошёл: `scope` 6 с, полная проверка 9 мин 8 с, Windows 2 мин 13 с.

## Решение

1. **Убраны** `.github/workflows/ci.yml`, `full.yml`, `state.yml`. **Остаются** `.github/scope.py` (его вызывает CircleCI) и
   `plugin/templates/ci/` (шаблоны для проектов пользователей).
2. **Динамическая конфигурация.** `.circleci/config.yml` (setup) считает состав PR и передаёт `code` и `hooks` в
   `.circleci/continue_config.yml`. Состав считает прежний `.github/scope.py` по
   `git diff --name-only origin/main...HEAD` (без `gh`); не получилось: запасной путь «все языки». Правка `.circleci/` считается
   правкой CI: идут все проверки и Windows.
3. **Одна проверка на PR, она же полный прогон.** Аналога «перевод из черновика в готов» как триггера в CircleCI нет (в
   интерфейсе триггеров есть «PR marked ready for review», но он создаёт отдельный запуск, а надёжность связки с обязательной
   проверкой не проверена). Поэтому раздел быстрой части и полного прогона (ADR-0013) снят: на каждую отправку в ветку PR (включая
   черновики) идут все тесты (`-m ""`), храповик `tests` и `skips` без `--partial`. Строки «`gh pr ready`, затем `--undo`»
   из правил больше не нужны.
4. **Имена проверок постоянные.** У каждого PR есть `ci/circleci: check` (у PR только с текстом это маленькое задание с одним `standard`,
   в workflow оно называется `check`) и `ci/circleci: windows-hooks` (у PR, не меняющего hooks, это заглушка на маленьком контейнере с тем же
   именем: иначе обязательной проверки не было бы, а «пропущенное» задание CircleCI не создаёт статус). Плюс `ci/circleci: scope`.
5. **Классы ресурсов** (ADR-0011 требует назвать не-Linux исполнитель и большие классы):
   - `scope`, `check` для текста, заглушка Windows: Docker `small`, 5 кредитов/мин;
   - `check` (PR с кодом) и `state`: Docker `large` (4 vCPU, 8 ГБ, 20 кредитов/мин), тесты с явным `-n 4` (в контейнере CircleCI
     `-n auto` видит ядра хоста, а не 4 vCPU; в `AGENTS.md` описан отказ полного прогона из-за памяти);
   - `windows-hooks`: исполнитель `win/server-2022`, класс `windows.medium` (**40 кредитов/мин**), только если PR меняет
     `plugin/hooks/**`, `plugin/templates/**`, `.github/**` или `.circleci/**`.
6. **Таймауты.** У CircleCI нет `timeout-minutes` на задание (общий предел плана Free: 1 час на задание). Вместо него:
   `no_output_timeout` на долгих шагах (срабатывает только при молчании) и общий предел на сами тесты: `timeout 1500` (25 минут) в
   `check` и `state`, ожидание процесса не дольше 15 минут в `windows-hooks`. **Автоотмена** устаревших прогонов настраивается в
   проекте, не конфигом: Project Settings → Advanced → Auto-cancel Redundant Workflows (включена владельцем).
7. **Табло (`state`) на CircleCI.** После слияния в main запускается workflow `state` (единственный запуск на main): полный прогон тестов на
   коммите main (отчёт относится к этому же коммиту) и `parch_status.py`, результат публикуется на ветку `status`. Отличия от прежнего
   `state.yml`: тесты идут в самом задании (раньше брался отчёт из PR), расход CI по неделе и статусы проверок открытых PR на табло пока
   не собираются (в списке PR нет столбца проверок). Один запуск ~245 кредитов, на каждое слияние.
   **Токен записи в ветку `status`** (`STATUS_PUSH_TOKEN`, личный токен GitHub fine-grained: только этот репозиторий, только право Contents:
   write) хранится не в переменных проекта, а в **context CircleCI `status-publisher`**, который подключён только к заданию `state` (на ветке
   `main`). Переменные проекта видели бы все задания всех веток репозитория, а конфиг берётся из самой ветки PR: ветка (в том числе ИИ-сессии)
   могла бы написать задание, печатающее токен. **Владелец ограничивает context** (Organization Settings → Contexts → `status-publisher` →
   Security): доступ только проекту этого репозитория и только для ветки `main` (правило по выражению `pipeline.git.branch == "main"`; если
   вашего плана такого правила нет, ограничить группой безопасности владельца). Сборкам из форков секреты не передаются: «Pass secrets to builds
   from forked pull requests» должно быть **выключено**. Токен не печатается, в журнале маскируется; публикация проверяет, что это ветка `main`
   без номера PR и что на `main` нет более нового коммита (гонка двух слияний подряд: новый коммит опубликует своё табло сам). В ruleset ветки
   `main` у владельца токена не должно быть права обхода. Пока context или токена нет, задание собирает табло и пишет, что не опубликовало его
   (если context не создан, workflow `state` на main сообщает об ошибке, на PR это не влияет).
8. **Ruleset ветки main** (меняет владелец вручную, порядок и шаги в описании PR): вместо `check`, `full-run`, `windows-hooks` обязательными
   становятся `ci/circleci: check` и `ci/circleci: windows-hooks`. Порядок: проверки CircleCI появились и зелёные на PR, затем меняется
   ruleset, затем слияние.
9. `parch_ci.py standard` читает и `.circleci/*.yml` (для проектов на CircleCI и самого продукта): расписание, исполнители (Windows и
   macOS только по принятому ADR), классы ресурсов выше `medium` (только названные здесь), предел времени у шагов с тестами. Правила по
   `.github/workflows` для шаблонов и проектов пользователей сохранены. Автоотмена из конфига не видна: `standard` пишет об этом
   пометку.

## Оценка кредитов

Цены по документации CircleCI: Docker small 5, medium 10, large 20 кредитов/мин; Windows medium 40 кредитов/мин
(circleci.com/pricing; Windows доступен на плане Free). Время по прошлым прогонам (полная проверка с кодом 9–12 минут, Windows 2–4 минуты).

| Что | Время | Кредиты за один запуск |
|---|---|---|
| PR с кодом (`scope` 1 мин small + `check` ~12 мин large) | ~13 мин | ~245 |
| PR только с текстом (`scope` + `check` ~2 мин small) | ~3 мин | ~15 |
| PR с hooks: Windows medium (включая установку Python и pip) | ~3–4 мин | ~160 сверху |
| Слияние в main: `state` (полный прогон на large) | ~12 мин | ~245 |

Раньше «быстрая часть» и «полный прогон» были двумя запусками на PR; теперь один полный на каждую отправку, расход кредитов на отправку с кодом
остался прежним (быстрая часть и так была почти равна полному прогону).

**Бесплатный и открытый пул.** Бесплатный план: 30 000 кредитов в месяц, не переносятся. Но репозиторий публичный, и по официальной странице
CircleCI для открытых проектов (circleci.com/open-source) организации на плане Free получают **до 400 000 кредитов в месяц на Linux, Arm и
Docker** и 30 000 на macOS и Windows; справка CircleCI формулирует тот же пул как 100 000 кредитов в неделю на Linux, при условии, что
репозитории публичны и проект отмечен как открытый. Эти кредиты не видны в интерфейсе. Сверка с документацией (2026-10-06): суммы совпадают по
порядку (около 400 000 в месяц на Linux), по Windows пул указан только на странице (30 000).

Месяц, ориентировочно (оценка, не измерение):

| Сценарий | Linux | Windows | Куда считается |
|---|---|---|---|
| Спокойный: 30 отправок с кодом, 40 с текстом, 8 с hooks, 20 слияний | ~13 000 | ~1 300 | вписывается и в обычные 30 000, и в открытый пул |
| Интенсивный (как последние дни): ~100 отправок с кодом, 60 с текстом, 20 с hooks, 60 слияний | ~41 000 | ~3 200 | выше обычных 30 000, но около 10 % открытого пула 400 000 |

Если открытый пул применён, расход Linux не упирается в лимит ни в одном сценарии, Windows (3 200 из 30 000) тоже вписывается. Если проект не признан
открытым, действуют обычные 30 000: интенсивный месяц превысит их; выше предела платный план Performance (от 15 долларов в месяц, дальше кредиты
покупаются). Какой пул применён, видно в Plan Usage после первой недели.

## Проверка конфигов и ловушка режима совместимости

Официальный CLI CircleCI (`circleci` 1.0.52041, скачан с `CircleCI-Public/circleci-cli`, контрольная сумма совпала) выполняет `circleci config validate`
для обоих файлов и `circleci config process` для трёх вариантов состава PR (только текст, код, код и hooks): получаются ровно предусмотренные
workflow. Скрипт состава PR выполняется тестами `tests/test_circleci_config.py` во временных git-репозиториях.

**Ловушка: режим совместимости с GitHub Actions.** Первый пайплайн проекта в CircleCI (`build-and-test`) был создан в режиме «GitHub Actions workflow
как конфиг»: он читал `.circleci/config.yml` как файл GitHub Actions, не понимал native-конфиг и показывал **фальшивый зелёный за 4 секунды**
без запуска проверок. Признаки: проверка проходит за секунды, в ней нет заданий `scope` и `check`, имя проверки не `ci/circleci: ...`. Пайплайн удалён;
рабочий пайплайн `ci` в родном режиме, триггер «PR opened or pushed to, default branch and tag pushes». Защита: обязательными делаются только проверки
с именами `ci/circleci: check` и `ci/circleci: windows-hooks`, которые создаёт только родной конфиг; проверка из режима совместимости их не создаст.

## Последствия для владельца

- Что изменится: у каждого PR проверки только от CircleCI (`ci/circleci: scope`, `check`, `windows-hooks`); GitHub Actions у репозитория больше нет.
  Пока ruleset не обновлён, слияние ждёт старых проверок GitHub (`check`, `full-run`, `windows-hooks`), которых больше не будет.
- Нужно сделать вручную: поменять обязательные проверки ruleset (пошагово в описании PR), задать `STATUS_PUSH_TOKEN` в CircleCI (без него табло не публикуется),
  держать выключенным «Pass secrets to builds from forked pull requests».
- Если решение окажется ошибкой: вернуть три workflow из истории git и прежний ruleset.
- Как откатить: `git revert` PR перехода, затем ruleset обратно на `check`, `full-run`, `windows-hooks`.

## Рассмотренные альтернативы

- Режим «GitHub Actions workflow как конфиг» в CircleCI: не поддерживает `windows-latest`, и из-за него был фальшивый зелёный.
- Триггер «PR marked ready for review» для полного прогона: сложнее и ненадёжнее связки с обязательной проверкой; полный прогон на каждую отправку
  проще и не дороже при нынешнем размере тестов (открытый пул кредитов).
- Состав PR через `path-filtering` (orb CircleCI): умеет только логические значения по шаблонам путей; проще переиспользовать проверенный `scope.py`.
- Табло с отчётом из CircleCI API (артефакт PR): нужен токен чтения и сопоставление PR с коммитом main; проще прогнать тесты на самом main.
