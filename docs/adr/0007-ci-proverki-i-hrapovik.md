# ADR-0007. CI-проверки по языкам: общий скрипт, «храповик» по отпечаткам, честные «красные»

- Статус: proposed
- Тип решения: необратимое (формат baseline и набор проверок закрепятся во всех подключённых проектах)
- Дата: 2026-10-02

## Контекст

Фаза D строит CI по языкам (Python → TypeScript → C# → PowerShell) с проверками из таблицы плана и тремя общими:
«число тестов не уменьшилось», «каждый модуль есть в MODULES.md», «храповик» (метрики дублирования и мёртвого
кода не растут относительно сохранённого baseline). Плюс проверка зависимостей, которая закрывает дыру из ADR-0004
(пакет можно добавить правкой манифеста в обход команды установки).

## Решение

1. **Один скрипт проверок для всех языков.** `plugin/templates/ci/parch/parch_ci.py` (только стандартная библиотека)
   копируется навыком `/parch:init-project` в проект как `.github/parch/parch_ci.py`: на раннере GitHub плагина нет,
   а скрипт должен быть рядом с кодом. Папка `.github/` уже защищена: агент не может править проверки, не спросив
   владельца. Языки подключаются адаптерами; сейчас есть Python, остальные добавляются в своих PR.
2. **«Храповик» по отпечаткам, а не по числам.** Если сравнивать только количество нарушений, одно старое можно
   починить, одно новое добавить, и счётчик не изменится. Поэтому в `state/baseline.json` лежат отпечатки: для мёртвого
   кода `инструмент|файл|вид|имя` (без номера строки, чтобы сдвиг строк не считался новым нарушением), для тестов
   идентификаторы тестов. Старые находки CI пропускает, любая новая останавливает. Дубли ведёт сам jscpd:
   у него есть собственный baseline (`state/jscpd-baseline.json`) и флаг «упасть на новых клонах».
3. **Тесты: сверка по списку, а не по числу.** Каждый тест из baseline должен существовать. Удаление одного теста
   с добавлением другого число сохраняет, но проверку не проходит. Переименование тоже требует решения владельца.
4. **baseline меняет только владелец.** `baseline --update` отказывается записывать новые нарушения (флаг `--accept-new`)
   и пропавшие тесты (флаг `--accept-removed`), а файлы `state/baseline.json`, `state/jscpd-baseline.json`,
   `state/features.json`, `state/vulture-whitelist.py` защищены от правки агентом теми же правилами, что CI-файлы.
   Улучшение (старое нарушение исправлено) CI замечает и просит закрепить его, чтобы оно не вернулось.
5. **Правило без охвата не бывает «зелёным».** Принцип проекта: проверка, которая ничего не проверила, считается
   ошибкой. Применено так: нет ни одного теста, нет правил архитектуры для существующих модулей, в правилах нет
   контрактов, модуль не назван в `root_package`, jscpd не нашёл файлов для анализа. Именно так найден реальный
   изъян import-linter: опечатка в `forbidden_modules` не вызывает ошибку, правило «проходит», ничего не проверяя.
   Поэтому каждое имя модуля из контрактов дополнительно проверяется на существование.
6. **Проверка зависимостей.** Все пакеты из `requirements*.txt` (включая вложенные `-r`), `pyproject.toml`
   (`dependencies`, `optional-dependencies`, `dependency-groups`, `poetry`) должны быть в разделе «Разрешённые пакеты»
   CONSTITUTION.md. Ссылки на git и файлы архивов считаются нарушением. Это закрывает дыру из ADR-0004 для Python.
7. **Версии инструментов зафиксированы** (ruff 0.16.10, pyright 1.1.414, pytest 9.1.1, pytest-cov 7.1.0, coverage 7.16.2,
   import-linter 2.15, vulture 2.16, deptry 0.25.1, jscpd 5.4.0, Node 22, Python 3.12): CI не должен ломаться
   от выхода новой версии. Тест следит, чтобы версии в шаблоне и в CI самого продукта совпадали.
8. **jscpd 5.x вместо 4.x.** Версия 5.4.0 написана заново (движок на Rust, один бинарный файл) и умеет `--baseline`
   и `--fail-on-empty`, то есть ровно то, что нужно для «храповика» и принципа из п. 5. Новая крупная версия
   менее обкатана, чем 4.x: риск принят, версия зафиксирована.

## Пропуски тестов, подавления и настройки проверок (правила заложены для всех четырёх языков)

Три способа «пройти» проверки, ничего не исправив, закрыты тем же «храповиком». Правила написаны сразу для Python,
TypeScript, C# и PowerShell; полный CI для трёх последних появится в следующих PR, но сами правила и тесты на них уже есть.

9. **Пропущенный тест считается удалённым** (проверка `skips`). Считаются: `pytest.mark.skip/skipif/xfail`, `pytest.skip()`,
   `importorskip`, `unittest.skip*`, `skipTest`; TypeScript `it/test/describe.skip/todo/only/fails`, `xit/xdescribe`;
   C# `Skip =`, `[Ignore]`, `[Explicit]`, `Assert.Ignore`, `Skip.If`; PowerShell `-Skip`, `Set-ItResult -Skipped`, `-Pending`.
   Считается по файлам тестов: новый или лишний пропуск нарушает «храповик», записать его в baseline можно только флагом
   владельца `--accept-skips`. В Python разбор идёт через `tokenize`: слова «skip» в строках и комментариях не считаются.
10. **Подавляющие комментарии не растут** (проверка `suppressions`). Python: `# type: ignore`, `# pyright: ignore`,
    `# pyright: basic/off`, `# noqa`, `# ruff: noqa`, `# pragma: no cover`, `# mypy: ignore-errors`; TypeScript: `@ts-ignore`,
    `@ts-expect-error`, `@ts-nocheck`, `eslint-disable`, `biome-ignore`, `prettier-ignore`, `istanbul/c8/v8 ignore`;
    C#: `#pragma warning disable`, `SuppressMessage`, `ReSharper disable`, `#nullable disable`, `ExcludeFromCodeCoverage`;
    PowerShell: `SuppressMessage(Attribute)`. Считается число по файлам и видам: переносить подавление внутри файла можно,
    добавлять нельзя. Запись в baseline только флагом `--accept-suppressions`.
11. **Настройки проверок защищены отпечатком** (проверка `settings`) **и вопросом владельцу в hook**. Файлы целиком:
    `ruff.toml`, `pyrightconfig.json`, `.coveragerc`, `pytest.ini`, `.importlinter`, `tox.ini`, `tsconfig*.json`, ESLint, Biome,
    Prettier, Vitest/Jest, dependency-cruiser, knip, `.jscpd.json`, `.editorconfig`, `Directory.Build.props`, `*.ruleset`,
    `*.runsettings`, `global.json`, `PSScriptAnalyzerSettings.psd1`, `PesterConfiguration*`. Разделы внутри файлов:
    `pyproject.toml` (`tool.ruff`, `pyright`, `pytest`, `coverage`, `importlinter`, `vulture`, `deptry`, `parch`), `setup.cfg`,
    `package.json` (`jest`, `eslintConfig`, `prettier` и скрипты `test`, `lint`, `typecheck`, `check`, `coverage`, `format`: подмена
    `"test": "echo ok"` отключила бы все тесты), `.csproj` (`Nullable`, `TreatWarningsAsErrors`, `NoWarn`, `WarningsAsErrors`, `AnalysisMode`
    и др.). CI хранит отпечатки в `state/baseline.json` и падает на любом изменении, добавлении или удалении (флаг владельца
    `--accept-config`). Hook `guard_paths` спрашивает владельца при правке таких файлов: для файлов целиком всегда, для
    `pyproject.toml`, `setup.cfg`, `package.json`, `.csproj` только если правка действительно меняет защищённые разделы (hook
    применяет правку к тексту и сравнивает отпечатки; правка через оболочку спрашивает всегда). Единый источник правил:
    `parch_ci.py`; hook подключает его из шаблонов плагина, чтобы правила в CI и в hook не разошлись.

## Известные ограничения

- **Тест с телом `assert True` не ловится.** Все проверки выше видят, что тест есть, не пропущен и проходит, но не видят,
  что он ничего не проверяет. План: еженедельное мутационное тестирование (например, `mutmut` для Python, Stryker для
  TypeScript и C#) в фазе F: оно меняет код программы и проверяет, что хотя бы один тест это замечает; тесты, которые
  не замечают ничего, попадают в отчёт.
- Подавления и пропуски в TypeScript, C# и PowerShell ищутся по тексту, поэтому слово из этого списка в строке или
  комментарии тоже считается (для Python это исключено разбором через `tokenize`). Ложное срабатывание лечится решением владельца.
- Динамические пропуски (тест сам решает во время выполнения не запускаться без маркера и вызова `skip`) этим не видны.

## Что проверяют тесты

Тестовый проект `tests/projects/python_shop` и его варианты с намеренными нарушениями: дубль, мёртвая функция,
запрещённая зависимость между модулями, удалённый тест, пакет не из списка (в `requirements.txt`, `requirements-dev.txt`,
`pyproject.toml`, вложенном `-r`, git-ссылке), модуль вне `MODULES.md`, опечатка в правиле архитектуры. «Храповик»:
старые нарушения проходят, новые блокируются (мёртвый код, дубли), исправление замечается, запись в baseline нового
нарушения отказывает без флага, падение покрытия блокируется.

## Последствия для владельца

- Что изменится: в проекте на Python CI ловит дубли, мёртвый код, нарушения границ между модулями, удалённые тесты,
  лишние пакеты и модули без записи в карте. Старый код с нарушениями можно подключить сразу: известное записывается
  в baseline, блокируется только новое.
- Если решение окажется ошибкой: слишком строгие проверки будут краснеть на безобидном (например, vulture считает
  «мёртвой» функцию, которую вызывает внешняя программа); для этого есть файл исключений `state/vulture-whitelist.py`
  и осознанное обновление baseline. Слишком мягкие пропустят нарушение; оба случая видны в логе CI.
- Как откатить: удалить шаги `parch_ci.py` из `.github/workflows/ci.yml` проекта; файлы baseline можно удалить.

## Ограничения

- Только Python; TypeScript, C# и PowerShell идут следующими PR, каждый после слияния предыдущего.
- Проверки не запускались на реальном GitHub-раннере для сгенерированного проекта; проверена та же последовательность
  команд, что в `python.yml`, на сгенерированном и на тестовом проектах.
- Дубли и мёртвый код ловятся эвристиками (jscpd, vulture): они не доказывают отсутствие дублей и мёртвого кода,
  а ограничивают их рост.

## Рассмотренные альтернативы

- Считать нарушения числом: проще, но допускает «обмен» старого нарушения на новое.
- Положить скрипт проверок в плагин и вызывать оттуда: на раннере плагина нет.
- jscpd 4.x: обкатаннее, но без собственного baseline и без защиты от пустого анализа; пришлось бы писать то же самое самим.
