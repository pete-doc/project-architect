# ADR-0013. Разделение CI: быстрая часть на каждую отправку, полный прогон перед слиянием

- Статус: proposed
- Тип решения: обратимое по коду, но схема работает только вместе с настройкой ruleset (см. «Обязательная часть схемы»)
- Дата: 2026-10-03

## Контекст

3 октября CI дал 28 прогонов и израсходовал около 950 минут квоты (2 октября: 31 прогон, около 670). Каждый прогон кода
идёт 9–17 минут и каждый раз запускает все тесты всех четырёх языков, хотя PR обычно меняет один язык. Из 28 прогонов
8 упали или были отменены: это 241 минута (четверть расхода) ушла на «ожидаемо красные» прогоны и на отладку в CI.
Это нарушает критерий G5 «CI не тратит квоту впустую». Минуты посчитаны по длительности заданий (Windows ×2), как
их считает GitHub; точные цифры на странице расходов GitHub.

## Решение

1. **Быстрая часть на каждую отправку** (`ci.yml`, задание `check`, лимит `timeout-minutes: 25`: если PR меняет общий код или сам CI, идут тесты всех языков и прогон не короче полного, первый прогон с лимитом 15 минут упал по времени). Проверки (ruff, pyright, `standard`),
   быстрые тесты и медленные тесты только тех языков, чьи файлы изменил PR. Какие языки менялись, определяет
   `.github/scope.py` по списку файлов PR; общий код проверок, настройки тестов и сам CI считаются изменением всех языков.
   Отчёт такого прогона помечен `parch-partial`.
2. **Что считается кодом.** Без кода и тестов считаются только решения (`docs/adr/`), вопросы (`docs/QUESTIONS.md`),
   отчёты об инцидентах и приёмке и сгенерированное табло (`state/incidents/`, `state/acceptance/`, `state/STATUS.md`).
   Всё остальное в `docs/` и `state/` (`state/baseline.json`, `state/features.json`, `docs/GOAL.md`, `docs/MODULES.md`
   и любые будущие файлы правил проверок) считается кодом: оно меняет правила, поэтому требует полного прогона. Новые
   файлы в этих папках по умолчанию тоже код.
3. **Храповик отличает урезанный прогон от полного.** Режим `parch_ci.py tests|skips --partial` принимает только
   помеченный отчёт: упавшие тесты, новые пропуски и удалённые тесты останавливают и его, а «не запущенные» тесты не
   требуются, но вывод прямо говорит: «ЧАСТИЧНЫЙ прогон… права на слияние он не даёт». Полный режим, наоборот, не
   принимает помеченный отчёт, и baseline по урезанному отчёту не обновляется.
4. **Полный прогон перед слиянием** (`full.yml`, единственное задание `full-run`, лимит 25 минут) делает всё, что делал
   прежний `check`: все тесты, храповик по отчёту, `standard`. PR без кода проходит его за секунды (без тестов).
5. **Как запрашивается полный прогон:** `gh pr ready`, то есть перевод PR из черновика в «готов к проверке»
   (событие `ready_for_review`). PR открываются черновиками; когда правки закончены и быстрая часть зелёная, PR
   переводят в «готов». После новой отправки полный прогон для нового коммита запрашивают заново:
   `gh pr ready --undo`, затем `gh pr ready`. Полный прогон не идёт на каждую отправку сам: так он не тратит минуты,
   пока правки не закончены.
6. **Проверка `full-run` это задание GitHub Actions, а не отметка.** Единственное событие, которое её создаёт,
   `ready_for_review`; у задания нет условия `if`. Это принципиально: задание, пропущенное по условию, GitHub считает
   успешным, и «не запущенный» полный прогон открыл бы слияние. Без события проверки `full-run` на коммите просто нет,
   и ruleset ждёт её («Expected»). Ставить проверки и статусы вручную через `gh api` запрещено (AGENTS.md); тест
   следит, чтобы ни один workflow не писал статусы.
7. **Что не меняется:** триггеры только `pull_request`, Ubuntu, отмена старых прогонов, `windows-hooks` по условию
   (его требует ruleset), правила `standard`.
8. Шаблоны CI для проектов пользователей остаются прежними (полный прогон на каждую отправку). Тот же приём для них
   отдельным решением в D2-3, когда правило окупится на реальном проекте.

## Обязательная часть схемы: настройка ruleset (решение владельца)

Без этого схема не защищает. В `protect-main` обязательными проверками закреплены **`check`, `full-run` и
`windows-hooks`**, и для каждой источником указан **GitHub Actions** (параметр `integration_id` проверки). Тогда
GitHub принимает только проверку, созданную заданием Actions, и отметку нельзя поставить вручную через API (ни
комментарием, ни статусом от имени пользователя). Если источник не закреплён, любой с правом записи может создать
статус с именем `full-run` и открыть слияние без полного прогона.

## Экономия (оценка)

Быстрая часть: около 3–4 минут (без установки node, dotnet, PowerShell, если язык не менялся), с языком C# или
PowerShell около 7–8 минут. Полный прогон: около 13 минут (прежний `check`). Это оценка по прежним замерам, не
замер нового CI: первые PR после слияния покажут настоящие цифры (табло: расход CI за неделю и на один PR).

| PR | Было (отправок × ~15 мин) | Станет | Экономия |
|---|---|---|---|
| 6 отправок, без изменений языков | 90 | 5 × 4 + 17 = 37 | около 59% |
| 3 отправки | 45 | 2 × 4 + 17 = 25 | около 44% |
| 1 отправка | 15 | 17 | минус 13% (полный прогон обязателен) |
| Только решения и отчёты | 3 | 3 (+ секунды на `full-run`) | 0 |

Отдельно правило AGENTS.md «полный прогон и baseline локально перед отправкой, красных прогонов «на проверку» нет»
должно убрать упавшие прогоны (сегодня 25% расхода). Это сильнее, чем разделение: без дисциплины разделение съест
часть выгоды лишним полным прогоном. Изменение файлов правил (`state/baseline.json` и т.п.) теперь тоже требует полного
прогона: это дороже, чем раньше, зато это ровно те файлы, которыми можно ослабить проверки.

## Последствия и риски

- Что изменится для вас: PR с кодом перед слиянием показывает три проверки: `check` (быстрая часть), `full-run`
  (полный прогон) и при изменении hooks `windows-hooks`. Слияние без зелёного `full-run` запрещено.
- Если ошибка в решении: быстрая часть может пропустить поломку другого языка (ловит только полный прогон перед
  слиянием; в `main` поломка не попадёт, но обнаружится позже, чем сейчас). Поэтому полный прогон обязателен.
- Если `full-run` не появляется (сбой workflow, PR не переводили в «готов»): слияние блокируется; повторить
  `gh pr ready --undo` и `gh pr ready`.
- Как откатить: вернуть `ci.yml` из истории и удалить `full.yml`; `full-run` из ruleset убрать.

## Рассмотренные альтернативы

- Запуск полного прогона по метке `full` (первый вариант этого ADR): метка рождает событие на любую другую метку
  (например, «нужно решение владельца»), а задание без условия на такое событие не запускается без дыры: либо
  пропущенное задание считается успешным, либо любая метка даёт красный `full-run`. `ready_for_review` таких событий
  не имеет.
- Статус `full-run` через `gh api statuses`: не привязан к Actions, его можно поставить вручную; ruleset не может
  потребовать источник Actions для статусов.
- Тяжёлые тесты только перед слиянием, без разбора по языкам: проще, но каждая отправка перестаёт проверять
  изменённый язык, поломка находится только на полном прогоне.
- Запуск полного прогона вручную (`workflow_dispatch`): запрещён `standard` (запуск только по `pull_request`).
- Полный прогон на каждую отправку при метке: каждая отправка после метки платит 13 минут, а правки обычно ещё идут.
