# ADR-0022. Шаблоны CI для проектов пользователей: CircleCI вместо GitHub Actions

- Статус: proposed
- Тип решения: обратимое по коду (откат: вернуть шаблоны из истории git), но меняет то, что владелец делает руками в каждом новом проекте, и расходы
- Дата: 2026-10-06
- Дополняет ADR-0020 и снимает его оговорку «шаблоны CI проектов пользователей остаются GitHub Actions». Для шаблонов заменяет ADR-0011 в части «Ubuntu на Actions» (остаётся правило «только Linux, остальное через ADR с оценкой»), ADR-0012 в части «табло публикует workflow GitHub Actions» (ветка `status` остаётся) и ADR-0013 в части быстрой части и полного прогона (одна проверка на PR, как в ADR-0020).

## Контекст

Решение владельца, 2026-10-06: шаблоны CI для проектов пользователей переходят на CircleCI полностью, GitHub Actions как вариант не остаётся;
табло переезжает вместе с CI. Причина проста: при первом живом прогоне F20 шаблон `state.yml` упал на первом слиянии (`HTTP 404: workflow full.yml
not found`: он ищет отчёт тестов в прогоне workflow, которого у проектов пользователей нет). Тесты продукта этого не ловили, потому что проверяют
файлы на диске, а не запуск. Для самого продукта CI на CircleCI уже работает (ADR-0020), в том числе табло, где тесты идут в самом задании.

## Решение

1. `/parch:init-project` создаёт `.circleci/config.yml` (собирается из шаблонов `plugin/templates/ci/circleci/`) и **не создаёт** `.github/workflows/`.
   Шаблоны GitHub Actions удаляются при реализации блока F24. Скрипты проверок остаются в `.github/parch/`.
2. Имена проверок: каждый язык даёт задание `check-<язык>`, а **один итоговый `check`** в workflow `ci` имеет `requires` на все языковые задания.
   В защите `main` обязательна **одна** проверка `ci/circleci: check` (решение владельца 2026-10-06); `check-<язык>` обязательными не делаются.
3. Табло: задание `state` на `main` само гоняет тесты и публикует `state/STATUS.md` на ветку `status`; без API CircleCI и без его токена.
   Порядок: тесты проекта, сборка табло, и только потом подключение ключа записи и публикация. Тесты упали или отчёта нет при существующих
   тестах: табло публикуется с понятной пометкой, задание красное. Отчёта нет в проекте без единого теста: допустимо, табло так и пишет.
4. Запись в ветку `status`: **SSH-ключ проекта** (deploy key GitHub с правом записи, закрытая часть в Project Settings → SSH Keys CircleCI);
   решение владельца 2026-10-06. Ключ подключается только в задании `state` и только после тестов проекта; нет ключа: сообщение с инструкцией,
   цвет задания определяют тесты. Ключ подключается последним (пункт В5), после защиты `main` (В4): без защиты он мог бы писать и в `main`.
   Пока ключа нет, задание `state` печатает «ключ записи не подключён, табло не опубликовано, шаг В5 в инструкции» и не падает с неясной ошибкой.
5. Только Linux, Docker, класс не выше `medium`. Пределы времени у CircleCI: единственный жёсткий предел 1 час на задание на плане Free (до 600 кредитов за
   зависшее задание `medium`); пределы шагов в шаблонах дают расчётный, а не гарантированный потолок. Windows и macOS в шаблонах нет; добавляются отдельным ADR с оценкой кредитов.
6. Раздел «Основания» для проверки `standard` берётся из **сообщений коммитов ветки** (`git log origin/main..HEAD`), хотя бы в одном коммите; описания PR
   в CircleCI нет (`CIRCLE_PULL_REQUEST` только для PR из форков), а читать описание PR приватного репозитория можно только с токеном: нового секрета в проекте
   не вводим (решение владельца 2026-10-06). Исполнитель пишет раздел один раз, в коммите; в описание PR он попадает командой `parch_ci.py basis`.
   Красным считаются: нет раздела, раздел пуст или из прочерков, нет новых коммитов относительно `main`, нет истории `main`. Заголовок принимается
   и как «## Основания», и как «Основания:» в начале строки (git вырезает строки с `#` в сообщении из редактора). Файл `.circleci/config.yml`
   проверяется официальным CLI (`circleci config validate`, версия и контрольная сумма зафиксированы) в тестах продукта; это шаг на секунды в существующем
   задании, нового исполнителя и расписания нет, поэтому отдельный ADR по правилу 10 не нужен.
7. Подробности, шаги владельца, оценка кредитов, тесты и риски: `docs/specs/F24-circleci-templates.md`.

## Последствия для владельца

- **Что изменится.** В каждом новом проекте вместо «включить бюджет Actions» нужно один раз сделать пять пунктов в строгом порядке (названия те же, что в спецификации F24 и F20):
  **В1** доступ GitHub App CircleCI к репозиторию, **В2** создать проект в CircleCI (токены не нужны), **В3** включить автоотмену устаревших прогонов,
  **В4** включить защиту `main` после первого зелёного `check`, **В5** подключить ключ записи табло, только после В4 (без защиты ключ
  не подключается). init выводит их в конце по-русски. Проверки у PR называются `ci/circleci: ...`. Расход считается в кредитах CircleCI:
  бесплатный план 30 000 в месяц, типичный маленький проект около 1 900 в месяц (около 6 %).
- **Чем рискуем.** Первый запуск шаблонов на настоящем CircleCI может найти новые ошибки; ключ записи доступен заданиям любой ветки проекта (риск ограничен
  веткой `status`, `main` защищён); ранее подключённые проекты (fm26-data и другие) остаются на GitHub Actions, пока их не мигрируют отдельной просьбой.
- **Как откатить.** `git revert` PR реализации возвращает шаблоны Actions; в уже подключённых новых проектах удалить `.circleci/` и проект в CircleCI.

## Рассмотренные альтернативы

- **Оставить Actions и починить `state.yml`.** Дешевле сейчас, но владелец решил уйти с Actions полностью (нестабильность раннеров, ADR-0020), и два CI в шаблонах
  удваивают проверки и тесты.
- **Оба варианта на выбор при init.** Удваивает шаблоны, тесты и инструкции; владелец от этого отказался.
- **Отчёт тестов через API CircleCI (артефакты прогона PR).** Нужен личный токен CircleCI и сопоставление PR с коммитом `main`; тесты в задании `state` проще и надёжнее.
- **Токен в context вместо ключа.** Лучше изолирован (ограничивается веткой `main`), но личный, с сроком действия и на каждый проект отдельный context; владелец выбрал SSH-ключ (2026-10-06).
