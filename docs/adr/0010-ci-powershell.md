# ADR-0010. PowerShell только тонкий «клей»: облегчённый CI вместо полного набора проверок

- Статус: proposed
- Тип решения: необратимое (форма проверок и пороги закрепятся в подключённых проектах)
- Дата: 2026-10-03

## Контекст

Четвёртый, последний PR фазы D. В плане для PowerShell были те же проверки, что для остальных языков: линтер, архитектура,
мёртвый код, дубли, тесты Pester с покрытием. Владелец решил иначе: PowerShell в проектах используется только как тонкий «клей»
для запуска программ, а вся логика живёт в Python или C#. Раз логики в скриптах нет, тяжёлый набор проверок для них не нужен и
только создавал бы ложное ощущение, что в PowerShell можно писать сложный код.

## Решение

1. **Правило продукта: PowerShell это только запуск программ.** Скрипт PowerShell вызывает программу (Python, C# или готовую
   утилиту), передаёт ей аргументы и возвращает код выхода. Разбор данных, условия, циклы, собственные функции, классы
   принадлежат Python или C#. Если скрипту понадобилась логика, её переносят в Python или C#, а скрипт остаётся запуском.
2. **Что проверяется в CI (три проверки и защита настроек):**
   - `psscriptanalyzer`: PSScriptAnalyzer (версия зафиксирована точно: 1.25.0), все скрипты `.ps1`, `.psm1`, `.psd1` проекта,
     настройки из `PSScriptAnalyzerSettings.psd1`. Падают находки уровня Error и Warning и ошибки разбора. Если инструмент
     не установлен или версия другая, проверка падает, а не пропускается. Если скриптов нет, проверка сообщает «скриптов пока нет».
   - `thin` («тонкость»): в каждом скрипте считаются строки кода (без пустых строк и комментариев) и собственные функции
     (`function`, `filter`, `workflow`, а также `class` и `enum`: это тоже собственная логика). Пороги лежат в `CONSTITUTION.md`,
     раздел «Пороги тонкости PowerShell»: `max_lines` и `max_functions` (по умолчанию 40 и 0). Превышение это провал с подсказкой
     перенести логику в Python или C#. Если раздела или порога нет, проверка тоже падает: удалением порога её не отключить.
   - `suppressions`: подавления PSScriptAnalyzer (`[SuppressMessage(...)]`, комментарии `# PSScriptAnalyzer`) считаются
     «храповиком» (ADR-0007): их число не растёт без флага владельца `--accept-suppressions`. Поиск идёт по коду и комментариям
     без содержимого строк (небольшой разбор PowerShell: комментарии `#` и `<# #>`, строки `'...'` и `"..."`, here-строки).
   - `settings`: `PSScriptAnalyzerSettings.psd1` под защитой (ослабить правила, правя настройки, нельзя без `--accept-config`).
3. **Чего для PowerShell нет, и это сделано намеренно:** тестов Pester, покрытия, проверки архитектуры, поиска дублей, мёртвого
   кода, «каждый модуль в MODULES.md», проверки зависимостей и счётчика тестов. Команды `tests`, `skips`, `modules`, `deps`,
   `dead-code`, `duplicates`, `architecture`, `coverage` для PowerShell отвечают «не применяется (ADR-0010)» и завершаются
   ошибкой, чтобы неверно составленный CI не прошёл молча.
4. **Парсер отчётов Pester остаётся, но не расширяется.** Он покрыт тестами на реальных отчётах и нужен, если проект всё же
   подключит свои тесты Pester; продукт их не требует и новых возможностей для них не добавляет.
5. **CI-шаблон `powershell.yml` идёт на Windows-runner** (как требовалось): ставится PSScriptAnalyzer точной версии из PowerShell
   Gallery, затем четыре проверки `parch_ci.py`.
6. **`/parch:init-project`** создаёт для PowerShell: `PSScriptAnalyzerSettings.psd1`, начальный baseline (подавления и настройки),
   раздел с порогами в `CONSTITUTION.md` и `.github/workflows/ci.yml` (или `ci-powershell.yml`, если первым языком выбран другой).
   Разрешённый пакет один: PSScriptAnalyzer (PSGallery).

## Известные ограничения

- «Тонкость» измеряется длиной и числом функций, а не сложностью: короткий скрипт может содержать условия и циклы. Это
  осознанное упрощение (так проверку можно объяснить и воспроизвести). Если понадобится, добавится порог на число условий и циклов.
- Литералы вида `& { ... }` (скриптблоки) и динамический вызов кода (`Invoke-Expression`) формально не «функции». Для первого
  работает порог строк; `Invoke-Expression` PSScriptAnalyzer сам предупреждает (правило PSAvoidUsingInvokeExpression).
- Для PSScriptAnalyzer нужны PowerShell (Windows PowerShell 5.1 или PowerShell 7) и сеть при первой установке модуля.
- Установка PSScriptAnalyzer на компьютер разработчика это установка модуля PowerShell Gallery; в проект он не попадает как
  зависимость кода и не входит в сборки.

## Последствия для владельца

- Что изменится: в проекте нельзя спрятать логику в скрипте PowerShell: CI остановит длинный скрипт или скрипт с собственной
  функцией и попросит перенести логику в Python или C#. Тестов, покрытия и дублей для PowerShell не требуется.
- Если решение окажется ошибкой: пороги можно поднять, правя `CONSTITUTION.md` (изменение защищено и требует вашего
  подтверждения); если нужны настоящие тесты и архитектура для PowerShell, это отдельное решение и отдельный ADR.
- Как откатить: удалить шаги `parch_ci.py` из workflow проекта; baseline можно удалить.

## Рассмотренные альтернативы

- Полный набор как для Python и C# (Pester, покрытие, дубли, проверка архитектуры скриптом): много проверок ради кода, которого
  по правилу продукта в PowerShell быть не должно.
- Запрет PowerShell целиком: тонкие скрипты запуска удобны, особенно на Windows.
- Мера сложности через число условий и циклов вместо длины: точнее, но труднее объяснить; отложено (см. ограничения).
