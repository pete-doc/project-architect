# ADR-0011. CI продукта и шаблонов: Ubuntu по умолчанию; матрицы, не-Linux раннеры и запуск не по PR только через ADR с оценкой квоты

- Статус: accepted (решение владельца, 2026-10-03)
- Тип решения: обратимое (настройки workflow), но влияет на расходы и на процесс проверки
- Дата: 2026-10-03
- Изменено 2026-10-03 по решению владельца: таймаут задания `check` продукта поднят с 20 до 25 минут (см. раздел «Изменение: таймаут 25 минут»).

## Контекст

За вечер 2 октября 2026 года CI продукта потратил 2 700 минут квоты и около 17 долларов. Причины:

- матрица из трёх систем: Ubuntu, Windows и macOS; к квоте Windows считается с коэффициентом 2, macOS с коэффициентом 10;
  каждая система гоняла весь набор тестов, примерно по 25 минут;
- у заданий не было `timeout-minutes`: зависший прогон мог расходовать квоту до шести часов;
- не было отмены устаревших прогонов: каждый новый коммит в PR запускал полный прогон, не останавливая прошлый;
- после каждого слияния прогон повторялся на `main` (триггер `push`), хотя в `main` попадает только то, что уже прошло проверки;
- полный прогон шёл даже для PR только с документами (например PR #10: изменён один файл ADR).

Проект разрабатывается только на Windows 11. macOS не целевая платформа, поэтому проверки на ней ничего не дают.

## Решение

1. **Ubuntu по умолчанию.** Все workflow продукта и все шаблоны `plugin/templates/ci/*.yml` идут на `ubuntu-latest`, без матриц.
   Исключение одно: job `windows-hooks` продукта (Windows 11 целевая платформа), только для тестов hooks и запускающего файла
   (`tests/test_guards.py`, `tests/test_launcher.py`, `tests/test_flow.py`), только если PR меняет `plugin/hooks/**`,
   `plugin/templates/**` или `.github/**`, с `timeout-minutes: 15`.
2. **Каждое задание имеет `timeout-minutes`** (25 для полной проверки CI продукта, 20 в шаблонах, 15 для Windows, 3 для определения состава PR).
3. **`concurrency` с отменой:** `group: ci-${{ github.ref }}`, `cancel-in-progress: true` (в шаблонах группа включает имя workflow,
   чтобы несколько workflow одного проекта не отменяли друг друга).
4. **Запуск только на `pull_request`.** Прогона на `push` в `main` нет.
5. **PR только с `docs/**` и `state/**` проходит без тестов:** выполняются проверка стиля, структуры (манифесты плагина, индекс
   ADR) и согласованность baseline с тестами (`parch_ci.py tests` без отчёта).
6. **Кэширование** .NET SDK, пакетов NuGet, модуля PSScriptAnalyzer и пакетов npm в CI продукта.
7. **Правило на будущее:** матрицы, не-Linux раннеры (Windows, macOS, платные большие раннеры) и запуск не по `pull_request`
   (push, расписание, ручной запуск) добавляются в продукт и в шаблоны **только через ADR с оценкой минут квоты за один
   прогон** (с учётом коэффициентов: Windows ×2, macOS ×10). За этим следят тест продукта `tests/test_ci_economy.py` и проверка `standard` (STANDARD.md, разделы 7.2 и 11): таймаут и отмена на каждом workflow, запуск только на `pull_request`, каждый раннер кроме `ubuntu-latest` (например `windows-latest` в job `windows-hooks`) назван в принятом ADR.
8. **Целевая платформа** продукта: Windows 11, она проверяется локально у владельца; CI на Linux проверяет переносимость
   (AGENTS.md, BUILD_PLAN.md, ADR-0002).

## Изменение: таймаут 25 минут для `check` продукта

Два соседних прогона одного и того же кода (PR про скорость тестов) дали шаг `pytest` 489 секунд и 931 секунда
(весь `check`: 8 мин 54 с и 16 мин 23 с). Проверено по журналам обоих прогонов:

- кэши попали в оба прогона (pip, .NET SDK, пакеты NuGet, npm, модуль PSScriptAnalyzer), подготовка заняла
  в обоих около 15–30 секунд, значит ключи кэша не виноваты;
- время каждого файла тестов выросло одинаково, примерно в 1,9 раза (C# 376 → 721 с, TypeScript 303 → 572 с,
  Python 116 → 230 с, PowerShell 90 → 170 с, hooks 34 → 62 с): это скорость самой машины раннера GitHub,
  а не конкретные тесты.

Поэтому запас на плавающую скорость раннера делается таймаутом: `timeout-minutes: 25` на задании `check` в
`.github/workflows/ci.yml` (было 20; при двукратном замедлении полный прогон занимает почти 17 минут, при
ещё худшем запас нужен). Это осознанное отступление от «10–20 минут» стандарта 1.3 (правило 4 раздела 7.2);
остальные задания (`scope` 3, `windows-hooks` 15) и все шаблоны для проектов остаются как были (20).
Проверка `standard` принимает значение выше 20 только если принятый ADR называет его записью
`timeout-minutes: 25` (эта запись и есть разрешение), и никогда больше 60.

## Последствия для владельца

- Что изменится: типичный PR с кодом тратит порядка 20 минут квоты вместо 190; PR только с документами порядка 3 минут;
  PR, меняющий hooks или шаблоны, дополнительно проходит короткую проверку на Windows. Слияние не запускает повторный прогон.
- **Нужно действие владельца:** в настройках репозитория (ruleset `protect-main`, обязательные проверки) старые имена
  `check (ubuntu-latest)`, `check (windows-latest)`, `check (macos-latest)` заменить на `check` и `windows-hooks`.
  До этого слияние блокируется: GitHub ждёт проверок, которых больше нет.
- Если решение окажется ошибкой: не пройдёт переносимость, которую раньше ловил macOS. Для проектов на Windows это
  допустимо; если понадобится, отдельный ADR добавит раннер с оценкой стоимости.
- Как откатить: вернуть матрицу в `ci.yml` отдельным ADR.

## Рассмотренные альтернативы

- Оставить матрицу, но с таймаутами и отменой: экономит меньше (macOS ×10 остаётся).
- Запускать все тесты на Windows вместо Ubuntu: ×2 к квоте и медленнее; на Ubuntu работают те же `dotnet` и `pwsh` (PowerShell 7).
- Фильтр путей на уровне всего workflow (`paths-ignore`): обязательная проверка PR только с документами тогда не появляется,
  и слияние блокируется; поэтому состав PR определяется внутри workflow заданием `scope`.
