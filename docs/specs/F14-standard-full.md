# Спецификация F14. Полная проверка `standard` (раздел 11 стандарта)

Статус: утверждена владельцем, 2026-10-05 (ответы на вопросы внесены в конце). Критерии цели: G2 (ИИ не обходит проверки) и G6 (не теряет нить). Зависит от
F11 (готово по CI) и F18 (связь блок → модули: без неё проверку связности делать нечем).

## Зачем

Сейчас проверка `standard` следит за стоимостью CI (таймауты, отмена прогонов, раннеры), бюджетом текста и отчётами об
инцидентах. Остальное из раздела 11 пока только обещано, и сама проверка честно пишет в выводе «пока не проверяется».
Пока так, ИИ может открыть PR с пустыми «Основаниями», завести второй файл инструкций или оставить проект без обязательных файлов,
и CI это не заметит.

## Что вы получите

- **Обязательные файлы** на месте (цель, конституция, карта модулей, реестр блоков, шаблон инцидента); нет файла: проверка
  называет его и говорит, откуда взять шаблон.
- **Связность** (раздел 3): `features.json` и `MODULES.md` разбираются и связаны; блок без цели, модуль без блока, цикл
  зависимостей, блок без тестов приёмки в статусе «готово» (часть уже на табло; здесь это провал CI, не только строка).
- **Конкурирующие инструкции**: второй файл, который учит ИИ тому же (`CLAUDE.md` без ссылки на `AGENTS.md`, лишние
  `.cursorrules`), и `.md` вне разрешённых мест (то же правило, что у хука, но в CI: хук можно обойти, CI нет).
- **«Основания» в PR**: раздел есть и не пустой (после вычёркивания комментариев шаблона) и называет хотя бы один источник
  (каталог, модуль, ADR, `git log`, поиск). Это проверяет текст, а не добросовестность поиска (раздел 12 стандарта).
- **Карточка соответствия** P1–P13 в `STATUS.md`: оценка и динамика, чтобы вы видели, куда движется проект
  (в разделе 9 стандарта с версии 1.3 тринадцать пунктов, добавлен P13 «Стоимость CI»; прежнее число 12 здесь и в
  разделе 11 стандарта было опечаткой, исправлено в PR 3 по заданию планировщика; принято владельцем при слиянии PR 3).
- **Версия стандарта**: при выходе новой версии `analyze-existing` показывает, что изменилось.

## Что строим (три PR)

**PR 1.** Обязательные файлы, конкурирующие инструкции, `.md` вне разрешённых мест. **PR 2.** Связность (использует F18) и
«Основания» в PR (в CI текст PR передаётся шагом workflow; нужен шаблон описания PR из блока F15, 4г). **PR 3.** Карточка
соответствия и показ изменений версии стандарта.

## Как проверим (тесты приёмки)

`tests/test_standard_full.py`: для каждого правила заведомо плохой пример, который проверка обязана остановить (нет файла;
второй файл инструкций; пустые «Основания»; «Основания» только из комментариев; блок без цели; цикл); чистый проект проходит.
Плюс прогон на тестовых проектах продукта: ложных провалов нет.

## Риски и откат

Главный риск: ложные провалы на существующих проектах (у них свой уклад). Поэтому на существующих проектах новые правила идут
под храповик (старые нарушения записаны, число только снижается) и первый показ идёт предупреждением. Откат: убрать
подключённые правила из `standard`; шаблоны и данные проекта не меняются.

## Что откладывается и сроки

- Откладывается: проверка «честности» оснований и поиска (CI этого не видит, остаётся ревью, F16); проверка PR-метки
  `stuck` по GitHub API (достаточно файлов в репозитории).
- Сроки: примерно три PR и три сессии. Старт только после F18 (две сессии), поэтому до F14 в сумме около пяти сессий. Шаблон PR
  (4г) ждёт перезапуска плагина у вас: пока его нет, PR 2 этого блока не стартует.

## Решения владельца (2026-10-05)

1. «Основания» в PR: достаточно «не пусто и назван источник».
2. На существующих проектах новые правила идут сначала предупреждением, потом храповиком (старые нарушения записаны, число
   только снижается).

## Дополнение по итогам F19 (2026-10-05, утверждено владельцем 2026-10-05 с уточнениями ниже)

3. **Исторические отчёты об инцидентах** (написанные до подключения продукта) попадают под режим существующего проекта:
   долг записывает владелец (`standard --update --accept-new`), дальше храповик; новые отчёты пишутся в формате продукта
   (имя `ГГГГ-ММ-ДД-БЛОК-слово.md`, разделы «Влияние на цель» и «Где искал»).
   - **Почему.** На пилоте F19 (строка 4) перенос `docs/incidents/` → `state/incidents/` дал 10 нарушений по именам и ещё 10
     по разделам: проверка применяла формат продукта ко всем файлам папки без храповика, и перенос по плану приведения
     нельзя было завершить, не переписав историю или не обойдя проверку.
   - **Как будет.** Для проекта с `existing_project: true` отчёт, записанный в `state/standard-baseline.json` как долг
     (ключ `incident:<имя файла>`), проверкой имени, блока и разделов не проверяется; отчёт, которого в долге нет, проверяется
     полностью. Пока долг не записан, существующий проект получает предупреждение (как в PR 1), а не провал. Долг может
     только снижаться: исправленный или удалённый отчёт выходит из него, новое нарушение падает. На новом проекте (без
     `existing_project`) ничего не меняется.
   - **В какой PR.** В **PR 2** этого блока: он расширяет тот же файл долга и режимы из PR 1 и уже трогает `standard`; в PR 3
     (карточка соответствия) это не нужно. Правило и тесты («плохие примеры»: исторический отчёт в долге проходит, новый
     без разделов падает, исправленный выходит из долга, новый проект проверяется как раньше) идут вместе со связностью и
     «Основаниями».
   - **Защита файла долга** (уточнение владельца). `state/standard-baseline.json` защищён так же, как
     `state/baseline.json`: агент его не меняет (охрана путей `guard_paths` и шаблон `settings.json` просят подтверждение
     владельца), любой PR, который его меняет, сливает только владелец (список условия 3 в `AGENTS.md`, ADR-0003, оформлено
     новым ADR по образцу ADR-0014), и в описании такого PR перечислены добавленные в долг ключи. Проверено на момент
     утверждения: файл **не** защищён (его нет в `_STATE_FILES` в `plugin/hooks/guard_paths.py`, в шаблоне
     `plugin/templates/claude/settings.json` и в списке `AGENTS.md`), защита добавляется в PR 2. Тест с плохим примером:
     попытка агента записать в долг ключ `incident:<новый отчёт>` блокируется (нужно подтверждение владельца) для каждой роли.
   - **Что повторяется после.** Строка 4 F19 на той же копии `C:\dev\fm26-data-lab` (ветка `row4-features`): после
     подключения копии к продукту (`init-project`; без него правила не применяются) в долг владельцем одной командой
     `standard --update --accept-new` уйдут и 10 исторических отчётов, и нарушения состава проекта из PR 1. Критерий 4 F19
     = `standard` проходит после записи долга владельцем. Подключение копии и запись долга: отдельный шаг после слияния
     PR 2 и версии плагина с ним, по слову владельца; критерий 4 в `state/acceptance/F19.md` отмечает владелец.
