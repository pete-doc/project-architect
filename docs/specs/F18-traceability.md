# Спецификация F18. Прослеживаемость цели до кода

Статус: утверждена владельцем, 2026-10-05 (ответы на вопросы внесены в конце). Критерий цели: G6 («ИИ не теряет нить проекта: цель прослеживается до
кода»), раздел 3 стандарта. Зависит от F15 (каталог возможностей и карта модулей уже есть).

## Зачем

Сейчас цепочка «цель → блок → тесты приёмки» проверяется и видна на табло, а звено «блок → модули кода» нет: модуль в
`docs/MODULES.md` не говорит, ради какого блока и какой цели он существует. Поэтому ИИ может годами держать код, который
никому не нужен, а вы не можете спросить «зачем этот файл» и получить ответ. После блока у каждого модуля есть блок, у
каждого блока цель, и на вопрос «зачем этот код» отвечает одна команда.

## Что вы получите

- В `docs/MODULES.md` колонка «Блок»: к какому блоку (`F7`) относится модуль. Шаблон проекта и черновик `analyze-existing`
  заводят её сами; где блок неизвестен, черновик ставит «?» и вопрос в `QUESTIONS.md`.
- Проверка CI `modules` дополняется: блок в колонке должен существовать в `state/features.json`; модуль без блока (и без
  статуса `keep-until`) попадает в список «кандидатов на удаление» на табло. Это не удаляет код: решение остаётся за вами.
- Команда `/parch:trace ПУТЬ`: по файлу или функции отвечает цепочкой «цель G → блок F → спецификация → тесты приёмки →
  модуль», простыми словами. Функции берёт из каталога возможностей (`docs/CAPABILITIES.md`).
- На табло строка по каждой цели: сколько её модулей без блока и сколько блоков без модулей.

## Что строим (два PR)

**PR 1. Колонка и проверка.** Колонка «Блок» в шаблоне и в черновике MODULES; проверка `modules` (блок существует, модуль без
блока замечен); строка на табло. Для существующих проектов храповик: модули без блока на момент подключения записаны, число
только снижается, новый модуль без блока падает (как у каталога, ADR-0015).

**PR 2. Команда `/parch:trace`.** Навык, который читает `MODULES.md`, `features.json`, `docs/GOAL.md` и каталог и печатает
цепочку; плохой пример: путь, которого нет ни в одном модуле, получает ответ «не относится ни к одному блоку».

## Как проверим (тесты приёмки)

`tests/test_traceability.py`: колонка есть в шаблоне; блок, которого нет в `features.json`, роняет проверку; новый модуль без
блока падает, старый из храповика нет; `trace` по файлу даёт цепочку и по постороннему пути честно говорит «не найдено».

## Риски и откат

Ложные «модуль без блока» на проектах, где `MODULES.md` ведётся не по нашему формату: проверка называет файл и строку, правка
одна ячейка. Откат: убрать колонку и шаг проверки; данные проекта не меняются.

## Что откладывается и сроки

- Откладывается: привязка отдельных функций к блокам (достаточно модуля); автоматический вывод блока из истории git; удаление
  модулей без блока (это F16, janitor, и только по вашему решению).
- Сроки: примерно два PR и две рабочие сессии. Блок стоит на пути F14 (она использует эту связь), а F16 идёт за F14, поэтому
  задержка F18 сдвигает и их. От вашего ответа зависит только строгость (вопрос 1 ниже).

## Решения владельца (2026-10-05)

1. Модуль без блока на новом проекте это провал CI; на существующих проектах храповик (старое записано, число только снижается).
2. Связь хранится колонкой «Блок» в `docs/MODULES.md`.
