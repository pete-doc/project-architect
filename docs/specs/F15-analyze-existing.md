# Спецификация F15. Полный analyze-existing

Статус: ждёт вашего «утверждаю». Код не пишется, пока вы не ответите. Критерий цели: G4 («существующий проект можно
проверить и привести к стандарту»); раздел 10 стандарта; опыт пилота на fm26-data (`docs/BACKLOG.md`).

## Зачем

Упрощённая версия навыка уже показала на fm26-data главное: проект с собственным устройством получает ложные
«отсутствует», а владелец не получает конкретного плана. Полная версия должна по-прежнему только читать проект и
выдавать три вещи: честную карточку (равноценные файлы засчитываются), карту того, что в проекте есть (модули, швы,
решения, цель), и **план приведения к стандарту как таблицу действий**, которую вы утверждаете. Вторая половина
блока даёт проектам механизмы против главной причины хаоса, ИИ пишет новое, не зная, что уже есть: каталог
возможностей, обязательные описания функций, архитектурные правила и протокол перед новой функцией.

## Что строим (четыре отправки в четырёх PR; проект анализа не меняется ни в одном)

**PR 1. Ядро анализа.** Словарь равноценных файлов (`DECISIONS.md` = решения, `master_plan.md` = цель,
`docs/incidents/` = инциденты, `STATUS.md`, `BACKLOG.md`…; неизвестное уходит вопросом владельцу): такой файл
засчитывается в карточку без штрафа, а план предлагает привести имя к имени стандарта. Черновик `GOAL.md` из
плана проекта и черновики записей решений из журнала решений (всё в `parch-analysis/`, помечено «черновик, ждёт
утверждения»). **План приведения: таблица действий** (ниже). Отчёт проверяет агент внутри Claude Code до выдачи (без
платного API).

**План приведения к стандарту: таблица действий.** Каждая строка — одно проверяемое действие:

| Действие | Что записано в строке | Чем подтверждается |
|---|---|---|
| **Перенести** | старый путь → новый путь | обновлены все ссылки (импорты, пути в скриптах, документы), тесты зелёные |
| **Переименовать под имена стандарта** | текущее имя → имя стандарта | то же, что при переносе |
| **Удалить** | файл или код + доказательство: мёртвый код, дубль, нет ссылок (запрос и результат) | архивная метка в git и поимённое утверждение владельцем |
| **Перестроить** | структура папок и уровни архитектуры | архитектурные правила по уровням проходят в CI |

Предохранители: каждый перенос вместе с обновлением всех ссылок и зелёными тестами; удаление только с архивной
меткой в git и поимённым утверждением владельца; неприкосновенные зоны проекта (у fm26-data это `data/` и сейвы) не
трогать без отдельного «да»; выполнение маленькими PR от безопасного к рискованному; переносы через `git mv`. План
утверждается целиком, необратимые пункты по отдельности.

**PR 2. Карта.** Черновики `MODULES.md` (модули по папкам и языкам: путь, назначение из описания или README, статус)
и `INTERFACES.md` (швы между языками: запуск процессов, общие файлы и форматы, вызовы между Python, C#, PowerShell и
TypeScript), для проверки швов нужны тестовый проект и пример с намеренным швом.

**PR 3. Каталог возможностей и описания функций.** Каталог возможностей собирается автоматически из однострочных
описаний публичных функций; CI проверяет его свежесть (каталог не отстаёт от кода). Обязательное однострочное
описание публичных функций: проверяет линтер, публичная функция без описания не проходит. Языки по очереди (см.
вопрос 1).

**PR 4. Архитектурные правила и протокол.** Архитектурные правила по уровням с примером: низкоуровневую библиотеку
подключать только в одном модуле. Протокол из 5 шагов перед новой функцией в инструкции роли исполнителя (каталог и
реестр модулей, поиск по коду, `git log -S`, прошлые отчёты и уроки, и только потом решение создать новое). Шаблон PR с
разделом «Основания» (что искал и почему создал новое); проверку заполнения подключает F14.

## Как проверим (тесты приёмки)

Для каждого правила заведомо плохой пример, который проверка обязана остановить: равноценный файл засчитан, а имя
предложено привести к стандарту; в таблице плана нет строки без одного из четырёх действий; «удалить» без
доказательства и без поимённого утверждения отвергается; «перенести» без обновления ссылок отвергается; путь в
неприкосновенной зоне помечен «нужно отдельное «да»»; после анализа `git status` проекта чист, кроме `parch-analysis/`;
устаревший каталог роняет CI; функция без описания и нарушение уровня архитектуры падают; библиотека, подключённая
в двух модулях, падает. Тесты приёмки блока: `tests/test_analyze_plan.py`, `tests/test_analyze_maps.py`,
`tests/test_catalog.py`, `tests/test_architecture_rules.py` (имена предварительные).

## Что нужно от вас (ответьте «да» или поправьте)

1. Каталог и линтер описаний: языки по очереди. Предлагаю сначала Python и C# (языки fm26-data), затем TypeScript и
   PowerShell. Верно?
2. Папка `plugin/agents/` пуста. Протокол из 5 шагов пишу в новую роль «исполнитель» (`implementer`); остальные роли
   (architect, tester) не трогаю. Верно?
3. Шаблон PR с «Основаниями» в F15, проверка заполнения в F14. Верно?
4. Черновики GOAL, MODULES, INTERFACES и решений лежат только в `parch-analysis/` и в проект попадают отдельными PR
   по вашему утверждению. Верно?
5. Словарь равноценных файлов начинается с известных соответствий (список в PR 1), всё неизвестное уходит
   вопросом, а не угадывается. Верно?

## Риски

Эвристики карты и швов дают ложные находки: поэтому всё помечено «черновик», а решение принимаете вы. Каталог на
больших проектах может стать шумным: каталог содержит только публичные функции с описанием. Откат: блок не меняет
проект анализа; навык и проверки отключаются удалением из плагина.
