# Спецификация F15. Полный analyze-existing

Статус: **заготовка, не утверждена.** Полная спецификация на одну страницу будет написана, когда до F15 дойдёт очередь
(после F13), и ждёт вашего «утверждаю» до кода. Здесь записано то, что владелец уже потребовал заложить (2026-10-04),
чтобы это не потерялось.

## Основа блока (из порядка работ)

Карта модулей и швов между языками, восстановленные решения, черновик цели с распознаванием равноценных файлов
(например, `DECISIONS.md` вместо `docs/adr/`, `master_plan.md` вместо `GOAL.md`), план приведения к стандарту.
Опыт пилота на fm26-data: см. `docs/BACKLOG.md` (карточка занижает проекты с собственным устройством).

## Требования владельца, которые обязательно войдут в спецификацию

1. **Каталог возможностей.** Собирается автоматически из описаний публичных функций; CI проверяет его свежесть (каталог
   не отстаёт от кода). Это ответ на «ИИ пишет новое, не зная, что уже есть».
2. **Обязательное однострочное описание публичных функций.** Проверяет линтер: публичная функция без описания в одну
   строку не проходит.
3. **Архитектурные правила по уровням** с примером: «низкоуровневую библиотеку подключать только в одном модуле».
4. **Протокол из 5 шагов перед новой функцией** в инструкции роли исполнителя: поиск по каталогу и реестру модулей,
   поиск по коду, история (`git log -S`), прошлые отчёты и уроки, и только потом решение создать новое.
5. **Раздел «Основания» в PR:** что искал (какие запросы и где) и почему создал новое, а не использовал имеющееся.

Связанные блоки: F18 (прослеживаемость цели до кода) и F14 (полная проверка `standard`, в ней проверка раздела
«Основания») продолжают эту линию; граница между блоками уточняется в полной спецификации.

## План приведения к стандарту: конкретная таблица действий (требование владельца, 2026-10-04)

Отчёт анализа содержит не общие советы, а таблицу действий; каждая строка это одно проверяемое действие:

| Действие | Что записано в строке | Чем подтверждается |
|---|---|---|
| **Перенести** | старый путь → новый путь | все ссылки обновлены (импорты, пути в скриптах, документы), тесты зелёные |
| **Переименовать под имена стандарта** | текущее имя → имя стандарта (например, `DECISIONS.md` → `docs/adr/`, `master_plan.md` → `docs/GOAL.md`) | то же, что при переносе |
| **Удалить** | файл или код + доказательство: мёртвый код, дубль, нет ссылок (запрос поиска и его результат) | архивная метка в git и поимённое утверждение владельца |
| **Перестроить** | структура папок и уровни архитектуры: что куда и какой уровень чем может пользоваться | архитектурные правила по уровням проходят в CI |

**Равноценные файлы засчитываются при оценке.** Файл проекта с тем же назначением, что у файла стандарта, считается
выполненным пунктом карточки (без штрафа), а план лишь предлагает привести имя к имени стандарта строкой «переименовать».

**Предохранители** (обязательные условия выполнения плана):
1. Каждый перенос идёт вместе с обновлением всех ссылок (импорты, пути в скриптах, документы) и зелёными тестами.
2. Удаление только с архивной меткой в git и поимённым утверждением владельца.
3. Неприкосновенные зоны проекта (у fm26-data это `data/` и сейвы) не затрагиваются без отдельного «да» владельца.
4. Выполнение маленькими PR, от безопасного к рискованному; переносы через `git mv` (история сохраняется).
5. План утверждается целиком; необратимые пункты (удаления, затрагивающие неприкосновенные зоны) отдельно, по одному.
