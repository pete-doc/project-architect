# Спецификация F15. Полный analyze-existing

Статус: ждёт вашего «утверждаю». Код не пишется, пока вы не ответите. Критерий цели: G4 («существующий проект можно
проверить и привести к стандарту»); раздел 10 стандарта; опыт пилота на fm26-data (`docs/BACKLOG.md`).

## Зачем

Упрощённая версия навыка показала на fm26-data главное: проект с собственным устройством получает ложные
«отсутствует», а владелец не получает конкретного плана. Полная версия по-прежнему только читает проект и выдаёт:
честную карточку (равноценные файлы засчитываются), карту того, что в проекте есть, и **план приведения к стандарту
как таблицу действий**, которую вы утверждаете. Вторая половина блока даёт проектам механизмы против главной причины
хаоса, ИИ пишет новое, не зная, что уже есть: каталог возможностей, обязательные описания функций, архитектурные
правила и протокол перед новой функцией.

## Что берём из документа «Модуль анализа» и что уже есть в навыке

Самого документа в репозитории нет (на него ссылается только `BUILD_PLAN.md`, фаза E), поэтому опираюсь на шесть
шагов оттуда и на раздел 8 стандарта. Что в упрощённом навыке уже есть, а что добавляет полная версия:

| Пункт | В упрощённом навыке | В полной версии |
|---|---|---|
| Инвентаризация, карточка P1–P13, отчёт, проверка «код не менялся» | **уже есть** | остаётся |
| Главные риски | есть, не больше 5 | **5–10**, по убыванию |
| Снимок исходного состояния инструментов | нет (сознательно) | перечень линтеров, тестов, версий и настроек из файлов проекта; запуск проверок проекта только с вашего разрешения для этого проекта |
| Горячие точки по истории git | нет | топ больших, часто меняемых файлов без тестов (раздел 8 стандарта) |
| Вопросы по мёртвому коду в `QUESTIONS.md` | нет | по каждому кандидату три вопроса: вызывается ли снаружи (скрипт, внешний процесс), есть ли рефлексия или динамический вызов, нет ли запуска планировщиком (cron, CI) |
| Карта модулей и швов | нет | PR 2 |

## Что строим (четыре отправки в четырёх PR; анализируемый проект не меняется ни в одном)

**PR 1. Ядро анализа.** Словарь равноценных файлов (`DECISIONS.md` = решения, `master_plan.md` = цель,
`docs/incidents/` = инциденты, `STATUS.md`, `BACKLOG.md`…; неизвестное уходит вопросом владельцу): такой файл
засчитывается в карточку без штрафа, а план предлагает привести имя к имени стандарта. Снимок инструментов, горячие
точки git, 5–10 рисков, `QUESTIONS.md` с вопросами по мёртвому коду. Черновики `GOAL.md` и записей решений из журнала
решений (всё в `parch-analysis/`, помечено «черновик, ждёт утверждения»). **План приведения** (таблица ниже). Отчёт
проверяет агент внутри Claude Code до выдачи (без платного API).

**План приведения к стандарту: таблица действий.** Каждая строка — одно проверяемое действие:

| Действие | Что записано в строке | Чем подтверждается |
|---|---|---|
| **Перенести** | старый путь → новый путь | обновлены все ссылки (импорты, пути в скриптах, документы), тесты зелёные |
| **Переименовать под имена стандарта** | текущее имя → имя стандарта | то же, что при переносе |
| **Удалить** | файл или код + доказательство: мёртвый код, дубль, нет ссылок (запрос и результат) | архивная метка в git и поимённое утверждение владельцем |
| **Перестроить** | структура папок и уровни архитектуры | архитектурные правила по уровням проходят в CI |

Предохранители: каждый перенос вместе с обновлением всех ссылок и зелёными тестами; удаление только с архивной
меткой в git и поимённым утверждением владельца; неприкосновенные зоны проекта (у fm26-data это `data/` и сейвы) не
трогать без отдельного «да»; выполнение маленькими PR от безопасного к рискованному; переносы через `git mv`. План
утверждается целиком, необратимые пункты по отдельности. **Код без тестов:** перенос или переименование кода, который
тестами не покрыт, идёт только после характеризационного теста (он фиксирует нынешнее поведение) либо со строкой
«рискованно, нужно отдельное «да»».

**PR 2. Карта.** Черновики `MODULES.md` (модули по папкам и языкам: путь, назначение из описания или README, статус)
и `INTERFACES.md` (швы между языками: запуск процессов, общие файлы и форматы, вызовы между Python, C#, PowerShell и
TypeScript). **Шов без контрактного теста — красный сигнал в карточке.** В плане приведения изменение шва идёт только
после контрактного теста этого шва. Для проверки нужны тестовый проект и пример с намеренным швом.

**PR 3. Каталог возможностей и описания функций.** Каталог возможностей собирается автоматически из однострочных
описаний публичных функций; CI проверяет его свежесть (каталог не отстаёт от кода). Обязательное однострочное
описание публичных функций: проверяет линтер, публичная функция без описания не проходит. Языки по очереди: Python и
C#, затем TypeScript и PowerShell.

**PR 4. Архитектурные правила и протокол.** Архитектурные правила по уровням с примером: низкоуровневую библиотеку
подключать только в одном модуле. Протокол из 5 шагов перед новой функцией в новой роли «исполнитель»
(`plugin/agents/implementer.md`): каталог и реестр модулей, поиск по коду, `git log -S`, прошлые отчёты и уроки, и
только потом решение создать новое. Шаблон PR с разделом «Основания» (что искал и почему создал новое); проверку
заполнения подключает F14.

## Где план выполняется на реальном проекте: блок F19

План приведения выполняется **отдельным блоком F19 «Приведение реального проекта к стандарту по утверждённому
плану»** (цель G4; зависит от F15 и F17; первый проект fm26-data). Его принимаете вы: `state/acceptance/F19.md`
со списком утверждённых пунктов плана. Блок идёт маленькими PR в самом проекте, от безопасного к рискованному, по
предохранителям выше. Спецификацию F19 пишу после F15 (одна страница, ваше «утверждаю»).

## Как проверим (тесты приёмки F15)

Для каждого правила заведомо плохой пример, который проверка обязана остановить: равноценный файл засчитан, а имя
предложено привести к стандарту; в таблице плана нет строки без одного из четырёх действий; «удалить» без
доказательства и без поимённого утверждения отвергается; «перенести» без обновления ссылок отвергается; перенос кода
без тестов без характеризационного теста и без пометки «рискованно» отвергается; изменение шва без контрактного теста
отвергается, шов без такого теста даёт красный сигнал; путь в неприкосновенной зоне помечен «нужно отдельное «да»»;
после анализа `git status` проекта чист, кроме `parch-analysis/`; вопросы по мёртвому коду содержат три вопроса;
устаревший каталог роняет CI; функция без описания и нарушение уровня архитектуры падают; библиотека, подключённая в
двух модулях, падает. Тесты приёмки блока: `tests/test_analyze_plan.py`, `tests/test_analyze_maps.py`,
`tests/test_catalog.py`, `tests/test_architecture_rules.py` (имена предварительные).

## Решения владельца (2026-10-04)

На все пять вопросов ответ «да»: языки каталога по очереди (Python и C#, затем TypeScript и PowerShell); протокол
пишется в новую роль `implementer`, остальные роли не трогаем; шаблон PR с «Основаниями» в F15, проверка заполнения
в F14; черновики GOAL, MODULES, INTERFACES и решений лежат только в `parch-analysis/` и попадают в проект отдельными
PR по вашему утверждению; словарь равноценных файлов начинается с известных соответствий, неизвестное уходит
вопросом, а не угадывается.

## Риски

Эвристики карты и швов дают ложные находки: поэтому всё помечено «черновик», а решение принимаете вы. Каталог на
больших проектах может стать шумным: он содержит только публичные функции с описанием. Откат: блок не меняет
анализируемый проект; навык и проверки отключаются удалением из плагина.
