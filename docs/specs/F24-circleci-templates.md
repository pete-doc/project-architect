# Спецификация F24. Шаблоны CI на CircleCI

Статус: черновик, ждёт утверждения владельца (вместе с ADR-0022 в статусе `proposed`). Цель G1. Зависит от F3 (init-project
и шаблоны) и F11 (init и бюджет CI). **F20 теперь ждёт F24.** Решение владельца, 2026-10-06: шаблоны CI для проектов
пользователей переходят с GitHub Actions на CircleCI полностью, GitHub Actions как вариант не остаётся; табло переезжает
вместе с CI. Это отменяет прежнее «шаблоны не менять» (оно действовало до F20). В этом PR только документы: код и шаблоны
не тронуты.

## Зачем

Живой прогон F20 (2026-10-06) нашёл поломку, которую не ловили никакие тесты продукта: шаблон `state.yml` ищет отчёт тестов
в прогоне `full.yml`, которого в проектах пользователей нет. GitHub отвечает «HTTP 404», шаг падает, табло после первого же
слияния не публикуется. Для самого продукта CI уже на CircleCI (ADR-0020), и там табло устроено надёжнее: тесты идут в самом
задании `state`, отчёт всегда рядом. F24 переносит этот проверенный рабочий вариант в шаблоны.

## Что кладёт `/parch:init-project` вместо `ci.yml` и `state.yml`

- `.circleci/config.yml` одним файлом, собранным из шаблонов `plugin/templates/ci/circleci/` (заготовка + блок на каждый язык
  проекта). `.github/workflows/` init **не создаёт**. Остаются `.github/parch/` (скрипты проверок) и
  `.github/pull_request_template.md`: пути не меняются, чтобы не ломать `standard`, hooks и тесты.
- Два workflow: `ci` (на каждую отправку в ветку, кроме `main`) и `state` (только на `main`, после слияния).
- **Имена заданий = имена проверок в GitHub** (`ci/circleci: <имя задания>`, документация CircleCI «Status updates»).
  Решение владельца 2026-10-06: **один итоговый шаг `check`**. Каждый язык проекта даёт своё задание `check-python`,
  `check-typescript`, `check-csharp`, `check-powershell`, а задание **`check`** (маленький контейнер `small`, без тяжёлых шагов) в
  workflow `ci` имеет `requires` на **все** языковые задания: оно запускается, только когда все они зелёные. В защите `main`
  обязательна **одна** проверка **`ci/circleci: check`**; языковые задания обязательными не делаются (их красный цвет виден в PR, а
  `check` без них не появится, и слить нельзя). Поведение статуса `check` в GitHub, когда языковое задание упало (не запущен ли
  он, «ожидается» ли вечно), по документации не проверено: проверяет шаг 5 прогона F20, пока не видно «слить нельзя», блок не принят.
  В проекте с одним языком то же самое: `check-python` и `check` с `requires: [check-python]`.
- Задание `check-python`: образ `cimg/python:3.12-node` (Node нужен pyright), класс `medium`; шаги те же, что в
  `python.yml`: `ruff`, формат, `pyright`, `pytest --junitxml`, проверки `parch_ci.py` (settings, tests, skips, suppressions,
  modules, catalog, standard с описанием PR, deps, architecture, dead-code, duplicates, coverage). Отчёт сохраняется
  `store_test_results` и `store_artifacts`, даже при падении тестов. **Пределы времени (честно):** у CircleCI нет `timeout-minutes`
  на задание; единственный жёсткий предел это **1 час на задание на плане Free** (документация поддержки CircleCI, проверено
  2026-10-06). Мы ставим сами: `no_output_timeout` и `timeout` (например, `timeout 600` на тесты) **на каждый шаг, который может
  зависнуть** (установка зависимостей, тесты, проверки `parch_ci.py`), так что расчётная длительность `check-python` до 15 минут;
  это расчёт из пределов шагов, а не гарантия задания.
- **Описание PR для проверки «Основания» (`standard`).** В Actions его передавала переменная `PARCH_PR_BODY` из события GitHub; в
  CircleCI такого нет. Переменная `CIRCLE_PULL_REQUEST` доступна **только для PR из форков** (документация CircleCI), поэтому PR
  ищется по ветке: запрос GitHub API `pulls?head=<владелец>:<CIRCLE_BRANCH>&state=open`, из ответа берётся описание. У приватного
  репозитория нужен **токен чтения** (fine-grained, только этот репозиторий, право «Pull requests: Read-only»), владелец кладёт
  его в переменную проекта `PARCH_GITHUB_READ_TOKEN` (пункт В2). Если описание получить не удалось (нет токена, PR не найден, API не
  ответил), `standard` на сборке PR **падает громко**: «описание PR недоступно, раздел «Основания» не проверен: переменная
  `PARCH_GITHUB_READ_TOKEN`, пункт В2»; молчаливого отключения проверки нет (плохой пример в тестах).
- **Ловушка режима совместимости** (ADR-0020): проект в CircleCI создаётся только в родном режиме («использовать конфиг из
  репозитория»). Режим «GitHub Actions workflow как конфиг» не понимает этот файл и показывает фальшивый зелёный за секунды.
  Признак: проверка проходит за 4 секунды, задания `check` в ней нет.

## Табло на CircleCI

- **Откуда отчёт тестов.** Задание `state` (только `main`) само гоняет тесты на коммите `main` и тут же строит табло: отчёт
  относится к тому же коммиту и никуда не ходит по сети. Ни API CircleCI, ни личный токен CircleCI не нужны (артефакты через
  API v2 отдаются только с токеном, `Circle-Token`, это лишний секрет).
- **Чем публикуется ветка `status` (решение владельца 2026-10-06).** SSH-ключом записи (deploy key GitHub с правом записи):
  владелец создаёт пару ключей, открытую часть добавляет в репозиторий как Deploy key с «Allow write access», закрытую в
  CircleCI (Project Settings → SSH Keys → Additional SSH Keys, хост `github.com`). Ключ хранится только в настройках проекта
  CircleCI, в репозитории его нет. У ключа нет права обхода ruleset `main`, поэтому в `main` он писать не может, **но только
  при включённой защите `main`: поэтому ключ добавляется последним, после защиты** (пункт В5 ниже; без защиты ключ писал бы и в `main`).
- **Порядок шагов в задании `state` фиксирован:** 1) `checkout`; 2) установка зависимостей; 3) **тесты проекта** (отчёт
  `store_test_results` и `store_artifacts`, код выхода тестов запоминается, шаг не прерывает задание); 4) сборка табло
  `parch_status.py`; 5) **только теперь** `add_ssh_keys` и публикация в `status`; 6) последний шаг возвращает код тестов. Код
  проекта (тесты, `conftest`) выполняется до подключения ключа и ключа не видит; `add_ssh_keys` есть только в задании `state`
  и нет ни в одном `check-*`. Порядок проверяет тест (см. ниже).
- **Табло и цвет задания `state` (решение владельца 2026-10-06):**
  - **Тесты упали** (код не 0 или в отчёте есть падения): табло публикуется с пометкой «тесты упали: N», **задание красное**.
  - **Отчёта нет, а тесты в проекте есть** (файлы тестов или записи в `state/baseline.json`): табло публикуется с пометкой
    «отчёта тестов нет при существующих тестах: тесты не запустились», **задание красное**. Это не 404 и не падение скрипта,
    а честный красный: пропавший отчёт не должен выглядеть зелёным.
  - **Отчёта нет, потому что в проекте нет ни одного теста:** допустимо, табло так и пишет «в проекте нет тестов», задание
    зелёное.
  - Падают из-за самого скрипта табло только настоящие поломки (не прочитан `features.json`, не удалось записать).
- **Что делает `state`, пока ключа ещё нет** (пункт В5 не сделан: по плану прогона F20 В5 идёт до первого слияния, но в любом проекте, где его пропустили, задание ведёт себя так): табло
  собирается, шаг публикации печатает по-русски **«ключ записи не подключён, табло не опубликовано, шаг В5 в инструкции»** и
  завершается без ошибки; цвет задания задаёт только результат тестов. Это не падение с неясной ошибкой. Как реализация
  отличает «ключа нет» от «ключ есть, но push отклонён» (нет права записи, ключ добавлен без записи): оба случая дают понятное
  сообщение со ссылкой на В5; поведение `add_ssh_keys` без ключей в проекте по документации не проверено, реализация проверяет
  его на живом проекте и при необходимости заменяет проверкой доступа по SSH.
- **Если слияний два подряд:** публикует только прогон последнего коммита `main` (как в ADR-0020).
- **Открытые PR на табло:** запрос к GitHub API без токена; у приватного репозитория он вернёт 404, и раздел «открытые PR»
  просто пропускается с сообщением (так уже работает `state_inputs.py`). Это ограничение записано, не поломка.

## Что владелец делает руками в каждом новом проекте (пункты В1–В5)

Пункты называются В1–В5, чтобы не путать с шагами 1–7 сценария F20; **порядок строгий, пункты нельзя менять местами**. Эти же
названия и этот же порядок стоят в F20 и в ADR-0022 и выводятся init в конце:

- **В1. Доступ GitHub App CircleCI к репозиторию** (до первого запуска CI).
- **В2. Создать проект в CircleCI и добавить токен чтения описания PR** (до первого запуска CI).
- **В3. Включить автоотмену устаревших прогонов** (до первого запуска CI).
- **В4. Включить защиту `main` после первого зелёного `check`** (имя проверки появляется в GitHub только после первого запуска).
- **В5. Подключить ключ записи табло: только после В4** (пока защиты `main` нет, ключ не подключается).

Подробно:

В1. **GitHub App CircleCI имеет доступ к новому репозиторию:** GitHub → Settings → Applications → CircleCI → Configure → выбрать
   репозиторий (если приложение стоит «на все репозитории», шаг не нужен).
В2. **Создать проект:** CircleCI → Home → **Create Project** → имя проекта → «Next: Set up a pipeline» → имя `ci` → «Next:
   Choose a repo» → плитка **GitHub Cloud** → репозиторий → **использовать существующий конфиг** (`.circleci/config.yml`) → триггер
   «PR opened or pushed to, default branch and tag pushes» → завершить настройку. **Токен чтения описания PR:** GitHub → Settings →
   Developer settings → Fine-grained personal access tokens → Generate new token: репозиторий только этот, право **Pull requests:
   Read-only**, больше ничего; затем CircleCI → Project Settings → **Environment Variables** → Add: имя `PARCH_GITHUB_READ_TOKEN`,
   значение токена. После В1–В3 и отправки PR дождаться **первого зелёного `check`**.
В3. **Project Settings → Advanced → Auto-cancel Redundant Workflows**: включить (иначе устаревшие прогоны тратят кредиты).
В4. **Защита `main` после первого зелёного `check`:** GitHub → Settings → Rules → New branch ruleset → `main` → Require status
   checks → добавить **одну** проверку `ci/circleci: check` (имя появляется в списке только после первого запуска; языковые
   `check-*` обязательными не делаются); оставить включёнными **Restrict deletions** и **Block force pushes** (запрет удаления
   `main` и принудительной отправки в неё).
В5. **Ключ публикации табло, только после В4:** на своём компьютере вне репозитория `ssh-keygen -t ed25519 -N "" -f status_key`;
   GitHub → репозиторий → Settings → **Deploy keys** → Add deploy key, `status_key.pub`, галка **Allow write access**; затем
   CircleCI → Project Settings → **SSH Keys → Additional SSH Keys → Add SSH Key**, хост `github.com`, закрытая часть
   `status_key`; после этого оба файла на компьютере удалить. **Ключ нельзя подключать, пока защита `main` не включена.**

Может ли `init-project` вывести это в конце: **да** (пунктами В1–В5 в этом порядке). Раздел отчёта init «замечания команды» (там сейчас стоит напоминание про
бюджет Actions) заменяется этой инструкцией по-русски; сам init шагов не выполняет (аккаунты и ключи только у владельца).

## Расход кредитов CircleCI (правило 10, ADR-0011)

**Лимит тарифа** (circleci.com/pricing, 2026-10-06): бесплатный план 30 000 кредитов в месяц, до 5 активных пользователей, кредиты
не переносятся; «30 000 кредитов по 10 кредитов в минуту (Linux medium) это 3 000 минут». Приватный репозиторий пул открытых
проектов (до 400 000 кредитов Linux) **не получает**: только эти 30 000. Класс `medium` Docker: 2 vCPU, 4 ГБ, 10 кредитов/мин
(small 5, large 20, по ADR-0020; в шаблонах выше `medium` не берём).

| Что | Время | Кредиты |
|---|---|---|
| Проверка PR `check-python` (пустой проект: установка, ruff, pyright, тесты, проверки) + итоговый `check` (`small`, около 15 с) | ~3 мин (оценка, не замер) | ~30 + ~2 |
| Табло `state` на `main` (те же тесты и публикация) | ~3 мин | ~30 |
| **Один прогон F20** (6 проверок PR с запасом + 2 табло) | ~24 мин | **~240; расчётный потолок 1 100** (6 × 15 мин × 10 + 2 × 10 мин × 10); см. ниже про жёсткий предел |
| **Типичный месяц маленького проекта** (40 отправок PR, 25 слияний) | ~190 мин | **~1 900 (около 6 % бесплатных 30 000)** |

**Расчётный и жёсткий потолок.** 1 100 кредитов это сумма заданных нами пределов шагов, а не гарантия. Единственный жёсткий предел
CircleCI: **1 час на задание на плане Free**; зависшее задание `medium` стоит до 60 мин × 10 = **600 кредитов** (2 % месячного лимита).
Худший случай прогона F20: расчётный потолок плюс одно зависшее задание, то есть около 1 700 кредитов (около 6 % лимита). Защита:
пределы на каждом шаге (см. выше), автоотмена (В3) и наблюдение исполнителя за прогоном с ручной отменой.

Если кредиты кончатся, сборки останавливаются до следующего месяца; поведение на Free при исчерпании в документации не проверено,
остаток виден в Plan Usage (проверить после первой недели). Все проекты организации CircleCI делят один пул.

## Windows и macOS

В шаблонах **только Linux** (Docker, класс `medium`). Windows (×4 к кредитам: 40 против 10 в минуту у medium) и macOS добавляются
только отдельным ADR с оценкой кредитов; `parch_ci.py standard` уже читает `.circleci/*.yml` и ловит чужие исполнители и
классы выше `medium` (ADR-0020, п. 9). Правила про `.github/workflows` для старых проектов остаются.

## Тесты (приёмка блока)

`tests/test_circleci_templates.py` (имя вносится в `acceptance_tests` блока F24 в PR реализации вместе с файлом: тест
`test_the_product_has_a_consistent_goal_and_plan` не допускает ссылку на несуществующий файл), у каждой проверки заведомо плохой пример:
- конфиг, собранный init для каждого из четырёх языков, проходит `circleci config validate` (CLI ставится в `check` продукта
  одним шагом с проверкой контрольной суммы, как в ADR-0020; без CLI тест пропускается только локально, в CI не пропускается);
- init не создаёт `.github/workflows/`, создаёт `.circleci/config.yml` с заданиями `check-<язык>`, итоговым `check`, у которого `requires`
  содержит **все** языковые задания (плохой пример: `check` без одного из них пропускает красный язык), и workflow `state`;
- **шаг табло против подставного API**, который отвечает 404, пустым списком и обрывом связи: раздел «открытые PR» пропускается, задание
  не падает из-за API (плохой пример: прежний шаблон падал с 404);
- **подставные данные тестов (решение владельца 2026-10-06):** тесты упали (отчёт с падением): задание красное, табло с пометкой «тесты
  упали»; **отчёта нет, а тесты в проекте есть**: задание красное, табло с пометкой «отчёта тестов нет при существующих тестах»;
  отчёта нет в проекте без единого теста: задание зелёное, табло пишет «в проекте нет тестов»;
- **порядок шагов:** в `state` шаг `add_ssh_keys` стоит после шага тестов проекта, а в заданиях `check-*` его нет (плохой пример:
  `add_ssh_keys` до тестов или в `check-python`);
- **описание PR (подставной GitHub API):** токена нет, PR не найден по ветке, API отвечает 404, 500 и обрывом: `standard` на сборке PR
  падает громко с сообщением про `PARCH_GITHUB_READ_TOKEN` (плохой пример: молчаливое отключение проверки «Основания», как при
  переносе `PARCH_PR_BODY` без источника); описание получено: раздел проверяется, пустые «Основания» ловятся;
- **нет ключа записи** (подставной проект без дополнительных ключей и ssh-агент без ключей): сообщение «ключ записи не подключён,
  табло не опубликовано, шаг В5 в инструкции», **без падения с неясной ошибкой**, цвет задаёт только результат тестов (плохой пример:
  необработанная ошибка `add_ssh_keys` или `Permission denied (publickey)` без пояснения); push отклонён (ключ без права записи): то же
  сообщение со ссылкой на В5; ключ есть, а ветка не `main`: не публикуется;
- текст В1–В5 в инструкции init совпадает по порядку и названиям с этим разделом (плохой пример: ключ раньше защиты `main`);
- `standard` ловит в шаблоне Windows/macOS-исполнитель, класс выше `medium` и задание без предела времени.

## Затронутые файлы и что с каждым будет (решение владельца 2026-10-06)

**Правило.** Старые тесты шаблонов Actions **заменяются, а не удаляются**: переписываются под шаблоны CircleCI так, чтобы число
тестов в храповике (`state/baseline.json`) не уменьшалось. Если какой-то тест придётся убрать, PR реализации называет его поимённо
с причиной, и по каждому решает владелец. Общего разрешения на удаление нет (`--accept-removed` только по такому решению). Список
составлен поиском по репозиторию (имена шаблонов, `ci.yml`, `state.yml`, `.github/workflows`) и при реализации сверяется заново.

| Файл | Что делает сейчас | Что будет |
|---|---|---|
| `plugin/templates/ci/python.yml`, `typescript.yml`, `csharp.yml`, `powershell.yml`, `state.yml` | шаблоны Actions | заменяются шаблонами `plugin/templates/ci/circleci/` (заготовка, блок на язык, `state`); старые удаляются в том же PR, что и тесты на них |
| `plugin/templates/claude/settings.json` | правило `Edit(/.github/**)` для проектов | добавляется `Edit(/.circleci/**)` (`.github/parch/` остаётся) |
| `plugin/skills/init-project/scripts/init_project.py` (7 мест) | копирует шаблоны в `.github/workflows/` | собирает `.circleci/config.yml`; выводит пункты В1–В5; не создаёт `.github/workflows/` |
| `plugin/skills/init-project/SKILL.md` | напоминание про бюджет Actions | инструкция В1–В5 вместо него |
| `plugin/hooks/guard_paths.py` | `.circleci` уже в списке защищённых каталогов CI | без изменений кода; тест `test_guards.py` дополняется правкой `.circleci/config.yml` |

## Что меняется в F20

Подробно в `docs/specs/F20-end-to-end.md`: шаг 3 (CI идёт в CircleCI, перед ним владелец делает В1–В3 из списка выше; В4 и В5 после
шага 3 в этом порядке), шаг 7 (табло публикует задание `state` по ключу записи), бюджет (кредиты CircleCI вместо минут Actions), таблица «Что
нужно от владельца». `docs/GOAL.md` не меняется.

## Риски и откат

- **Все подключённые проекты с `.github/workflows` старого вида** (fm26-data и любые прежние) остаются как есть; миграцию
  каждого делает отдельная просьба владельца, автоматически ничего не переписывается.
- **Ключ записи.** Ключ проекта CircleCI доступен заданиям любой ветки проекта (конфиг берётся из самой ветки): ветка с задачей,
  печатающей ключ, получила бы право писать в нерезервные ветки репозитория. `main` защищён ruleset без права обхода; риск
  ограничен веткой `status` и новыми ветками. Для публичных проектов вариант с токеном в context (ADR-0020) надёжнее.
- **Первый запуск шаблона на настоящем CircleCI** может найти ещё ошибки (как `state.yml` на Actions): поэтому F20 держит запас
  кредитов и повтор прогона.
- **Откат:** вернуть шаблоны `ci.yml` и `state.yml` из истории git (`git revert` PR реализации), в уже подключённых новых проектах
  удалить `.circleci/` и проект в CircleCI.

## Решения владельца 2026-10-06 (открытых вопросов нет)

1. **Ключ записи ветки `status`:** SSH-ключ проекта (deploy key GitHub с записью). Подключается только в задании `state` и только
   после тестов проекта.
2. **Повтор прогона F20:** на новом пустом приватном репозитории. Репозиторий создаёт владелец после слияния реализации F24
   (не раньше). `parch-e2e-test` остаётся как есть.
3. Старые тесты шаблонов заменяются, а не удаляются (раздел «Затронутые файлы»); один итоговый `check` в защите `main`; нет отчёта
   при существующих тестах или упавшие тесты: `state` красное.
