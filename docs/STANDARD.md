# Стандарт ProjectArchitect: как устроен и как ведётся ИИ-проект

*ProjectArchitect · проектный документ · версия 1.3 · 3 октября 2026*
*Спецификация для продукта: по ней `/parch:init-project` создаёт новый проект, а `/parch:analyze-existing` проверяет существующий и приводит его к стандарту.*

> **Кому адресован этот документ.** Разработчикам продукта ProjectArchitect и аудиту. ИИ, который ведёт проект пользователя, этот документ в работе **не читает**: стандарт доходит до него через шаблоны, проверки и короткие инструкции ролей (раздел 12).

> **Что изменилось в 1.2.** Добавлена защита от петли планировщика: бюджет инцидентов на блок, статус `stuck`, обязательный раздел «Влияние на цель» в отчётах, карточка решения для человека (разделы 3, 6.3, 6.6, 7.1, 11). Исправлено описание того, как планировщик видит репозиторий: подключение GitHub к Claude Project — снимок, а не живое чтение, и писать в репозиторий планировщик не может (раздел 4). Открытые вопросы реализации вынесены в раздел 13.

> **Что изменилось в 1.3.** Стандарт впервые учитывает, что CI стоит денег. Повод: 2 октября 2026 CI продукта за один вечер съел 2 700 из 3 000 бесплатных минут и $17 — матрица из трёх ОС без таймаута и без отмены старых прогонов, добавленная исполнителем «на всякий случай». Новый раздел 7.2 «Стоимость CI»: Linux по умолчанию, целевая ОС проверяется там, где исполнитель и так работает, таймаут и отмена в шаблоне, конфигурация CI — необратимое по цене решение. Затронуты разделы 0, 1, 5, 6.5, 7.1, 9, 11, 12, 13.

## 0. Зачем нужен стандарт и как он применяется

Проект, который ведёт ИИ, ломается не там, где ломается обычный. Код может быть приличным, а проект всё равно разваливается: ИИ теряет цель, забывает принятые решения, не знает, что задача уже решена, ходит по кругу, плодит планы, которые никто не читает. Поэтому стандарт описывает две вещи сразу:

1. **Качество кода** — по модели сопровождаемости ISO/IEC 25010 плюс сложность (раздел 8).
2. **Организацию ИИ-процесса** — файлы, роли, источники знаний, конвейер работы, обработку сбоев, синхронизацию (разделы 1–7).

Стандарт один для всех проектов. **Новый проект** создаётся по нему с первого дня (`/parch:init-project`). **Существующий** сначала проверяется на соответствие (`/parch:analyze-existing`), затем ИИ приводит его к стандарту серией небольших PR, а вы утверждаете ключевые решения (раздел 10). Соответствие стандарту проверяется автоматически в CI (раздел 11), а не на словах.

### Пять принципов, из которых выводится всё остальное

1. **Единственный источник истины — репозиторий.** Всё, что нужно знать ИИ о проекте, лежит в файлах репозитория. То, что существует только в чате, в памяти модели или в Jira, для проекта не существует.
2. **Факты, а не память.** Перед решением ИИ читает файлы и код, а не вспоминает. Любое утверждение о проекте опирается на конкретный файл.
3. **Проверки, а не инструкции.** Всё, что можно проверить автоматически, проверяется hook'ом или CI. Инструкции в тексте — только для того, что проверить нельзя. Hook работает на машине исполнителя бесплатно, CI — за деньги: поэтому сначала hook, а CI только повторяет его результат, чтобы ему можно было верить (раздел 7.2).
4. **Цель прослеживается до кода.** Каждый кусок кода существует ради конкретной части цели, и это видно из файлов.
5. **Человек утверждает необратимое.** Цель продукта, архитектура, удаление функциональности. Всё остальное ИИ решает сам и записывает.

## 1. Участники и их роли

| Участник | Что делает | Чего не делает | На что опирается |
|---|---|---|---|
| **Человек (владелец)** | Формулирует цель продукта, утверждает необратимые решения, отвечает на вопросы из `QUESTIONS.md`, следит за табло, решает судьбу застрявших блоков (6.6) | Не пишет и не читает код | `state/STATUS.md`, PR с пометкой «нужно решение владельца» |
| **Claude Project (планировщик)** | Держит цель, разбивает её на блоки, пишет спецификации и критерии приёмки, следит за прогрессом и связностью блоков, решает, что делать с заблокированными блоками | Не пишет код, не сливает PR, **не пишет в репозиторий сам** — его решения попадают туда через исполнителя (раздел 4) | Снимок репозитория в знаниях Project, синхронизированный перед сессией (раздел 4) |
| **Claude Code / Cursor (исполнитель)** | Реализует одну задачу за сессию: тесты, код, проверки, PR; оформляет решения планировщика как PR только с документами | Не меняет цель, архитектуру и критерии приёмки сам; не правит тесты, CI и защитные файлы | Спецификация задачи и протокол чтения (раздел 4) |
| **CI (судья)** | Решает, принят ли PR; считает состояние проекта (`features.json`, `STATUS.md`), в том числе число инцидентов на блок и минуты CI за цикл | Не делает первым то, что уже сделал hook; не работает на платных раннерах без ADR (7.2) | Код и тесты |
| **Роли-агенты внутри исполнителя** | architect (план), tester (тесты), implementer (код), reviewer (ревью в чистом контексте), janitor (уборка), explorer (поиск) | Каждая роль — только своё | Права ролей задают hooks |

Ключевая идея: **планировщик и исполнитель разделены**. Тот, кто пишет код, не решает, что именно нужно сделать. Тот, кто решает, не пишет код. Так исполнитель не может «упростить» задачу под то, что у него получилось.

## 2. Структура проекта: файлы и папки

```
AGENTS.md                  # ≤150 строк, пишет человек (или утверждает): как собрать, как проверить, главные запреты, ссылки
CLAUDE.md                  # @AGENTS.md + специфика Claude Code
.cursor/rules/parch.mdc    # если используется Cursor: только ссылка на AGENTS.md, без своих правил
.claude/settings.json      # permissions (из шаблона)
docs/
  GOAL.md                  # цель продукта: что это, для кого, критерии готовности продукта (G1, G2...), что НЕ входит
  CONSTITUTION.md          # стек, разрешённые пакеты, пороги проверок, классы обратимых/необратимых решений, бюджеты (6.1, 6.6), целевая ОС и бюджет CI (7.2)
  PROJECT_INSTRUCTIONS.md  # канонический текст инструкций Claude Project (версионируется здесь)
  WORKFLOW.md              # конвейер и правила сбоев этого проекта (из шаблона, раздел 5–6)
  adr/                     # решения; README.md — индекс; принятые правятся только заменой
  MODULES.md               # реестр модулей: назначение, какие блоки и цели обслуживает, статус
  INTERFACES.md            # межъязыковые и межмодульные швы, со ссылками на контрактные тесты
  LESSONS.md               # ≤50 строк: неочевидные уроки, каждый со ссылкой на регрессионный тест
  QUESTIONS.md             # открытые вопросы к владельцу; ИИ пишет сюда вместо предположений
  specs/<id>-<name>.md     # спецификация блока; после завершения — specs/archive/
state/
  features.json            # блоки (раздел 3); поля passes и incidents пишет только CI
  STATUS.md                # табло, генерирует CI
  baseline.json            # храповик
  incidents/<дата>-<блок>-<тип>.md # отчёты о петлях, блокерах и откатах (раздел 6); блок в имени обязателен
```

**Правила структуры** (все проверяются автоматически):
- Планы и заметки живут только в `docs/specs/` и `state/incidents/`. Новый `.md` в другом месте блокирует hook.
- Инструкции для ИИ живут только в `AGENTS.md` и `CLAUDE.md`. Если в проекте найдены другие файлы с инструкциями (`.cursorrules`, `INSTRUCTIONS.md`, `prompts/` с противоречащими правилами), это нарушение стандарта: конкурирующие инструкции — одна из главных причин, по которым ИИ «теряет нить».
- Инструкции Claude Project не живут только в настройках Claude: канонический текст лежит в `docs/PROJECT_INSTRUCTIONS.md`. В самих настройках Project — короткий текст со ссылкой на репозиторий. Так инструкции версионируются, проверяются и не расходятся с проектом.
- Имя файла инцидента содержит идентификатор блока (`2026-10-14-F9-loop.md`): по нему CI считает инциденты на блок (раздел 6.6).

## 3. Цель и прослеживаемость: как каждый следит за конечной целью

### Цепочка прослеживаемости

```
GOAL.md (критерии G1..Gn)  →  features.json (блоки F1..Fm, у каждого goal: [G..])
      →  specs/F*.md (критерии приёмки)  →  тесты приёмки  →  модули в MODULES.md (у каждого features: [F..])
```

Запись блока в `state/features.json`:

```json
{
  "id": "F7",
  "title": "Импорт таблицы пациентов",
  "goal": ["G2"],
  "depends_on": ["F3"],
  "spec": "docs/specs/F7-import.md",
  "acceptance_tests": ["tests/acceptance/test_import.py"],
  "status": "planned | in_progress | blocked | stuck | done | dropped",
  "passes": false,
  "incidents": 0
}
```

`passes` ставит только CI по результату реальных тестов приёмки. `incidents` считает только CI по файлам в `state/incidents/` с этим блоком в имени. `status` меняет планировщик, кроме трёх значений: `done` ставит CI, когда `passes` истинно; `stuck` ставит CI, когда `incidents` достигает бюджета (6.6); снять `stuck` может только решение человека.

### Автоматические проверки связности

- **Блок без цели** (`goal` пуст или ссылается на несуществующий G) — нарушение: это расползание объёма. Это относится и к блокам, которые планировщик заводит для исправления ошибок: исправление без привязки к критерию цели не заводится как блок.
- **Модуль без блока** в `MODULES.md` — кандидат на удаление (или на статус `keep-until: дата` по решению владельца).
- **Блок без тестов приёмки** не может стать `done`.
- **Зависимость на невыполненный блок**: блок не может быть `done`, пока не `done` все блоки из `depends_on`.
- **Цикл зависимостей** между блоками — провал.
- **Блок `stuck` не получает новых задач**: PR, ссылающийся на блок в статусе `stuck`, CI не принимает, пока статус не изменён решением человека.

### Кто и как следит за целью

| Участник | Что смотрит | Как часто |
|---|---|---|
| Человек | `STATUS.md`: для каждой цели G — сколько её блоков готово (по реальным тестам), что заблокировано, что застряло, какие решения ждут его | Когда хочет; минимум после каждой крупной вехи |
| Claude Project | `features.json` и `STATUS.md` целиком: прогресс по целям, блокеры, число инцидентов, следующая задача, нет ли блоков, оторванных от цели | В начале каждой сессии планирования |
| Claude Code | Только свою задачу: спецификацию, её связь с целью (поле `goal`), записи нужных модулей | В начале каждой сессии |
| CI | Пересчитывает `passes`, `incidents`, `done`, `stuck` и табло по реальным тестам и файлам инцидентов | На каждом PR и после каждого слияния |

Прогресс продукта считается не по словам агентов, а по формуле: **доля критериев цели, у которых все блоки прошли тесты приёмки**. Оговорка, которую стандарт не скрывает: тесты приёмки пишет ИИ (роль tester), и CI проверяет только, что они проходят, а не что они проверяют нужное. Защита от слабых тестов — ревью в чистом контексте и запрет исполнителю править тесты — частичная (раздел 12).

## 4. Откуда ИИ знает проект: источники знаний и протокол перед решением

### Иерархия источников (при противоречии побеждает верхний)

1. **Код и результаты тестов** — то, что реально есть.
2. **Принятые ADR и `CONSTITUTION.md`** — то, что решено.
3. **`features.json`, `MODULES.md`, `INTERFACES.md`** — карта проекта.
4. **Спецификация задачи** — что нужно сделать сейчас.
5. **`LESSONS.md` и `state/incidents/`** — что уже пробовали и что не работает.
6. Память модели и содержимое чата — **не источник**. Если информация есть только там, её нужно сначала записать в файл.

### Протокол исполнителя перед решением

Перед тем как писать код, исполнитель обязан (это зашито в инструкцию роли и в шаблон описания PR):

1. Прочитать спецификацию задачи и её связь с целью.
2. Найти в `MODULES.md` модули, которых касается задача, и прочитать их записи.
3. **Найти существующую реализацию**: поиск по символам и тексту в коде. Если похожее уже есть — переиспользовать или расширить, а не писать заново.
4. Прочитать ADR, относящиеся к затрагиваемым модулям.
5. Проверить `LESSONS.md` и `state/incidents/` на эту область.
6. Посмотреть историю: `git log` по затрагиваемым файлам — не решалась ли эта задача раньше и не откатывалась ли.
7. Если чего-то не хватает для решения — записать вопрос в `QUESTIONS.md` и остановиться, а не предполагать.

В описании PR есть обязательный раздел **«Основания»**: на какие файлы, ADR и найденный код опирается решение, и какая существующая реализация была проверена. Пустой раздел — PR не принимается (проверка CI).

### Протокол планировщика (Claude Project)

Главная опасность для Claude Project — **устаревшие знания**, и стандарт исходит из того, как подключение GitHub к Project устроено на самом деле, а не как хотелось бы:

- Подключение GitHub к знаниям Project — это **снимок файлов одной ветки**, без истории коммитов и без PR. Снимок обновляется только кнопкой «Sync». Писать в репозиторий через это подключение нельзя. Приватные репозитории подключаются, если приложению Claude дан доступ к ним.
- Поэтому **первое правило сессии планирования — синхронизация**: перед тем как планировщик принимает хоть одно решение, владелец нажимает «Sync». Это правило держится на человеке (канал «человек», раздел 12), и стандарт делает его дешёвым: в `STATUS.md` указан коммит, на котором он построен, и планировщик начинает каждую сессию с фразы «я вижу состояние на коммите X от даты Y», чтобы владелец мог заметить, что снимок старый.
- В знания Project загружаются только стабильные документы (`GOAL.md`, `CONSTITUTION.md`, `WORKFLOW.md`) и живое состояние (`features.json`, `STATUS.md`, `MODULES.md`, `QUESTIONS.md`, `state/incidents/`). Открытые PR планировщик не видит; всё, что он должен о них знать, CI пишет в `STATUS.md` (раздел «В работе»).
- **Планировщик не пишет в репозиторий.** Каждое его решение (новый блок, перенос, отказ, изменение спецификации) оформляется как **задание на обновление плана** — короткий текст с точным содержимым изменений в `features.json` и спецификациях. Это задание исполнитель превращает в PR только с документами. Как именно текст задания попадает от Project к исполнителю — открытый вопрос реализации (раздел 13); до его решения владелец передаёт текст сам.
- Решение, оставшееся только в чате и не дошедшее до репозитория, считается не принятым.

## 5. Конвейер: порядок работы в нормальном случае

1. **Цель.** Человек формулирует или меняет цель → `GOAL.md` (необратимое: только с его утверждения).
2. **Планирование.** Владелец синхронизирует знания Project. Claude Project по `GOAL.md` и текущему состоянию выбирает следующий блок, пишет спецификацию с критериями приёмки и задание на обновление плана. Исполнитель оформляет его как PR только с документами. Если в нём есть необратимое решение (новая архитектура, новый язык, новый крупный модуль), PR ждёт человека.
3. **Тесты приёмки.** Роль tester пишет тесты приёмки по спецификации до кода. Они должны падать.
4. **Реализация.** Claude Code в отдельной ветке: протокол чтения (раздел 4) → код → локальные проверки hook'ом (те же ворота, что в CI, бесплатно и до push) → ревью субагентом в чистом контексте (локально, только корректность и соответствие спецификации) → PR с разделами «Что сделано», «Основания», «Как проверено».
5. **Проверка.** CI повторяет ворота на PR (раздел 7.2: Linux, с таймаутом, старый прогон отменяется новым push). PR только с документами проходит лёгкой проверкой структуры без тестов.
6. **Слияние.** Автоматически для обычных PR; через человека для PR, меняющих защитные механизмы, конфигурацию CI или содержащих необратимые решения.
7. **Обновление состояния.** CI пересчитывает `features.json` и `STATUS.md` отдельной маленькой работой, без повторного прогона тестов: они уже прошли на том же коммите в PR.
8. **Обратная связь.** Claude Project в следующей сессии (после синхронизации) видит новое состояние и выбирает следующий блок.

Правило размера: **один блок — одна сессия — один PR**. Блок, который не помещается в одну сессию, планировщик дробит.

## 6. Что делать, когда что-то идёт не так

Для каждого типа сбоя — свой сигнал, свой порядок действий и своя граница, после которой решение переходит выше. Границы устроены лестницей: сессия → блок → человек. На каждой ступени свой бюджет, и ни одна ступень не может крутиться бесконечно.

### 6.1. Проблема: проверка не проходит

Обычная работа. Исполнитель исправляет в рамках сессии. **Бюджет: 3 попытки на одну и ту же ошибку.** Ошибка считается той же, если совпадает её «подпись» (проверка + файл + текст ошибки). После трёх попыток — это петля (6.3).

Прежде чем чинить, исполнитель задаёт один вопрос: **роняет ли эта ошибка тесты приёмки блока?** Если нет — она не мешает блоку стать `done`, и исправление не является частью задачи. Ошибка, которая не задевает тесты приёмки, но блокирует PR (ворота CI: сложность, дублирование, покрытие), идёт по правилу храповика: исключение из метрики — решение владельца, а не повод чинить до бесконечности.

### 6.2. Ошибка: дефект обнаружен после слияния

1. **Сначала откат, потом разбор.** Слитый PR откатывается (`git revert`) отдельным PR, чтобы `main` снова был рабочим.
2. Пишется регрессионный тест, который воспроизводит дефект и падает.
3. В `LESSONS.md` — одна строка: что было неочевидно, со ссылкой на тест.
4. Блок возвращается в `in_progress`, исправление идёт обычным конвейером.
5. Отчёт в `state/incidents/` с идентификатором блока в имени: он входит в бюджет блока (6.6).

### 6.3. Петля: проблема не решается несколько итераций

Признаки петли (отслеживаются автоматически, hook `stop_gate` и журнал аудита):
- одна и та же подпись ошибки 3 раза подряд;
- один и тот же файл правится туда-обратно (изменение и его отмена);
- сессия превысила бюджет попыток или времени.

Порядок действий:
1. **Стоп.** Hook запрещает продолжать в этой сессии.
2. **Отчёт о петле** в `state/incidents/`: что пробовали, какие гипотезы, что не сработало, вывод проверок — и обязательный раздел **«Влияние на цель»** (6.5a).
3. **Поиск в истории** — главное, что ИИ обычно забывает сделать: не решалась ли эта проблема раньше (`git log -S`, закрытые PR, `LESSONS.md`, прошлые отчёты в `state/incidents/`). Частая причина петли — ИИ не видит, что проблема уже была решена, и ходит по кругу.
4. **Новая сессия с чистым контекстом.** Ей дают только спецификацию, отчёт о петле и результаты поиска в истории, без старого переполненного контекста. Потерянная нить проекта почти всегда означает переполненный или загрязнённый контекст.
5. Если и вторая сессия упёрлась в петлю — **эскалация к планировщику** (6.6). Планировщик не получает права на бесконечные попытки: у блока есть свой бюджет.

### 6.4. Блок невозможно реализовать в принципе

1. Исполнитель не «упрощает задачу» молча и не делает заглушку. Он пишет **отчёт-блокер**: почему невозможно, какие доказательства (документация, результаты проб), какие есть альтернативы и чем каждая хуже, и раздел «Влияние на цель» (6.5a).
2. Блок получает статус `blocked`.
3. Планировщик решает: альтернативный подход (ADR), изменение спецификации, перенос или отказ (`dropped`).
4. Если отказ затрагивает критерий цели в `GOAL.md` — решение принимает человек.

### 6.5. Нужно изменить архитектуру, цель модуля или цель проекта

Изменение никогда не делается «по ходу» внутри обычной задачи. Оно оформляется как **запрос на изменение**:

| Что меняется | Как оформляется | Кто утверждает |
|---|---|---|
| Архитектура (структура модулей, связи, технологии) | ADR `proposed` + анализ влияния | Человек |
| Цель или граница модуля | Изменение записи в `MODULES.md` и спецификаций затронутых блоков | Планировщик, если цели продукта не задеты |
| Цель продукта | Изменение `GOAL.md` | Только человек |
| Конфигурация CI: раннеры, матрицы ОС, триггеры, таймауты | ADR `proposed` с оценкой минут квоты и денег за один прогон (7.2) | Человек |

Конфигурация CI стоит в этой таблице не потому, что её трудно откатить, а потому, что её цена проявляется только счётом в конце месяца: это необратимость по деньгам, а не по коду. Исполнитель не добавляет раннер или ОС «на всякий случай».

**Анализ влияния** строится по цепочке прослеживаемости (раздел 3): какие блоки, модули, тесты и интерфейсы затронуты. До утверждения код не пишется. После утверждения изменения идут обычными блоками.

### 6.5a. Раздел «Влияние на цель» — обязателен в каждом отчёте об инциденте

Каждый отчёт о петле, блокере или откате содержит раздел «Влияние на цель» с тремя ответами:

1. **Какой критерий цели** (G из `GOAL.md`) не будет выполнен, если этот блок бросить сейчас. Если ни один — так и пишется: «ни один», и это главный вывод отчёта.
2. **Есть ли обходной путь**: другой способ закрыть тот же критерий цели без этой задачи.
3. **Сколько уже потрачено**: число инцидентов по блоку и число сессий.

Пустой или формальный раздел — отчёт не принимается (проверка CI: раздел есть, в нём есть ссылка на G или слово «ни один»). Смысл правила: прежде чем кто-либо решает, *как* починить, из файла должно быть видно, *нужно ли* чинить.

### 6.6. Застрявший блок: защита от петли планировщика

Петлю исполнителя останавливают 6.1 и 6.3. Но планировщик может крутить ту же петлю на уровень выше: ошибка → подзадача «исправить» → не удалось → новая подзадача → и так без конца, при том что исправляемое, возможно, вовсе не нужно продукту. Этот раздел закрывает именно эту дыру.

**Бюджет блока.** В `CONSTITUTION.md` задан бюджет инцидентов на блок (по умолчанию **2**). CI считает инциденты по файлам `state/incidents/<дата>-<блок>-*.md` и пишет число в `features.json` (`incidents`). Счётчик привязан к блоку, а не к сессии и не к подзадаче: дробление и переформулировка блока планировщиком счётчик **не обнуляют** — новые подблоки наследуют инциденты родителя.

**Статус `stuck`.** Когда `incidents` достигает бюджета, CI ставит блоку статус `stuck`. С этого момента:
- планировщик не заводит по этому блоку новых задач и подзадач — PR, ссылающийся на блок `stuck`, CI не принимает;
- блок попадает в `STATUS.md` в раздел «Нужно ваше решение» с карточкой решения (ниже);
- снять `stuck` может только решение человека, записанное в репозиторий (изменение `status` в PR с пометкой «решение владельца»).

**Протокол планировщика при эскалации.** Это инструкция роли (её нельзя проверить, поэтому она в 40 строках планировщика): получив отчёт о петле или блокере, планировщик **сначала** перечитывает поле `goal` блока и соответствующие критерии в `GOAL.md` и отвечает на вопрос «что сломается, если этого не делать», и только **потом** думает, как чинить. Если ответ «ничего» — он предлагает отказ от блока, а не новую попытку. Если есть обходной путь — предлагает его. Новая попытка — последний вариант, не первый.

**Карточка решения для человека.** Для каждого блока `stuck` CI формирует в `STATUS.md` карточку из отчётов об инцидентах, всегда с тремя вариантами, чтобы владелец мог ответить одним словом, не читая код:

```markdown
### F9 «Выгрузка в PDF» застрял: 2 инцидента, 3 сессии
Нужен для: G2 «Отчёты» (критерий G2.3). Без него G2 не закроется.
Обходной путь (из отчёта 2026-10-14-F9-loop.md): выгружать в Word, PDF делать из него.
Ваши варианты:
  1. Отказаться — G2.3 помечается как не выполняемый (нужно ваше «да», это изменение цели)
  2. Обходной путь — планировщик заводит блок «экспорт в Word», F9 закрывается через него
  3. Продолжать — одна новая попытка с другим подходом (отчёт обязан назвать, чем он другой)
```

Ответ владельца записывает исполнитель: статус блока, при варианте 1 — изменение `GOAL.md`, при варианте 2 — новый блок с `goal` родителя, при варианте 3 — бюджет блока поднимается на 1, и это решение фиксируется в отчёте. Второй раз вариант 3 для того же блока предлагается только вместе с ADR об изменении подхода.

**Почему именно так.** Исправление ошибки — это обычно обратимое решение, и по принципу 5 его должен принимать ИИ. Но после двух инцидентов цена вопроса уже выше, чем минута внимания владельца, а ИИ в этой точке систематически переоценивает нужность задачи, которую пытается спасти. Поэтому граница проходит по цене, а не по обратимости.

## 7. Синхронизация: где что хранится и как участники видят одно и то же

| Место | Роль | Источник истины? |
|---|---|---|
| **Git-репозиторий (GitHub)** | Всё: цель, решения, план, состояние, код | **Да, единственный** |
| **GitHub PR** | Единица изменения и журнал аудита: что, кем, зачем, с какой проверкой | Часть репозитория |
| **CI (GitHub Actions)** | Считает состояние: `passes`, `incidents`, `done`, `stuck`, `STATUS.md` | Вычисляет, не хранит |
| **Claude Project** | Пульт планирования; видит снимок репозитория, синхронизированный перед сессией (раздел 4) | Нет |
| **Claude Code / Cursor** | Исполнитель; локальная копия репозитория; единственный, кто пишет в репозиторий от имени ИИ | Нет |
| **Плагин ProjectArchitect** | Инструменты (hooks, проверки, команды), не хранилище | Нет |

Правило: **если две копии расходятся, права репозитория.** Внешние трекеры задач (Jira и подобные) стандартом не используются: второй список задач рядом с `features.json` — гарантированный источник рассинхрона. Человек видит и меняет план через табло прогресса (раздел 7.1).

### 7.1. Табло прогресса для человека

Человеку нужен простой визуальный инструмент: что сделано, что предстоит, что застряло, и возможность поменять планы. Стандарт решает это так, чтобы не появился второй источник истины.

**Смотреть.** Файл `state/STATUS.md` генерирует CI после каждого слияния. GitHub показывает его как обычную страницу, в том числе с телефона. Вверху — одна строка итога, затем раздел «Нужно ваше решение», затем таблица по целям и блокам, затем диаграмма:

```markdown
# Прогресс: 7 из 12 блоков готово · цель G1 готова · G2 — 3 из 6 · G3 не начата
Обновлено: 2026-10-14, коммит a1b2c3d

## Нужно ваше решение
- ADR-0012 «Перейти на SQLite» — ждёт утверждения
- F9 застрял (2 инцидента) — карточка решения ниже
- F4 заблокирован: внешний сервис не даёт выгрузку (отчёт в state/incidents/)

### F9 «Выгрузка в PDF» застрял: 2 инцидента, 3 сессии
Нужен для: G2 «Отчёты» (критерий G2.3). Без него G2 не закроется.
Обходной путь: выгружать в Word, PDF делать из него.
Ваши варианты: 1. Отказаться · 2. Обходной путь · 3. Продолжать (новый подход)

## В работе
- F7 «Таблица по пациентам» — PR #41 открыт, CI зелёный, ждёт ревью

## План
| Цель | Блок | Что это | Статус | Зависит от | Инциденты |
|---|---|---|---|---|---|
| G1 Импорт данных | F1 | Чтение Excel | ✅ готово | — | 0 |
| G2 Отчёты | F7 | Таблица по пациентам | 🔨 в работе | F3 | 0 |
| G2 Отчёты | F9 | Выгрузка в PDF | 🛑 застрял | F7 | 2 |
| G2 Отчёты | F4 | Выгрузка из сервиса | ⛔ заблокирован | — | 1 |
| G3 Статистика | F11 | Графики | ⏳ впереди | F7 | 0 |
```

Ниже таблицы — диаграмма блоков и зависимостей (Mermaid; GitHub рисует её прямо на странице), блоки раскрашены по статусу. Статус «готово» берётся из тестов приёмки, а не из слов агента (с оговоркой раздела 3 о том, кто пишет тесты).

**Менять.** Человек не редактирует файлы руками. Он говорит Claude Project обычными словами: «перенеси выгрузку в PDF в конец», «добавь блок: экспорт в Word», «статистику пока не делаем», «по F9 — вариант 2». Планировщик формирует задание на обновление плана, исполнитель оформляет его как PR только с документами, табло обновляется после слияния. Изменения, затрагивающие цель (`GOAL.md`) или отказ от критерия цели, ждут явного «да» человека, и PR с ними сливает человек (одна кнопка на GitHub, читать код для этого не нужно).

Табло построено только из `features.json`, `GOAL.md`, результатов CI и `state/incidents/`. Своих данных у него нет, поэтому оно не может разойтись с проектом.

Под строкой итога табло показывает расход CI: «CI за цикл: 412 из 3 000 минут квоты · этот блок: 38 минут». Число берётся из GitHub API. Рост расхода на блок — такой же сигнал, как рост сложности: петлю, которую не поймал `stop_gate`, обычно видно по минутам раньше, чем по чему-либо ещё.

### 7.2. Стоимость CI

CI в этом стандарте — судья, и судья платный. GitHub Actions даёт на бесплатном плане 2 000, на Pro — 3 000 минут в месяц для приватных репозиториев, а дальше берёт деньги или останавливает CI до начала следующего цикла. Минуты считаются с множителем по ОС: Linux ×1, Windows ×2, macOS ×10. Публичные репозитории минут не тратят.

Стандарт исходит из того, что проект ведёт ИИ, а ИИ при любой неясности делает «побольше на всякий случай»: три ОС вместо одной, запуск на каждый push вместо PR, без таймаута. Так за один вечер уходит месячная квота. Поэтому следующие правила — не оптимизация, а защита, и у каждого есть канал (раздел 12).

**Правила** (шаблон CI создаётся с ними, проверка `standard` их сторожит):

1. **Linux по умолчанию, и только он.** Один job на `ubuntu-latest`. Другая ОС или матрица — только через ADR с оценкой «минут квоты и денег за один прогон» (6.5). `dotnet`, `pwsh` с PSScriptAnalyzer, Node и Python одинаково работают на Ubuntu; «продукт для Windows» сам по себе не причина для Windows-раннера.
2. **Целевая ОС проверяется там, где исполнитель и так работает.** Если проект разрабатывается на Windows, Claude Code запускает тесты на Windows при каждой сессии бесплатно; Linux-job в CI тогда проверяет не «то же самое ещё раз», а обратное — что в код не пролезло ничего Windows-специфичного (пути, кодировки, `cmd` вместо `sh`). Целевая ОС записана в `CONSTITUTION.md`. Если какие-то тесты можно выполнить только на целевой ОС (запускающие файлы, права), это отдельный маленький job на ней: только эти тесты, `timeout-minutes: 15`, запуск только когда PR меняет соответствующие пути.
3. **Hook первый, CI второй.** Всё, что ловит CI, сначала ловит hook на машине исполнителя до push: lint, формат, сложность, дублирование, unit-тесты, проверка `standard`, детектор петли. CI повторяет это, чтобы результату можно было верить, и ничего не делает первым. Ревью в чистом контексте — локальный субагент, не CI.
4. **`timeout-minutes` на каждом job**, 10–20 минут. Это самое важное правило: по умолчанию GitHub ждёт 360 минут, и один повисший тест из ИИ-кода стоит шесть часов квоты. Таймаут срабатывает чаще, чем кажется, и это нормально — он ловит именно те зависания, которые не поймал детектор петли.
5. **`concurrency` с `cancel-in-progress: true`** по ветке: новый push отменяет старый прогон. Исполнитель коммитит часто; без этого правила три попытки из бюджета 6.1 — это три полных параллельных прогона.
6. **Запуск только на `pull_request`.** Не на каждый push и не на push в `main` после слияния: тесты на этом коммите уже прошли в PR. После слияния идёт только пересчёт состояния (`features.json`, `STATUS.md`) — отдельный job без тестов, минута-две.
7. **PR только с документами** (`docs/`, `state/`) проходит лёгкой проверкой структуры без тестов. Таких PR у планировщика — все.
8. **Кэш зависимостей** в шаблоне: установка SDK и модулей не должна занимать половину прогона.
9. **Бюджет на Actions в GitHub** — действие владельца, не ИИ: небольшой, не нулевой (например, $5). Нулевой бюджет останавливает CI посреди работы без предупреждения; отсутствие бюджета означает, что об ошибке конфигурации владелец узнаёт из счёта. `/parch:init-project` говорит владельцу об этом прямо, одной фразой, с ссылкой на страницу бюджетов.
10. **Минуты за цикл и за блок — на табло** (7.1) и под храповиком: расход CI на блок не растёт без решения владельца.

**Когда CI остановился** (кончилась квота, сработал нулевой бюджет, GitHub недоступен): ничего не сливается и ничего не становится `done`, потому что `passes` ставит только CI. Табло в этом случае тоже не обновляется — его генерирует тот же CI, — поэтому о проблеме владелец узнаёт из письма GitHub, а не из `STATUS.md`. Стандарт честно записывает это как ещё одно место, которое держится на человеке (раздел 12). Исполнитель при недоступном CI не обходит его (локальный «зелёный» не заменяет судью), а пишет владельцу одной строкой и останавливается.

**Что не делается правилом, но называется.** Публичный репозиторий — минуты бесплатны вообще; подходит для проектов без чувствительных данных, и это решение владельца. Self-hosted раннер на машине владельца — тоже бесплатно, но машина должна быть включена, и это лишняя подвижная часть для непрограммиста.

## 8. Качество кода: сопровождаемость по ISO/IEC 25010 и сложность

Оценка строится на модели качества ISO/IEC 25010, характеристика **сопровождаемость** (maintainability), плюс отдельная строка **сложность**. Формулировка в отчётах — «оценка по модели ISO/IEC 25010», без заявления о формальном соответствии: формальное соответствие требует сертификации.

| Подхарактеристика | Что значит | Метрики | Инструменты (Python / TypeScript / C#) |
|---|---|---|---|
| **Модульность** | Изменение в одном модуле минимально задевает другие | Нарушения архитектурных правил; циклические зависимости; доля модулей, описанных в `MODULES.md` | import-linter / dependency-cruiser / ArchUnitNET |
| **Переиспользуемость** | Общее вынесено и используется, а не копируется | Дублирование кода; модули с одинаковым назначением в `MODULES.md` | jscpd (все языки) |
| **Анализируемость** | Насколько легко понять код и найти причину проблемы | Сложность функций (раздел ниже); размер функций и файлов; подавления предупреждений | ruff / Biome / Roslyn-анализаторы |
| **Изменяемость** | Изменения вносятся без новых дефектов | Связанность модулей (сколько модулей зависит от данного и от скольких зависит он); «горячие точки» — большие часто меняемые файлы без тестов | граф зависимостей тех же инструментов; история git |
| **Тестируемость** | Насколько легко проверить, что код работает | Покрытие; число тестов и его динамика; пропущенные тесты; блоки без тестов приёмки | pytest+coverage / Vitest / dotnet test+coverlet |
| **Сложность** | Отдельная строка, главный враг ИИ-кода | Цикломатическая сложность (число путей через функцию) и когнитивная сложность (насколько трудно её прочитать человеку); глубина вложенности | ruff (правило C901) / Biome (правило когнитивной сложности) / Roslyn (метрики кода) — точные правила Claude Code сверяет с документацией |

PowerShell оценивается только проверкой «тонкости» (ADR-0010).

### Две шкалы

- **Абсолютная** — только для первой оценки чужого проекта: рейтинг каждой подхарактеристики от 1 до 5 по ориентирам модели SIG и SonarQube. Отвечает на вопрос «насколько всё плохо».
- **Относительная (храповик)** — главная в повседневной работе. Ни одна метрика не может ухудшиться без решения владельца. Отвечает на вопрос «стало лучше или хуже».

## 9. Аудит ИИ-процесса: что проверяется в существующем проекте

Помимо кода `/parch:analyze-existing` проверяет, как организован сам процесс. Каждый пункт получает оценку: **отсутствует / частично / по стандарту**.

| № | Проверка | Как определяется |
|---|---|---|
| P1 | Цель продукта записана и имеет проверяемые критерии | Есть ли `GOAL.md` или его аналог; есть ли критерии, а не только описание |
| P2 | Прослеживаемость цель → блоки → тесты → модули | Есть ли план блоков; связаны ли модули с блоками; доля модулей без назначения |
| P3 | Инструкции для ИИ: одно место, короткие, без противоречий | Все файлы с инструкциями (`CLAUDE.md`, `AGENTS.md`, `.cursorrules`, `.cursor/rules`, промпты в репозитории); их размер; поиск противоречий между ними |
| P4 | Инструкции Claude Project версионируются | Есть ли канонический текст в репозитории; совпадает ли он с тем, что владелец показывает из настроек Project |
| P5 | Расползание планов и заметок | Число `.md` вне `docs/`; устаревшие планы, на которые ничто не ссылается |
| P6 | Решения записаны | Есть ли ADR или аналог; восстановимы ли ключевые решения из файлов |
| P7 | Защита от ложного «готово» | Есть ли hooks, CI с обязательными проверками, защищённая ветка; может ли агент править тесты |
| P8 | Источник истины один | Где живёт состояние: репозиторий, внешние трекеры, чаты, файлы на диске; есть ли расхождения |
| P9 | Протокол перед решением | Есть ли в инструкциях требование искать существующий код и опираться на файлы |
| P10 | Обработка сбоев | Есть ли правила для петель, блокеров, откатов; есть ли история инцидентов; есть ли бюджет на блок, а не только на сессию |
| P11 | Повторение ошибок | Есть ли `LESSONS.md` с тестами; есть ли признаки повторно исправленных одних и тех же дефектов в истории git; есть ли блоки с длинной серией попыток без вопроса о их нужности |
| P12 | Взаимодействие человек — Project — исполнитель | Описано ли, кто что решает и через что передаёт; есть ли решения, которые существуют только в чатах |
| P13 | Стоимость CI | Раннеры и матрицы в workflow; есть ли таймауты и отмена прогонов; на какие события запускается; есть ли ADR под каждый не-Linux раннер; расход минут за последний цикл (GitHub API) |

Часть пунктов (P4, P8, P12) требует информации, которой нет в репозитории. Их анализ оформляет как вопросы владельцу в `QUESTIONS.md`, а не угадывает.

## 10. Применение стандарта

### Новый проект

`/parch:init-project` создаёт всю структуру раздела 2. Самый важный шаг — разговор с владельцем о цели: агент задаёт вопросы и составляет `GOAL.md` с критериями, владелец утверждает. Без утверждённой цели планирование не начинается. Второй вопрос владельцу — целевая ОС проекта (на ней работает исполнитель, она идёт в `CONSTITUTION.md`); CI при этом всё равно Linux (7.2). Затем: `CONSTITUTION.md` (включая бюджеты 6.1 и 6.6), шаблоны, CI под языки с таймаутом и отменой прогонов, одна фраза владельцу про бюджет на Actions, `docs/PROJECT_INSTRUCTIONS.md` — готовый текст для настроек Claude Project, в котором первой строкой стоит протокол синхронизации (раздел 4) и протокол эскалации (6.6).

### Существующий проект

1. **Аудит** (`/parch:analyze-existing`, только чтение): код по разделу 8, процесс по разделу 9, карта модулей и швов, восстановленные ADR, вопросы.
2. **Отчёт о разрыве** — на русском, без кода: что соответствует стандарту, что частично, чего нет; главные риски.
3. **План приведения к стандарту** — последовательность небольших PR, от безопасных к рискованным: сначала документы и структура (`GOAL.md`, реестры, инструкции), потом CI в режиме храповика, потом уборка и рефакторинг.
4. **Владелец утверждает** `GOAL.md`, восстановленные ADR и план.
5. **ИИ выполняет план** обычным конвейером. Код меняется только после того, как утверждены цель и решения. Устаревшие конкурирующие инструкции и планы не удаляются, а переносятся в архив с указанием, чем они заменены.

## 11. Проверка соответствия стандарту

Соответствие проверяется командой и в CI, а не вручную:

- **Проверка `standard` в CI:** обязательные файлы на месте; `features.json` и `MODULES.md` разбираются и связаны (раздел 3); нет конкурирующих файлов инструкций; нет `.md` вне разрешённых мест; у PR заполнен раздел «Основания»; у каждого отчёта в `state/incidents/` в имени есть блок и заполнен раздел «Влияние на цель» (6.5a); `incidents` в `features.json` совпадает с числом файлов инцидентов; блок с `incidents ≥ бюджет` имеет статус `stuck`; нет PR по блокам `stuck`; у каждого job в workflow есть `timeout-minutes`, у workflow — `concurrency` с отменой, запуск только на `pull_request` (плюс пересчёт состояния после слияния), и каждый раннер кроме `ubuntu-latest` упомянут в принятом ADR (7.2).
- **Карточка соответствия в `STATUS.md`:** пункты P1–P12 и подхарактеристики раздела 8 с текущей оценкой и динамикой.
- **Версия стандарта** указывается в `CONSTITUTION.md`. При выходе новой версии стандарта `/parch:analyze-existing` показывает, что изменилось и что нужно доделать.

## 12. Как стандарт доходит до ИИ, чтобы ИИ в нём не запутался

Если бы ИИ читал этот документ в каждой сессии и пытался помнить все правила, он бы в нём запутался: длинные инструкции модели выполняют хуже коротких, а правило, которое нужно помнить, рано или поздно забывается. Следующим шагом понадобился бы «стандарт соблюдения стандарта», и так далее. Поэтому стандарт устроен иначе: **ИИ не нужно знать стандарт, чтобы его соблюдать.**

### Четыре канала, и только они

| Канал | Как работает | Что требует от ИИ | Примеры |
|---|---|---|---|
| **Шаблон** | Структура создаётся сразу правильной | Ничего | Папки, `GOAL.md`, `features.json`, `MODULES.md`, CI (Linux, таймаут, отмена прогонов, только PR), шаблон отчёта об инциденте с разделом «Влияние на цель» |
| **Проверка** (hook или CI) | Нарушение останавливается с точным сообщением, что не так и как исправить | Прочитать сообщение об ошибке | `.md` вне `docs/`, блок без цели, правка тестов, рост сложности, петля из трёх одинаковых ошибок, пустой раздел «Основания», пустой раздел «Влияние на цель», бюджет инцидентов блока, PR по блоку `stuck`, раннер или матрица без ADR, job без таймаута |
| **Инструкция роли** | Короткий текст роли агента: только то, что нельзя проверить | Прочитать 20–40 строк своей роли | Протокол перед решением; что делать при блокере; при недоступном CI — остановиться, не обходить; для планировщика — «сначала что сломается, потом как чинить» (6.6) |
| **Человек** | Решает то, что нельзя доверить ИИ | — | Цель продукта, необратимые решения, судьба застрявших блоков, синхронизация знаний Project перед сессией, бюджет на Actions в GitHub |

### Правила, которые не дают стандарту разрастись

1. **У каждого правила стандарта есть канал.** Правило без шаблона, проверки, строки в инструкции роли или решения человека из стандарта удаляется: если его нечем обеспечить, оно ничего не значит.
2. **Предпочтение — проверке.** Правило переводится в инструкцию роли, только если его невозможно проверить автоматически. Проверку не нужно помнить, она срабатывает сама.
3. **Бюджет текста для ИИ.** `AGENTS.md` — не больше 150 строк, инструкция роли — не больше 40 строк. Превышение ловит проверка `standard`.
4. **Сообщение об ошибке — это инструкция.** Каждая проверка при провале пишет, что нарушено, почему это важно и что сделать. ИИ узнаёт правило ровно в момент, когда оно нужно, и только его.
5. **Нет уровня выше.** Проверки стандарта — это код продукта, и их правильность доказывается тестами продукта с плохими примерами. Ни ИИ, ни отдельный «стандарт соблюдения» для этого не нужны.

### Что всё равно держится на инструкции или на человеке, а не на проверке

Честно: часть правил автоматически проверяется только частично.

- Протокол «перед решением найди существующий код» до конца проверить нельзя: CI видит, что раздел «Основания» заполнен, но не видит, был ли поиск добросовестным. То же с поиском в истории при петле.
- Раздел «Влияние на цель» CI проверяет на наличие и на ссылку на G, но не на честность: ИИ может написать «нужен для G2», когда это не так. Защита — карточка решения, где владелец видит и критерий, и обходной путь, и число попыток, и может не согласиться.
- Тесты приёмки пишет ИИ; что они проверяют нужное — подтверждает только ревью в чистом контексте.
- Синхронизация знаний Project перед сессией — действие человека; стандарт лишь делает заметным, когда оно пропущено.
- Остановка CI (квота, бюджет) видна владельцу только из письма GitHub: табло в этот момент не обновляется, потому что его строит тот же CI.

Нарушения ловятся косвенно: ревьюер в чистом контексте, рост дублирования под храповиком, повторные инциденты в `state/incidents/`.

## 13. Открытые вопросы реализации

Вопросы, на которые у стандарта пока нет ответа, и которые `/parch:init-project` должен решить до того, как обещать владельцу «скажи словами — и табло обновится».

1. **Транспорт заданий планировщика.** Как текст задания на обновление плана попадает от Claude Project к исполнителю, который оформит его как PR. Варианты: владелец копирует текст сам; задание сохраняется как файл в знаниях Project и подхватывается; исполнитель запускается по расписанию и читает очередь. До решения — владелец копирует сам, и это должно быть сказано ему прямо.
2. **Живое состояние для планировщика.** Снимок с кнопкой «Sync» достаточен, если владелец нажимает её перед каждой сессией. Если найдётся подключение GitHub с живым чтением файлов, стандарт переходит на него, и правило о синхронизации из раздела 4 удаляется как лишнее (правило без нужды — по правилу 1 раздела 12).
3. **Слияние PR с решением владельца.** Сейчас это кнопка на GitHub. Нужно проверить, что владельцу без опыта достаточно инструкции в три строки в `STATUS.md`, и что защищённая ветка не требует от него ничего больше.
4. **Минуты CI на табло.** Расход за цикл и за блок GitHub отдаёт через API (billing и workflow runs), но нужен токен с правом чтения billing, а это настройка владельца. До решения табло показывает хотя бы длительность последних прогонов из того, что доступно workflow без токена.
