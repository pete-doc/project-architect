# BUILD_PLAN — ProjectArchitect

*Техническое задание для Claude Code. Положить в корень репозитория `project-architect` и выполнять по одной фазе за сессию.*

## 1. Что строим

ProjectArchitect — набор инструментов, который подключается к любому программному проекту и держит ИИ-разработку под контролем: следит за архитектурой, стандартами, дублированием, мёртвым кодом и лишними файлами и показывает человеку состояние проекта без чтения кода. Подробное обоснование — в документах проекта: «Сервис автономной ИИ разработки» (исследование) и «Модуль анализа существующего проекта» (дизайн).

Продукт состоит из двух частей в одном репозитории:

- **Плагин Claude Code (plugin)**: роли агентов, hooks, skills (`/init-project`, `/analyze-existing`, `/adr`, `/status`).
- **Шаблоны (templates)**: CI-файлы GitHub Actions по языкам, шаблоны документов (`CONSTITUTION.md`, `MODULES.md`, `INTERFACES.md`, `LESSONS.md`, ADR), генератор `STATUS.md`.

Поддерживаемые языки целевых проектов: Python, TypeScript, C#, PowerShell.

Владелец продукта — не программист и код не читает. Все решения и отчёты для него пишутся на русском, на языке последствий («что изменится, что будет при ошибке, как откатить»), а не реализации.

## 2. Правила работы (обязательны в каждой фазе)

1. **Одна фаза — одна ветка — один pull request.** Работа напрямую в `main` запрещена.
2. **Сначала документация, потом код.** Перед началом фазы прочитай актуальную официальную документацию Claude Code по тем механизмам, которые используешь (plugins, hooks, subagents, skills, settings/permissions) на code.claude.com/docs. Не полагайся на память: форматы меняются. Если документация расходится с этим планом, побеждает документация, а расхождение запиши в описание PR.
3. **Кроссплатформенность.** Владелец работает на macOS и на Windows 11. Все hooks и скрипты пишутся на Python 3 (не bash и не PowerShell) и тестируются так, чтобы работать на обеих системах. Пути — только через `pathlib`.
4. **Каждая проверка доказывает, что она ловит нарушение.** Для каждого hook и каждого правила CI нужен тест с заведомо плохим примером, который проверка обязана остановить. Проверка без такого теста не считается сделанной.
5. **Минимум файлов.** Новый файл создаётся, только если без него нельзя. Никаких промежуточных планов, заметок и отчётов в корне: рабочие заметки не коммитятся, а решения идут в `docs/adr/`.
6. **Решения записываются.** Любой выбор, который трудно отменить (структура плагина, формат данных, новая зависимость), оформляется как ADR со статусом `proposed` и ждёт утверждения владельцем. Обратимые решения агент принимает сам, но тоже фиксирует в ADR.
7. **Описание PR — на русском**, в трёх разделах: «Что сделано», «Какие решения приняты и почему», «Как проверить, что работает» (с выводом тестов, а не словами «всё работает»).
8. **Нельзя объявлять фазу готовой**, пока CI не зелёный и не выполнены все критерии приёмки фазы.

## 3. Структура репозитория продукта

```
project-architect/
  AGENTS.md                 # ≤150 строк: как собирать, тестировать, правила из раздела 2
  CLAUDE.md                 # @AGENTS.md + краткая специфика Claude
  BUILD_PLAN.md             # этот файл
  plugin/                   # сам плагин Claude Code (структура — по актуальной документации)
    agents/                 # architect, implementer, reviewer, janitor, explorer
    hooks/                  # Python-скрипты hooks
    skills/                 # init-project, analyze-existing, adr, status
  templates/
    docs/                   # CONSTITUTION, MODULES, INTERFACES, LESSONS, QUESTIONS, adr/0000-template.md
    ci/                     # python.yml, typescript.yml, csharp.yml, powershell.yml, status.yml, review.yml
    state/                  # features.json (пустой), STATUS.md (шаблон)
  tests/                    # тесты самого продукта, включая «плохие примеры»
  docs/adr/                 # решения по самому продукту
  .github/workflows/ci.yml  # CI самого продукта
```

## 4. Фазы

### Фаза A. Скелет и CI самого продукта

**Задачи.** Создать структуру из раздела 3 с пустыми местами под будущие части. Настроить CI самого репозитория: линтер и проверка типов для Python (ruff, pyright), запуск тестов (pytest), запуск на Ubuntu и Windows. Написать AGENTS.md и CLAUDE.md. Подготовить ADR-0001 «Форма продукта: плагин + шаблоны» и ADR-0002 «Hooks и скрипты на Python ради macOS и Windows».

**Приёмка.**
- CI зелёный на Ubuntu и Windows.
- Есть тест, который специально падает при нарушении стиля, и CI его ловит. Пример показан в описании PR, после чего нарушение убрано.
- Плагин устанавливается в пустой тестовый проект и виден в Claude Code (пусть пока и ничего не делает).
- ADR-0001 и ADR-0002 лежат со статусом `proposed`.

### Фаза B. Hooks

**Задачи.** Реализовать hooks:
- `guard_paths`: запрет правки тестов, настроек Claude, CI-файлов, `state/features.json` и принятых ADR для роли implementer; запрет создавать `.md` вне `docs/`.
- `guard_packages`: установка пакетов только из разрешённого списка в CONSTITUTION; новый пакет требует ADR.
- `guard_destructive`: блок `rm -rf`, `git push --force`, обращений к секретам.
- `post_edit_check`: после правки файла запускать форматтер, линтер и проверку типов для его языка и возвращать агенту только строки с ошибками.
- `stop_gate`: не давать закончить, пока не пройдены тесты и проверки; учитывать флаг повторного срабатывания, чтобы не зациклиться.
- `audit_log`: журнал всех команд и решений hooks в `.claude/audit/`.
Плюс правила permissions, запрещающие агенту править конфигурацию hooks.

**Приёмка.** Для каждого hook есть тест: попытка нарушения → блок → понятное сообщение агенту. Тесты проходят на macOS и Windows. В описании PR — таблица «hook → что блокирует → пример блокировки».

### Фаза C. Шаблоны документов, `/init-project` и `/adr`

**Задачи.** Шаблоны всех документов из `templates/docs/`, каждый с короткой инструкцией внутри. Skill `/init-project`: задаёт владельцу 3–5 вопросов на русском (что за проект, какие языки, что важно), копирует шаблоны, создаёт CONSTITUTION с выбранным стеком и проставляет CI под языки. Skill `/adr`: создаёт запись решения, делит решения на обратимые и необратимые, для необратимых пишет одностраничное объяснение на русском для владельца.

**Приёмка.** На пустом тестовом проекте `/init-project` создаёт рабочую структуру, и CI в нём сразу зелёный. `/adr` создаёт корректный файл и обновляет индекс `docs/adr/README.md`.

### Фаза D. CI по языкам

**Задачи.** Шаблоны CI в порядке: Python → TypeScript → C# → PowerShell.

| Язык | Типы | Линтер | Архитектура | Мёртвый код | Дубли | Тесты |
|---|---|---|---|---|---|---|
| Python | pyright | ruff | import-linter | vulture, deptry | jscpd | pytest + coverage |
| TypeScript | tsc strict | ESLint/Prettier или Biome | dependency-cruiser | knip | jscpd | Vitest/Jest |
| C# | компилятор, nullable, warnings as errors | .NET analyzers, dotnet format, Roslynator | ArchUnitNET или NetArchTest.eNhancedEdition | IDE0051/IDE0052, Roslynator | jscpd | xUnit + coverlet |
| PowerShell | — | PSScriptAnalyzer | свой скрипт-проверка | покрытие Pester | jscpd (проверить) | Pester |

Общие проверки для всех: «число тестов не уменьшилось», «каждый модуль есть в MODULES.md», режим «храповика» (метрики дублирования и мёртвого кода не растут относительно сохранённого baseline). C# и PowerShell запускаются на Windows-runner.

**Приёмка.** Для каждого языка есть маленький тестовый проект с намеренными нарушениями (дубль, мёртвая функция, запрещённая зависимость, удалённый тест), и CI ловит каждое. Отдельно проверено, что «храповик» пропускает старые нарушения и блокирует новые.

### Фаза E. `/analyze-existing`

**Задачи.** Реализовать шесть шагов из документа «Модуль анализа существующего проекта»: инвентаризация, baseline, карта (`MODULES.md`, `INTERFACES.md`), восстановленные ADR и `QUESTIONS.md`, отчёт `analysis/ANALYSIS_REPORT.md` с карточкой здоровья на русском, проверка отчёта отдельным reviewer-агентом. Шаги 1–5 ничего не меняют в коде.

**Приёмка.** Прогон на тестовом проекте из четырёх языков с межъязыковыми швами: швы найдены и внесены в INTERFACES.md, карточка здоровья заполнена, в коде нет ни одного изменения (проверяется через `git diff`).

### Фаза F. Табло, janitor и ревью

**Задачи.** `status.yml`: после каждого слияния и по расписанию пересчитывает `features.json` по реальным тестам и генерирует `STATUS.md` (проходящие фичи, число тестов и его динамика, PR с правкой тестов, ADR на утверждении, тренды дублирования и мёртвого кода, число файлов). Агент janitor по расписанию открывает небольшие PR на удаление подтверждённого мёртвого кода с архивным тегом в git; модули со статусом `keep-until` не трогает. `review.yml`: ИИ-ревью PR только на корректность и соответствие спецификации. Skill `/status` — объяснение табло на русском.

**Приёмка.** На тестовом проекте STATUS.md обновляется сам после слияния; janitor не удаляет модуль с `keep-until`; ревью оставляет замечания только по существу.

### После фаз: пилот

Прогнать `/analyze-existing` на одном реальном проекте владельца. Результаты пилота и найденные проблемы продукта записать в `docs/adr/` и задачи следующего цикла. Только после пилота писать инструкции Claude Project как пульта управления.

## 5. Первый промпт для Claude Code

> Прочитай BUILD_PLAN.md полностью. Выполни фазу A. Перед началом прочитай актуальную документацию Claude Code по plugins, hooks и settings. Работай в отдельной ветке, открой pull request с описанием на русском по правилу 7. Если что-то в плане неясно или противоречит документации — сначала спроси меня.
