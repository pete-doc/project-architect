# Разбор существующего проекта

Исходный документ: `docs/design/analyze-existing.md` в репозитории ProjectArchitect (таблица инструментов по языкам,
карточка здоровья, раздел «Что анализ не делает»). Спецификация: `docs/specs/F15-analyze-existing.md`.

Ты проверяешь, насколько существующий проект соответствует стандарту ProjectArchitect, и готовишь план приведения.
Владелец не программист: пиши по-русски, коротко, на языке последствий (что есть, чего нет, что будет, если оставить
как есть), без терминов реализации. Ты **ничего не меняешь в коде проекта**: единственное, что ты создаёшь, это
папка `parch-analysis/` (отчёт `parch-analysis/ANALYSIS_REPORT.md` и файлы, которые пишут команды скрипта). Папка
`analysis/` и любые другие папки проекта принадлежат владельцу: в них ты не пишешь ничего.

Этот навык ничего не удаляет, не переписывает архитектуру и не угадывает намерения: всё, что касается смысла, идёт
вопросом владельцу (`QUESTIONS.md`). Найденный «мёртвый» код сначала вопросы, потом решение владельца, и только потом
удаление отдельным PR с архивной меткой.

Не запускай тесты проекта, пока владелец не разрешил; если тесты могут запускать игру, сервер или трогать данные,
сначала спроси. Чтобы разделить тесты на «безопасные» и «опасные», сначала только читай их: опасен не тот тест, который
запускает процесс, а тот, чья запускаемая программа по умолчанию пишет или трогает игру, данные, сейвы или настоящие
скрипты проекта, если тест не передал ей временный путь (проверь, что будет, если подмена не сработает). Список обоих
видов покажи владельцу и запускай только безопасные и только после его «да», по одному файлу, с лимитом времени, без
следов в проекте (`PYTHONDONTWRITEBYTECODE=1`, `-p no:cacheprovider`). В карточке опасные идут как «не запускались
анализом», а не как провал. Не пытайся обойти блокировку hook: остановись и напиши владельцу.

## Шаг 0. Предупреди владельца и узнай границы

Напиши: «Я изучаю проект и ничего в нём не меняю. Новые файлы только в `parch-analysis/`. Что нельзя трогать вообще
(например, сейвы, данные, выгрузку), и можно ли запускать линтеры, проверку типов, сборку и поиск дублей в режиме
«только отчёт»?» Неприкосновенные зоны (`protected_paths`) возьми из ответа и из инструкций проекта.

## Шаг 1. Собери факты

Папка проекта: `$ARGUMENTS`, если передан, иначе текущая.

```bash
sh "${CLAUDE_PLUGIN_ROOT}/hooks/run-hook.cmd" ../skills/analyze-existing/scripts/analyze.py <<'JSON'
{"command": "inventory", "project_dir": ".", "protected_paths": ["data/", "saves/"], "game_markers": ["steam.exe"]}
JSON
```

Если скрипт отказался работать, потому что папка `parch-analysis/` уже существует, **остановись и спроси
владельца**, как быть: не удаляй и не перезаписывай её сам. Повторный анализ (чтобы сравнить «было/стало») идёт в
новую папку: добавь во все команды `"report_dir": "parch-analysis-2"` (допустимо `parch-analysis-<слово>`), старая
папка остаётся нетронутой. Состояние папки «до» скрипт сохранил сам (вне проекта),
передавать его на шаге 7 не нужно. Если `git.is_repo` равно `false`, скажи владельцу, что «ничего не менялось»
проверить нельзя, и продолжай.

В ответе: `equivalents` (равноценные файлы: засчитываются в карточку без штрафа, имена приводит к стандарту план),
`tools` (какие инструменты из таблицы документа настроены), `hotspots` (горячие точки по истории git),
`dead_code` (кандидаты в мёртвый код), `modules` (модули по папкам и языкам с назначением и статусом), `seams` (швы
между языками: запуск одного языка из другого и общий файл данных; у каждого поле `red`: `true`, если контрактного
теста нет), `risks`, `plan` (таблица действий), `p_card`, `health_card`.

## Шаг 2. Снимок инструментов (только с разрешения)

Если владелец разрешил запуск, перечисли допустимые инструменты из списка скрипта (`ruff`, `pyright`, `vulture`,
`jscpd`, `dotnet-build`, `dotnet-format`, `tsc`, `psscriptanalyzer`) и запусти только разрешённые, в режиме «только
отчёт»:

```bash
sh "${CLAUDE_PLUGIN_ROOT}/hooks/run-hook.cmd" ../skills/analyze-existing/scripts/analyze.py <<'JSON'
{"command": "baseline", "project_dir": ".", "run": ["ruff", "pyright"], "protected_paths": ["data/", "saves/"]}
JSON
```

Результаты ложатся в `parch-analysis/baseline/` (JSON) и уже разобраны в числа (`metrics`). Особенности:

- `ruff` меряется по правилам стандарта (E, F, I, B, UP, строка 100), а не по набору «по умолчанию»; в карточке
  отдельно видно, сколько замечаний исправляется автоматически.
- `dotnet-build` и `dotnet-format` идут по каждому `.csproj` (или `.sln`), а не из корня. Если в проектах есть шаги
  после сборки (копирование, запуск команд), сборка не запускается: **остановись и напиши владельцу**, что нашёл;
  `allow_build_steps` ставь только по его слову.
- `jscpd`, если не установлен, не запускается без разрешения на скачивание: спроси владельца (скачивается пакет
  `jscpd@5.4.0` во временную папку вне проекта), и только после «да» добавь `"allow_download": true`.
- Неприкосновенные зоны (`protected_paths`) исключаются из `ruff`, `vulture`, `jscpd`, `PSScriptAnalyzer`.
- Если у инструмента `metrics` пустой, а статус «выполнен», вывод не разобрался: это ошибка навыка, заведи её в
  `docs/BACKLOG.md` и скажи владельцу; цифру не придумывай.

Без разрешения пропусти шаг: карточка тогда честно скажет «не измерялось». Если владелец разрешил запустить безопасные
тесты, положи итог файлом `parch-analysis/baseline/tests.json` (`{"tool": "tests", "status": "выполнен", "metrics":
{"files_run", "tests_passed", "tests_failed", "files_not_run"}}`) до шага 3: карточка его подхватит.

## Шаг 3. Запиши материалы анализа

```bash
sh "${CLAUDE_PLUGIN_ROOT}/hooks/run-hook.cmd" ../skills/analyze-existing/scripts/analyze.py <<'JSON'
{"command": "write", "project_dir": ".", "protected_paths": ["data/", "saves/"]}
JSON
```

Скрипт создаёт в `parch-analysis/`: `QUESTIONS.md` (вопросы по процессу и по мёртвому коду: один простой вопрос на
файл, ответ А/Б/В; обработчики фреймворков, код с атрибутами и сгенерированные файлы отсеяны заранее; в вопросы
владельцу попадает только то, что требует знания о проекте), `PLAN.md` (таблица действий), `drafts/GOAL.md`,
`drafts/ADR-DRAFTS.md`, `drafts/MODULES.md` (карта модулей), `drafts/INTERFACES.md` (швы между языками; шов без
контрактного теста помечен красным) (всё помечено «черновик, ждёт утверждения»), `facts.json`. Если `plan_problems` не пуст, строка плана нарушает предохранитель:
исправь план, а не предохранитель.

## Шаг 4. Прочитай нужное и уточни оценки

- Файлы из `instruction_files`: для P3 и P9 ищи противоречия и требование искать существующий код, называй файлы.
- Равноценные файлы (`equivalents`): прочитай начало, убедись, что роль определена верно; если нет, исправь оценку и
  добавь вопрос владельцу.
- Оценки из `p_card` предварительные: уточни их по тексту, не завышай. P4, P8, P12 не угадывай: оформи вопрос.
- Швы (`seams`): поиск по тексту приблизительный. Для каждого красного шва открой места из `evidence` и скажи, шов
  ли это на самом деле (общее имя файла в двух языках бывает случайным); найденный тест, названный «контрактным», прочитай:
  проверяет ли он именно стык (формат файла, аргументы запуска), а не просто упоминает имя. Ошибочный шов не прячь,
  а оформи вопросом владельцу. Изменение шва в плане идёт только после контрактного теста этого шва.
  Красные швы делятся на две группы по риску (`group` в `seams`, причины в `group_reasons`): **(а)** трогают игру,
  сейвы или `data/` (файл шва в неприкосновенной зоне, запись вне проекта, запись в зону, слово игры из
  `game_markers` в коде): каждому своя строка «Контрактный тест» в `PLAN.md`, она идёт до любых изменений, тест только
  читает файлы шва и не запускает скрипты. Шов попадает в (а) и по цепочке вызовов: если скрипт шва запускает или
  подключает (путь к файлу, импорт) скрипт со словами игры, прямо или через один шаг, причина записана как «запускает
  X» или «через X запускает Y». Слово игры бывает регулярным выражением с приставкой `re:` (например,
  `re:Stop-Process[^\n]*\bfm\b`: остановка процесса считается только вместе с `fm`). **(б)** остальные: строк нет, условие «сначала контрактный тест» действует,
  только если строка плана меняет одну из сторон шва. В отчёте назови, сколько швов в каждой группе. Слова игры
  (`game_markers`: процесс игры, её папка, мод-загрузчик) и файлы-зоны (`protected_paths` принимает и пути к
  файлам, например скрипт, который загружает сейв) спроси у владельца вместе с зонами, не угадывай.
- Что считается контрактным тестом: тест, который обращается к коду обеих сторон шва и сверяет формат (колонки, поля,
  код возврата). Обращение это путь к файлу или его имя с расширением, импорт модуля или вызов класса; слово, равное
  имени файла без расширения (`run`, `harvest`), стороны не называет. Тест, который только называет файл или скрипт, не засчитывается (скрипт
  показывает такие тесты в `weak_tests` и оставляет шов красным); два теста, каждый про свою сторону, тоже. Имена в
  комментариях и docstring не считаются (это пояснение, а не обращение к коду). Прочитай
  и засчитанные тесты: скрипт смотрит на текст, а не на смысл.
- Файлы, пишущие за пределы проекта (`outside_writes`: папка игры, BepInEx, Steam, другие диски): в карте и в плане они
  помечены «неприкосновенная зона, нужно отдельное «да»». Прочитай каждый такой файл и подтверди или сними пометку
  (скрипт ищет по тексту: путь вне проекта и операция записи, в которую он попал). Файл, который только читает вне
  проекта или управляет игрой через сервис, не пишет файлы вне проекта; если он тревожит, оформи вопрос владельцу.
- Модули (`modules`): у каждого модуля без описания («описания нет: вопрос владельцу») оформи вопрос, не выдумывай
  назначение.

## Шаг 5. Напиши отчёт `parch-analysis/ANALYSIS_REPORT.md`

Создай файл (папка уже есть, её создал скрипт) со структурой:

1. **Коротко.** 3-5 строк: что за проект, на чём он, главный вывод.
2. **Карточка здоровья по языкам** (`health_card`): сигнал, значение, тревожно ли; что не измеряли, так и пиши.
3. **Карточка процесса P1-P13:** оценка (**отсутствует / частично / по стандарту / вопрос владельцу**) и что это значит.
4. **Что есть в проекте:** языки, тесты, CI, инструменты по таблице документа, горячие точки, карта модулей
   (`drafts/MODULES.md`) и швы между языками (`drafts/INTERFACES.md`): сколько швов и сколько без контрактного теста.
5. **Главные риски (5-10)** по убыванию: что может сломаться и чем это грозит.
6. **Решения, ждущие вас:** одна строка на каждый черновик в `drafts/`.
7. **План приведения к стандарту:** таблица из `PLAN.md` целиком, с пометками «нужно отдельное «да»».
8. **Вопросы владельцу:** `QUESTIONS.md`.
9. **Что анализ не делает:** не удаляет, не переписывает архитектуру, не гарантирует понимания намерений.
10. **Что не вошло в эту версию:** каталог возможностей и описания функций, архитектурные правила и протокол
    исполнителя: это следующие PR блока F15.

## Шаг 6. Проверка отчёта отдельным агентом

Перед выдачей отчёта запусти отдельного агента в чистом контексте (инструмент Agent, без платного API): он читает
только `parch-analysis/ANALYSIS_REPORT.md`, `parch-analysis/facts.json` и `parch-analysis/baseline/` и перечисляет
утверждения отчёта, которых нет в данных или которые им противоречат (выдуманные связи, неверные числа). Исправь
отчёт по его замечаниям; если замечаний нет, так и скажи владельцу.

## Шаг 7. Проверь, что код не менялся

```bash
sh "${CLAUDE_PLUGIN_ROOT}/hooks/run-hook.cmd" ../skills/analyze-existing/scripts/analyze.py <<'JSON'
{"command": "verify", "project_dir": "."}
JSON
```

Новые файлы допускаются только в `parch-analysis/` (и след разрешённой сборки C#: `bin/`, `obj/`); правка любого
другого файла, даже уже изменённого до тебя, и новый файл вне этой папки (в том числе в `analysis/`) считаются
нарушением. Если `ok` равно `false`, остановись: перечисли владельцу `changed` и скажи, что отчёт нельзя считать
безопасным. Ничего не откатывай сам без вопроса.
