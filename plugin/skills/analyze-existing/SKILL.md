# Разбор существующего проекта (упрощённая версия)

Ты проверяешь, насколько существующий проект соответствует стандарту ProjectArchitect. Владелец не программист:
пиши по-русски, коротко, на языке последствий (что есть, чего нет, что будет, если оставить как есть), без терминов
реализации. Ты **ничего не меняешь в коде проекта**: единственное, что ты создаёшь, это файл отчёта
`analysis/ANALYSIS_REPORT.md`.

В эту версию входят: инвентаризация, карточка процесса P1-P13, отчёт о разрыве, вопросы владельцу и проверка «код
не менялся». Не входят (делаются позже): запуск проверок проекта и baseline, карта модулей и швов между языками,
восстановленные ADR, проверка отчёта отдельным reviewer. Скажи об этом владельцу в отчёте, чтобы он не думал, что это сделано.

Не запускай тесты, сборку или установку пакетов проекта. Не пытайся обойти блокировку hook: остановись и напиши владельцу.

## Шаг 0. Предупреди владельца

Напиши: «Я только читаю проект и ничего в нём не меняю. Единственный новый файл: `analysis/ANALYSIS_REPORT.md`.
Если изменится что-то ещё, я остановлюсь и скажу.»

## Шаг 1. Собери факты

Папка проекта: `$ARGUMENTS`, если передан, иначе текущая.

```bash
sh "${CLAUDE_PLUGIN_ROOT}/hooks/run-hook.cmd" ../skills/analyze-existing/scripts/analyze.py <<'JSON'
{"command": "inventory", "project_dir": "."}
JSON
```

Запомни весь ответ. Поле `git.snapshot` понадобится на шаге 4 как есть (оно показывает, что было в папке до тебя).
Если `git.is_repo` равно `false`, скажи владельцу, что «ничего не менялось» проверить нельзя, и продолжай.

## Шаг 2. Прочитай нужное

- Файлы из `instruction_files`: для P3 (одно место, короткие, без противоречий) и P9 (требование искать существующий
  код и опираться на файлы). Противоречия ищи по тексту, называй файлы и строки.
- `docs/GOAL.md` или `GOAL.md`, если есть: для P1 оцени, проверяемы ли критерии.
- Если в `p_card` стоит «вопрос владельцу» (P4, P8, P12), не угадывай: оформи вопрос, как он дан в `questions`.

## Шаг 3. Напиши отчёт `analysis/ANALYSIS_REPORT.md`

Создай папку `analysis/` и файл со структурой:

1. **Коротко.** 3-5 строк: что за проект, на чём он, главный вывод.
2. **Карточка процесса.** Таблица: пункт P1-P13, оценка (**отсутствует / частично / по стандарту / вопрос владельцу**),
   что это значит для владельца. Оценки из `p_card` предварительные: уточни их по тексту, но не завышай.
3. **Что есть в проекте.** Языки и число файлов, тесты, CI (таймауты, запуск, раннеры), папки и документы.
4. **Главные риски.** Не больше пяти, по убыванию: что может сломаться и чем это грозит.
5. **Что делать дальше.** Небольшие PR от безопасных к рискованным: сначала документы и структура (цель, реестры,
   инструкции), потом CI в режиме храповика, потом уборка и рефакторинг. Код меняется только после того, как владелец
   утвердил цель и решения.
6. **Вопросы владельцу.** Из `questions` плюс всё, что ты не смог определить по файлам.
7. **Что не вошло в эту версию.** Список из начала этого файла.

## Шаг 4. Проверь, что код не менялся

```bash
sh "${CLAUDE_PLUGIN_ROOT}/hooks/run-hook.cmd" ../skills/analyze-existing/scripts/analyze.py <<'JSON'
{"command": "verify", "project_dir": ".", "before": "ВСТАВЬ git.snapshot ИЗ ШАГА 1 КАК СТРОКУ"}
JSON
```

Если `ok` равно `false`, остановись: перечисли владельцу `changed` и скажи, что отчёт нельзя считать безопасным.
Ничего не откатывай сам без вопроса.

## Шаг 5. Скажи владельцу итог

Пять строк по-русски: где лежит отчёт, главный вывод, три самых важных риска, какие вопросы ждут ответа, подтверждение
«код не менялся» (или что проверить было нельзя).
